# Distributed Caching

## Why caching is used
Caching stores frequently accessed data in a faster layer so systems can:
- Save network calls
- Avoid repeated computation
- Reduce load on database and downstream services
- Improve response latency

Interview one-liner:
“Caching improves read performance by serving hot data from a fast layer instead of recomputing or querying slower systems repeatedly.”

---

## Why cache is not “free”

Your note is correct: cache can be expensive and must be sized carefully.

### Important realities
1. **Cost**
	- Memory (RAM) is significantly more expensive than disk.

2. **Too much cache data can hurt performance**
	- Bigger cache is not always better if eviction/indexing/replication overhead increases.
	- Larger working set may reduce effective hit ratio if key patterns are poor.

3. **Too small cache causes thrashing**
	- Hot items get evicted too fast.
	- System repeatedly misses cache and hits DB.
	- This produces high I/O and unstable latency.

Interview phrase:
“A cache that cannot hold the hot working set behaves like a miss machine.”

---

## Cache policies (admission + eviction)

Cache policy answers two questions:
1. **Admission**: which data should enter cache?
2. **Eviction**: which data should be removed when full?

### Common eviction policies

## LRU (Least Recently Used)
- Evicts entries not used recently.
- Works well when recent access predicts near-future access.

Pros:
- Simple and widely used

Cons:
- Can perform poorly for scan-heavy workloads

## LFU (Least Frequently Used)
- Evicts entries used least often.
- Better for stable hot keys over long periods.

Pros:
- Strong for long-term popularity patterns

Cons:
- Can keep stale “historically popular” keys unless decay is applied

Interview tip:
Mention modern variants like TinyLFU/W-TinyLFU for better admission decisions.

## Types of cache

## 1) Local in-memory cache (near application)
- Stored inside app process (e.g., Caffeine/Guava in Java, in-memory map).
- Fastest access (no network hop).

Pros:
- Very low latency
- Reduces pressure on shared cache tier

Cons:
- Each app instance has its own copy (invalidation harder)
- Memory duplication across instances
- Not resilient to process restart

## 2) Distributed/global cache (Redis/Memcached)
- Shared cache cluster accessed over network.

Pros:
- Centralized cache state
- Better resilience and horizontal scaling
- Useful across multiple app instances/services

Cons:
- Network latency vs local cache
- Operational overhead (clustering, failover, persistence strategy)

---

## Multi-layer cache (hybrid)

Hybrid approach combines both:
- L1: local in-process cache
- L2: distributed Redis cache
- L3: database/source of truth

Read flow:
1. Check L1
2. Miss -> check L2
3. Miss -> query DB, then populate L2 and optionally L1

Why it works:
- L1 gives ultra-low latency for hottest keys
- L2 gives shared consistency across servers

## Write strategies in caching

### Write-through
On write:
1. Write DB
2. Write cache immediately

Pros:
- Cache remains fresh
- Good read-after-write behavior

Cons:
- Higher write latency
- Need consistency handling across app nodes/local caches

Your question (“What happens to other server in-memory cache?”):
- Their local caches become stale unless invalidation/broadcast is used.
- Common fix: publish invalidation events via message bus.

### Write-back (write-behind)
On write:
1. Write cache first
2. Persist to DB asynchronously later

Pros:
- Very low write latency
- Good for bursty write workloads

Cons:
- Data loss risk if cache fails before DB flush
- Recovery and durability complexity

Best for non-critical or carefully engineered pipelines.

### Write-around
On write:
1. Write directly to DB
2. Do not cache immediately
3. Cache only when subsequent read occurs

Pros:
- Avoids polluting cache with cold write-only data

Cons:
- First read after write is a cache miss

## Cache consistency challenges

1. **Stale data**
	- Cache may serve outdated values after DB updates.

2. **Invalidation complexity**
	- “There are only two hard things: cache invalidation and naming things.”

3. **Cross-node local cache coherence**
	- One node updates value; other nodes still serve old local copies.

Solutions:
- TTL + versioned keys
- Event-driven invalidation
- Cache-aside with explicit delete on write
- Short TTL on volatile entities

---

## Failure patterns and protections

### Cache stampede
Many requests miss same key and hit DB simultaneously.

Fixes:
- Request coalescing / single-flight
- Probabilistic early refresh
- Stale-while-revalidate

### Thundering herd on expiry
Many hot keys expire at same time.

Fix:
- Add TTL jitter (randomized expiration windows)

### Cache penetration
Repeated queries for non-existent keys hit DB.

Fixes:
- Negative caching
- Bloom filters in front of DB

---

## Sizing and capacity planning

Key interview points:
- Estimate hot working set size
- Target hit ratio based on latency SLO
- Monitor eviction rate and miss penalty
- Plan shard count and replication factor

Useful metrics:
- Cache hit rate / miss rate
- p95 latency from cache and DB
- Evictions/sec
- Memory fragmentation
- Network throughput

---

## Real-world example

E-commerce product page:
1. Product metadata and price are read-heavy.
2. Keep product details in Redis (L2), hottest products in L1.
3. On price update, write DB and invalidate cache key.
4. Next read repopulates cache.

Result:
- Lower DB QPS
- Faster page loads
- Controlled consistency with explicit invalidation

---

## Interview trade-offs summary

Advantages:
- Lower latency
- Lower DB load
- Better scalability for read-heavy systems

Challenges:
- Consistency and invalidation complexity
- Extra operational tier
- Memory cost and tuning effort

---

## One-line interview summary
“Distributed caching reduces latency and database pressure by serving hot data from memory, but success depends on choosing the right cache policy, write strategy, and invalidation model to control staleness and thrashing.”
