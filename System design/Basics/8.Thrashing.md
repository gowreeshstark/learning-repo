# Thrashing in Operating Systems

**Reference:** [TakeUForward - Why Does Thrashing Occur?](https://takeuforward.org/operating-system/why-does-thrashing-occur)

---

## Overview

**Thrashing** occurs when the CPU spends more time **paging (swapping memory to disk)** than actually **executing instructions**. It's a performance crisis where the system becomes unresponsive due to excessive page faults and disk I/O.

> **Interview one-liner:** Thrashing = the system spending more time swapping memory to disk than doing useful work.

---

## Definition

**Thrashing** is a condition where **CPU utilization falls sharply** due to excessive paging activity. The system enters a thrashing state when:

1. Too many processes are in memory
2. Each process needs more memory **frames** than available
3. Processes frequently cause **page faults** (accessing pages not in memory)
4. The OS spends most time handling page faults instead of executing processes
5. CPU utilization drops dramatically
6. System becomes extremely slow and unresponsive

### Thrashing Symptoms
- **Low CPU utilization** (20-30% when it should be 80%+)
- **High disk activity** (constant disk reads/writes)
- **Long response times** for user input
- **System appears frozen** or sluggish
- Page fault rate sky-rockets
- **Disk I/O queue** very long

---

## Why Does Thrashing Occur?

### Root Cause: Over-Subscription
Too many processes competing for limited physical memory.

### The Thrashing Cycle

```
Problem: High Multiprogramming Degree
    ↓
Processes need more frames than available
    ↓
Frequent page faults occur
    ↓
OS constantly swaps pages to/from disk
    ↓
CPU idle, waiting for disk operations
    ↓
CPU utilization drops sharply
    ↓
CPU Scheduler tries to compensate → adds MORE processes
    ↓
❌ DISASTER: Problem gets WORSE, enters THRASHING
    ↓
More page faults, more disk activity...
    ↓
VICIOUS CYCLE continues
```

### Contributing Factors

| Factor | Impact |
|--------|--------|
| **High multiprogramming degree** | Too many processes in memory |
| **Small page size** | More pages needed, more page faults |
| **Limited physical memory** | Can't hold all active pages |
| **Poor replacement algorithms** | Evict pages that will be needed soon |
| **No admission control** | System loads too many new processes |
| **Synchronous paging** | CPU blocked waiting for disk I/O |

## Page Faults and Paging

### What is a Page Fault?
A **page fault** occurs when a process accesses a page that is not currently in memory. The CPU must:
1. Stop the process
2. Trigger **disk I/O** to load the page from disk
3. Wait (high latency, 10-100ms)
4. Resume the process once page is loaded

### Cost of Page Faults
- **Disk I/O:** ~10-100 milliseconds (extremely slow)
- **CPU context switching overhead**
- **TLB (Translation Lookaside Buffer) misses**
- **Cache flushes** when switching processes

### Thrashing in Detailed Steps

```
Time:    ┌─ Process A executing
         │   └─ Page fault (accessing page P1)
         │      └─ Disk I/O starts (10ms+)
         │         └─ CPU goes idle
         │            └─ CPU scheduler loads Process B
         │               └─ Process B executes
         │                  └─ Page fault (accessing page P2)
         │                     └─ Disk I/O starts
         │                        └─ CPU goes idle
         │                           └─ CPU scheduler loads Process C
         │                              ...
         │
    Result: CPU spending 90% time waiting for disk, 10% executing
```

## Working Set Model

The **Working Set Model** is a solution to prevent/minimize thrashing.

### Definition
A **working set** is the **set of pages a process actively uses within a time window Δ (delta)**.

```
Working Set (WS) = Set of pages accessed in last Δ time units
```

### Key Principles

1. **Working Set Size (WSS)** = number of frames process needs
   - If process has enough frames to hold all pages in its working set, it won't thrash
   - If allocated frames < WSS, page faults increase rapidly

2. **Total Memory Demand:**
   ```
   D = Σ (WSSᵢ for all processes)
   ```
   - Sum of all working set sizes
   - If D > Available Physical Memory → **THRASHING GUARANTEED**

3. **Locality:** Processes exhibit **temporal and spatial locality**
   - Working set reflects the "active" portion the process needs
   - Pages outside working set are rarely accessed

### Working Set Graph

```
CPU Utilization
     |
  80%|          ╱────────    (Sweet spot)
     |        ╱
     |      ╱
  60%|    ╱
     |  ╱
  40%|╱─────────────╲╲╲╲  (Thrashing region)
     |               ╲╲╲╲╲
  20%|                 ╲╲╲╲╲╲
     |____________________╲_____ Degree of Multiprogramming
     0   D1        D2              
```

- **Before D1:** Increasing processes increases CPU utilization (pages loaded, more work done)
- **At D1:** Peak efficiency (optimal)
- **After D2:** Thrashing begins; more processes = less CPU utilization

## Causes of Thrashing (Detailed)

### 1. Excessive Multiprogramming
```
Example:
- System has 16 GB RAM
- Each process needs ~4 GB working set
- OS loads 5 processes (20 GB > 16 GB available)
→ Immediate thrashing, constant page swaps
```

### 2. Large Working Sets
- Processes that access many different pages
- Example: Database with millions of records scanned in sequence

### 3. Insufficient Physical Memory
- Adding more processes to compensate for slow execution
- Worsens the problem

### 4. Process Stealing Frames
- One process causes page faults, steals frames from others
- Cascades: other processes now have insufficient frames
- All processes suffer more faults

### 5. Poor Page Replacement Algorithm
- Evicting pages that will be needed very soon
- Example: LRU fails when process has sequential access pattern

| Consequence | Impact |

| **Context Switching Hell** | Excessive % CPU time on switching, not work |
| **Memory Oscillation** | Pages swapped in/out repeatedly |
| **Deadline Misses** | Time-critical tasks fail |

## Solutions to Thrashing

### 1. Local Replacement Strategy (Most Important)

**How it works:**
- When a process needs a frame, **evict a page from THAT process** (not from others)
- Prevent one process from stealing frames from others
- Each process works with a guaranteed minimum set of frames

**Benefits:**
- Reduces cascading page faults
- If Process A thrashes, it doesn't drag down Process B
- Isolates the problem

```
Global Replacement (BAD):  Global Replacement (BAD):
Process A page fault         Process A page fault
 → evict any available page  → evict from Process B
 → steals Frame from B       → B now lacks frames
 → B gets more faults        → B also starts thrashing
 → cascading problem         → system-wide thrashing

Local Replacement (GOOD):
Process A page fault
 → evict a page from A only
 → other processes unaffected
 → A isolated to A's pages
```

### 2. Working Set Strategy

**How it works:**
1. **Monitor each process's working set size (WSS)**
2. **Ensure each process gets enough frames** to hold its working set
3. **Admit new processes only if total WSS ≤ available memory**
4. **Dynamically adjust** as working sets change

**Algorithm:**
```
For each process:
  - Calculate current WSS (pages used in last Δ time)
  - Allocate this many frames to process
  
Before admitting new process:
  - Required frames = current_total_WSS + new_process_WSS
  - If required > available memory:
    → SUSPEND a process (swap it out completely)
    → Free its frames
    → Now admit new process (or resume suspended)
```

**Advantages:**
- Eliminates thrashing by design
- Maximizes CPU utilization
- Fair frame allocation
- Adapts to changing workloads

### 3. Disable Page Swapping (Extreme)
- Prevent paging entirely
- All processes must fit in memory
- Trade-off: Lower multiprogramming degree, simpler system

### 4. Increase Physical Memory
- Add more RAM
- Simple but expensive/limited solution
- Eventually reaches hardware ceiling

### 5. Reduce Process Set / Load Shedding
- Run fewer processes
- Explicitly suspend non-critical tasks
- CPU scheduler stops adding new processes

### 6. Swap Entire Process
- Instead of page-by-page swapping
- Swap entire process to disk
- Resume later when memory available

## Thrashing vs Other Performance Issues

| Issue | Cause | Symptom | Solution |
|-------|-------|---------|----------|
| **Thrashing** | Too many processes, excessive paging | Very low CPU util, high disk I/O | Working set, local replacement |
| **Convoy Effect** | I/O blocking | CPU underutilized but not thrashing | Better scheduling |
| **Deadlock** | Circular wait for resources | Processes hang indefinitely | Prevention, detection, recovery |
| **Memory Leak** | Unreleased allocated memory | Gradually increasing memory use | Better memory management |

## Interview Quick-Fire Q&A

**Q: What is thrashing?**
Thrashing occurs when the OS spends more time paging (swapping) than executing processes, causing severe performance degradation.

**Q: What causes thrashing?**
Too many processes competing for limited memory; each needs more frames than available, causing excessive page faults.

**Q: How to detect thrashing?**
Low CPU utilization with high disk activity; constant page faults without progress.

**Q: What is a working set?**
The set of pages a process actively uses within a time window; size indicates frames needed.

**Q: How does the working set model prevent thrashing?**
Ensure each process gets enough frames to hold its working set; admit new processes only if total demand ≤ memory.

**Q: Local vs global page replacement?**
Local: evict from same process (isolates problem). Global: evict any page (can cascade faults).

**Q: Is thrashing the same as high CPU utilization?**
No; thrashing has LOW CPU utilization because CPU is idle waiting for disk I/O.

**Q: How to recover from thrashing?**
Suspend processes, use working set strategy, enable local replacement, or disable paging temporarily.

## Key Takeaways

- **Thrashing** = excessive paging, low CPU utilization, system unresponsive.
- **Root cause:** Over-subscription — more processes than memory can handle.
- **Working set:** Set of pages process needs; D = Σ WSS is key metric.
- **If D > Available Memory** → thrashing is guaranteed.
- **Local replacement** prevents cascading faults.
- **Working set strategy** ensures processes get needed frames.
- **Modern solution:** Combine local replacement + working set framework.
- Early detection critical — thrashing snowballs quickly.
