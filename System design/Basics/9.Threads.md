# Process, Program, and Thread in Operating Systems

**Reference:** [TakeUForward - Difference Between Process, Program, and Thread](https://takeuforward.org/operating-system/difference-between-process-program-and-thread-different-types)

---

## Overview

Programs, processes, and threads are fundamental concepts in operating systems, but they represent **different levels of execution**. Understanding their distinctions is crucial for system design, performance optimization, and debugging.

> **Interview one-liner:** Program = what to run; Process = actively running program; Thread = lightweight execution unit within a process.

---

## Definitions

### Program
**A program is a passive, static entity** — a set of instructions stored on disk (executables, bytecode, scripts).

- **Storage:** Disk, storage device
- **Execution:** Does not execute by itself
- **State:** Dormant until invoked
- **Example:** `C:\Program Files\Chrome\chrome.exe`, Java `.class` file

### Process
**A process is an active instance of a program** — the actual running execution of a program with allocated resources.

- **Creation:** When a program is loaded and executed
- **Execution:** Active, using CPU and memory
- **Isolation:** Separate memory space and resources
- **Lifecycle:** Created when program starts, destroyed when it ends
- **Example:** Running Google Chrome window, a Java application instance

### Thread
**A thread is the smallest unit of execution** within a process — a lightweight sub-task that shares the process's resources.

- **Belonging:** Exists within a process
- **Resource sharing:** Shares memory, file handles with other threads in same process
- **Execution:** Independently scheduled for CPU time
- **Creation:** Lower overhead than process creation
- **Example:** Multiple concurrent operations in a single browser tab

---

## Characteristics & Properties

### Program Characteristics
- **Static** — Doesn't change during execution
- **Passive** — No action by itself
- **Persistent** — Remains on disk until deleted
- **Independent** — Can exist without execution
- **Executable format** — Binary, bytecode, or script

### Process Characteristics
- **Dynamic** — Actively changing state during execution
- **Active** — Consumes CPU, memory, I/O resources
- **Transient** — Exists only during execution
- **Isolated** — Protected memory space, separate from other processes
- **Resource ownership** — Has its own:
  - Virtual address space (memory)
  - File descriptors
  - Registers and program counter
  - Stack and heap
  - Environment variables

### Thread Characteristics
- **Lightweight** — Lower creation/switching overhead than processes
- **Shared memory** — Threads in same process share:
  - Code segment
  - Data segment
  - Heap
  - File descriptors
- **Independent execution** — Each has:
  - Own program counter
  - Own stack (stack frame)
  - Own register set
- **Fast switching** — Context switch 10-100x faster than process switch
- **Concurrent** — Multiple threads can run logically in parallel

## Program vs Process vs Thread: Detailed Comparison

| Aspect | Program | Process | Thread |
|--------|---------|---------|--------|
| **Definition** | Set of instructions on disk | Active execution instance | Smallest execution unit in process |
| **Creation** | Developed by programmer | OS creates from program | OS creates within process |
| **Nature** | Static, passive | Dynamic, active | Lightweight, active |
| **Execution** | Not executed; passive entity | Executed by CPU | Executed within process context |
| **Memory** | No memory allocated | Own separate memory space | Shares process memory |
| **Isolation** | Independent (not relevant) | Isolated from other processes | Not isolated (affects siblings) |
| **Lifespan** | Exists until deleted | Lives during execution | Lives until task finishes |
| **Context Switch** | N/A | Expensive (save/restore full state) | Fast (save/restore registers, PC) |
| **Communication** | N/A | Needs IPC (sockets, pipes, messages) | Direct via shared memory |
| **Resource Overhead** | Minimal (storage only) | High (memory, OS tracking) | Low (shares most resources) |
| **Example** | `notepad.exe` on disk | Running Notepad window | Multiple simultaneously active edits |
| **Creation Time** | Zero (exists as file) | Milliseconds (OS overhead) | Microseconds (within process) |
| **Failure Impact** | None (dormant) | Process crashes, restarts needed | Thread crashes may kill entire process |

## Types

### Types of Programs
1. **System Programs** — OS utilities (defrag, backup, antivirus)
2. **Application Programs** — User-facing apps (browsers, editors, games)
3. **Utility Programs** — Helper tools (compression, file managers)

### Types of Processes
1. **Independent Processes** — Don't need other processes (standalone app)
2. **Cooperating Processes** — Communicate with other processes (parent-child, producer-consumer)

### Types of Threads

#### 1. User-Level Threads
- **Managed by:** Application (user-space library), not OS kernel
- **Context switch:** Very fast (no kernel involvement)
- **Pros:** 
  - Lightweight, fast creation/switching
  - Can implement any scheduling algorithm
  - No kernel modifications needed
- **Cons:**
  - If one thread blocks, entire process blocks (no kernel knows)
  - Can't utilize multiple CPU cores
  - Many-to-one mapping (multiple user threads → one kernel thread)
- **Examples:** Early Java threads, GNU Pth

#### 2. Kernel-Level Threads (OS Threads)
- **Managed by:** OS kernel
- **Scheduling:** OS scheduler
- **Context switch:** Slower than user-level (kernel overhead)
- **Pros:**
  - If one thread blocks, others continue (kernel reschedules)
  - Can utilize multiple CPU cores (true parallelism)
  - One-to-one mapping (one user thread → one kernel thread)
  - Better for multi-core systems
- **Cons:**
  - Higher overhead for creation/switching
  - Kernel changes needed
- **Examples:** Modern Java threads, Windows/Linux threads

#### 3. Hybrid (M:N) Threads
- **Combines** user-level + kernel-level
- **M** user threads map to **N** kernel threads
- **Pros:** Balance between lightweight and true parallelism
- **Cons:** Complex to implement
- **Examples:** Solaris threads, some green threads implementations

## Context Switching

### Process Context Switch
1. **Save state** of current process (registers, PC, SP, VM tables)
2. **Update PCB** (Process Control Block) with saved state
3. **Load new process** PCB from ready queue
4. **Restore registers, PC, memory maps** for new process
5. **Resume execution** of new process

**Cost:** 10-100 microseconds (expensive, involves kernel, cache flushes)

### Thread Context Switch (Same Process)
1. **Save** current thread's registers, PC, stack pointer
2. **Load** new thread's registers, PC, stack pointer
3. **Resume** new thread

**Cost:** 1-10 microseconds (fast, same memory space, cache largely preserved)

**Key Difference:** Process switch requires VM table swap (expensive); thread switch within same process avoids this.

## Scheduling

### Process Scheduling
- **OS scheduler** picks which process runs next
- Uses algorithms: FCFS, SJF, RR, Priority, etc.
- Preemptive or non-preemptive

### Thread Scheduling
- **For user-level threads:** Library-level scheduler (application controls)
- **For kernel-level threads:** OS kernel scheduler (standard algorithms)
- Threads within a process scheduled independently

## Process & Thread Communication

### Inter-Process Communication (IPC) — Expensive
**Processes are isolated; must use OS mechanisms:**
- Pipes and named pipes
- Sockets
- Message queues
- Shared memory (with careful synchronization)
- Remote procedure calls (RPC)
- Files

**Example:** Producer process writes to pipe; consumer process reads.

### Inter-Thread Communication — Cheap
**Threads share memory; can communicate directly:**
- Shared variables (global, static)
- Shared data structures (arrays, trees, etc.)
- Queues within shared memory
- Condition variables, semaphores

**Example:** Thread 1 writes to shared buffer; Thread 2 reads.

## When to Use Threads vs Processes?

| Scenario | Use Threads | Use Processes |
|----------|-------------|---------------|
| **Heavy data sharing** | ✓ | ✗ (expensive IPC) |
| **Need isolation/security** | ✗ (shared memory) | ✓ (separate spaces) |
| **Performance critical** | ✓ (fast context switch) | ✗ (slow switching) |
| **Bug isolation** | ✗ (crash affects all) | ✓ (crash is isolated) |
| **Parallel compute on multi-core** | ✓ (with kernel threads) | ✓ |
| **Lightweight, many concurrent tasks** | ✓ | ✗ (too heavy) |
| **Multi-machine communication** | ✗ | ✓ (IPC works across machines) |
| **Web server serving multiple clients** | ✓ Threads (thread pool) | ✗ Too many processes |

## Interview Quick-Fire Q&A

**Q: Difference between program, process, and thread?**
Program = passive code on disk; Process = active execution instance; Thread = lightweight unit within process.

**Q: Can multiple processes be created from one program?**
Yes; each run creates a separate, isolated process instance.

**Q: Why are threads better than processes?**
Threads have lower overhead, fast context switching, and direct memory sharing.

**Q: What's a user-level thread vs kernel-level thread?**
User-level: lightweight, library-managed, can't use multiple cores. Kernel-level: OS-managed, truly parallel, more overhead.

**Q: Why would you use processes over threads?**
For isolation/security; if one crashes, others survive.

**Q: Can a thread access another thread's stack?**
No; each thread has its own stack. But they share heap and global data.

**Q: Is context switching between threads cheaper than processes?**
Yes; 10-100x faster because same memory space, no VM table swap.

**Q: What happens if one user-level thread blocks in I/O?**
The entire process blocks; kernel doesn't know about it.

**Q: How do threads communicate?**
Shared variables, shared buffers, queues in shared memory.

**Q: How many threads can a process have?**
Limited by available memory (each stack ~1MB); typically 100s-1000s per process.

## Key Takeaways

- **Program** = static code; **Process** = dynamic execution; **Thread** = lightweight unit.
- **Processes isolated,** preventing cross-contamination but adding overhead.
- **Threads share memory,** enabling fast communication but requiring careful synchronization.
- **User-level threads:** lightweight but can't parallelize across cores.
- **Kernel-level threads:** true parallelism but higher overhead.
- **Context switch:** Process (10-100µs, expensive) vs Thread (1-10µs, fast).
- **Modern systems use kernel-level threads** for true multi-core parallelism.
- **Modern browsers/servers** use multi-process + multi-threaded architecture for isolation + concurrency.
