# Consistent Hashing & Sharding in Load Balancer and Database

---

## Consistent Hashing

### What is Consistent Hashing?
A hashing technique that maps both **requests/keys** and **servers** onto the same circular ring (hash space of 0 to 2³² - 1). Each request is routed to the **nearest server clockwise** on the ring.

> **Interview one-liner:** Consistent hashing = smart distribution so adding/removing a server only reshuffles a small fraction of keys, not everything.

### How It Works

```
Normal Hashing:
  server = hash(key) % n_servers
  Problem: If n changes (server added/removed), ALL keys remap → massive cache invalidation

Consistent Hashing:
  - Map servers onto ring: hash(server_id) → position on ring
  - Map request onto ring: hash(request_key) → position on ring
  - Route request to nearest server clockwise on ring

         0
    270──●──90
         |
        180

  Servers: A@45, B@135, C@225, D@315
  Request R@100 → goes to B@135 (nearest clockwise)
  Request R@200 → goes to C@225
```

### Using k Virtual Nodes (v-nodes) to Maximize Load Balancing
A single server gets only one position on the ring by default → **uneven distribution** if servers vary in capacity. To fix this:

- **Each server is hashed k times** using different hash seeds → k positions on the ring
- More virtual nodes = **smoother, more uniform distribution**
- Powerful servers get **more virtual nodes** → proportionally more load

```
Without v-nodes (k=1):
  Server A @ position 50     (handles keys 320→50)
  Server B @ position 130    (handles keys 50→130)   ← smaller arc
  Server C @ position 300    (handles keys 130→300)  ← huge arc, hotspot!

With v-nodes (k=3 per server):
  Server A @ 50, 170, 290
  Server B @ 90, 210, 330
  Server C @ 130, 250, 10
  → Each server roughly owns 1/3 of the ring, split across 3 arcs
```

### Even if 1 Server Goes Down
```
Server B (@ 90, 210, 330) crashes

Without consistent hashing: ALL keys remap to different servers
  → massive cache miss storm, thundering herd problem

With consistent hashing: Only the keys that were mapped to B's positions
  move to next clockwise server
  → ~1/n of keys affected (n = number of servers)
  → minimal disruption

Example (n=4 servers):
  Server removed → only ~25% keys shift
  Server added   → only ~25% keys shift
```

### Load Balancer Perspective

**Request routing:**
```
Client Request (user_id=12345)
       │
       ▼
 Load Balancer
       │
       ├─ hash(user_id) = 67890
       │
       ├─ Find position 67890 on ring
       │
       └─ Nearest server clockwise → Server B
              ↓
         Server B handles request
         (Same user always hits same server → session affinity)
```

**Benefits in LB:**
- **Session affinity (sticky sessions)** – Same user always routed to same server
- **Cache locality** – User's cached data lives on one server; consistent routing exploits it
- **Minimal disruption** on server changes

**Real-world use:**
- **Nginx, HAProxy** – with consistent hashing module
- **AWS ELB** – sticky sessions
- **Memcached / Redis Cluster** – key routing across cache nodes

## Sharding

### What is Sharding?
Splitting a large dataset **horizontally across multiple database servers** (shards). Each shard holds a **subset of rows**; collectively they hold all data.

> **Interview one-liner:** Sharding = horizontal partitioning across multiple servers; each server owns a slice of the data.

---

## 1. Hierarchical Sharding of DB

Instead of one level of sharding, data is split in **multiple tiers**:

```
Level 0 (Top): Route by Region
  ┌──────────────────────────────────────┐
  │          Global Router               │
  └─────┬──────────────────┬─────────────┘
        │                  │
   US Region          EU Region
        │                  │
Level 1 (Mid): Route by User ID range
  ┌─────┴─────┐        ┌───┴───────┐
  │Shard US-1 │        │Shard EU-1 │
  │users 0-5M │        │users 0-5M │
  └─────┬─────┘        └───────────┘
        │
Level 2 (Bottom): Further split by time / type
  ┌─────┴──────┐
  │ Shard A    │  ← Users 0-2.5M, last 1 year
  │ Shard B    │  ← Users 0-2.5M, older data
  └────────────┘
```

**Benefits:**
- **Geo-partitioning** – Data stays close to users (low latency, compliance)
- **Granular scaling** – Scale specific region or tier independently
- **Isolation** – EU data never crosses to US (GDPR compliance)

**YouTube Example:**
```
Global Router
  → Region Shard (US / EU / APAC)
       → User Shard (hash(user_id) % n)
            → Time Shard (recent / archive)
```

**Interview tip:** Hierarchical sharding is used by Google, Facebook to handle geographic distribution + regulatory compliance + massive scale simultaneously.

---

## 2. Use of Sharding in Load Balancer

The LB uses the shard key to **route requests to the correct shard** directly.

### Request-Level Sharding (LB as Router)
```
Client Request: GET /api/videos?user_id=12345
                      │
               Load Balancer
                      │
          shard = hash(user_id) % 4
          shard = hash(12345) % 4 = 1
                      │
              Route to Shard 1 DB
              (only reads/writes for shard 1)
```

**Why this matters:**
- LB eliminates the need for every app server to know shard topology
- App servers stay stateless (no DB routing logic)
- Changing shard count = change LB config, not app code

### Consistent Hashing + Sharding Together
```
Shard Ring:
  Shard A handles key range 0–25%
  Shard B handles key range 25–50%
  Shard C handles key range 50–75%
  Shard D handles key range 75–100%

New shard E added:
  Without consistent hashing: All keys remap across A,B,C,D,E → massive DB rebalancing
  With consistent hashing: Only ~20% of keys migrate to E → minimal disruption
```

**Real-world use:**
- **Cassandra**: Uses consistent hashing to route requests + replication
- **DynamoDB**: Partitions keys via consistent hashing, LB routes to partition
- **Redis Cluster**: 16,384 hash slots distributed across nodes

## 3. Indexing in Sharding

Indexing gets complex when data is split across shards.

### Local Index (Per-Shard Index)
Each shard has its own independent index for its own data.

```
Shard 1 (users 0–5M):
  Index: email → row_pointer  (only for users 0–5M)

Shard 2 (users 5M–10M):
  Index: email → row_pointer  (only for users 5M–10M)

Query: Find user by email (unknown which shard)
  → Must query ALL shards (scatter-gather)
  → Each shard searches its local index in parallel
  → Results merged → answer returned
```

**Pros:** Simple, independent per shard  
**Cons:** Scatter-gather for non-shard-key queries is expensive

### Global Index (Cross-Shard Index)
A separate index server maps values to shard + row location.

```
Global Index Server:
  email                     → shard_id + row_pointer
  ──────────────────────────────────────────────────
  alice@youtube.com         → Shard 1, row 234
  bob@youtube.com           → Shard 3, row 891
  charlie@youtube.com       → Shard 2, row 512

Query: Find user alice@youtube.com
  1. Query Global Index → returns Shard 1, row 234
  2. Directly query Shard 1, row 234
  3. Return result (no scatter-gather!)
```

**Pros:** Fast single-shard lookups even on non-key columns  
**Cons:** Global index is a **single point of failure + hotspot**; requires replication

### Shard Key Index Strategy
**Always include the shard key** in every index to avoid scatter-gather:

```sql
-- BAD: Index on email alone (shard key is user_id)
CREATE INDEX idx_email ON users(email);
-- Query by email → must hit all shards

-- GOOD: Composite index (shard_key + search_key)
CREATE INDEX idx_shard_email ON users(user_id, email);
-- Keeps queries within correct shard
```

### YouTube Example: Video Search Across Shards
```
Videos sharded by: creator_id

Query: Search "machine learning" videos → NO shard key!
  → Scatter-gather: send to all shards, each runs full-text search
  → Expensive but necessary for search

Query: Get videos by creator_id=12345 → HAS shard key!
  → hash(12345) → Shard 2
  → Only query Shard 2 (fast, single shard)

Solution for search without shard key:
  → Dedicated Elasticsearch cluster (separate from sharded DB)
  → Elasticsearch has its own distributed inverted index
  → Handles scatter-gather efficiently
```

## Interview Quick-Fire Q&A

**Q: What is consistent hashing and why is it better than normal hashing?**
Normal hashing (`key % n`) remaps all keys when n changes. Consistent hashing maps keys and servers to a ring; adding/removing a server only remaps ~1/n keys.

**Q: What are virtual nodes (v-nodes)?**
Each server is assigned k positions on the hash ring instead of 1. This smooths out distribution and lets powerful servers hold more v-nodes for proportionally more load.

**Q: What happens when a server is added/removed with consistent hashing?**
Only ~1/n of keys (those mapped to that server's arcs) are redistributed. All other keys stay unaffected.

**Q: How does consistent hashing help the Load Balancer?**
Provides session affinity (same user → same server), better cache locality, and minimal disruption when servers scale up or down.

**Q: What is hierarchical sharding?**
Multi-level sharding (e.g., first by region, then by user ID, then by time). Enables geo-compliance, independent tier scaling, and data isolation.

**Q: How does the LB use sharding?**
LB computes shard = hash(shard_key) and routes requests directly to the correct DB shard, keeping app servers stateless.

**Q: Local index vs global index in sharding?**
Local: each shard indexes its own data; non-shard-key queries scatter-gather. Global: separate index maps any value to the correct shard; fast lookups but single point of failure.

**Q: What query patterns require scatter-gather?**
Queries on non-shard-key columns (e.g., full-text search when sharded by user_id). Mitigated by maintaining a separate search index (Elasticsearch).

**Q: Why must the shard key be in every index?**
To ensure queries hit only the relevant shard; missing the shard key forces scatter-gather across all shards.

**Q: Consistent hashing in Cassandra?**
Cassandra places each node at multiple ring positions (v-nodes). Data is routed to the closest node clockwise; replication factor copies data to the next N nodes.

## Key Takeaways

- **Consistent hashing** places servers + keys on a ring; only ~1/n keys move when topology changes.
- **Virtual nodes (k hash functions)** ensure even distribution and proportional load per server.
- **Hierarchical sharding** splits data in tiers (region → user range → time) for geo-compliance and independent scaling.
- **LB uses shard key** to route requests directly to the correct shard — keeps app servers stateless.
- **Local index**: simple, scatter-gather for non-shard-key queries.
- **Global index**: fast lookups but needs careful replication to avoid bottleneck.
- **Always include the shard key in indexes** to prevent full scatter-gather.
- Use **Elasticsearch / dedicated search clusters** for full-text search across shards.
