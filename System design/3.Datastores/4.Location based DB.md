# Location-Based Databases

## Overview

Location-based databases store and query geographical coordinates (latitude, longitude) efficiently. Common use cases include:
- Finding restaurants near user location
- Tracking delivery vehicles
- Real-time ride-sharing (Uber/Lyft)
- Geofencing and location alerts
- Map visualization with clustering

**Challenge**: Efficiently answer queries like "Find all restaurants within 5km of (40.7128°N, 74.0060°W)"

## Naive 2D Representation Problem

### Simple Grid Approach

```
Divide map into grid cells:

        Longitude (X)
    70W      75W      80W
   ┌────┬────┬────┐
40N│ A  │ B  │ C  │  Latitude (Y)
   ├────┼────┼────┤
35N│ D  │ E  │ F  │
   ├────┼────┼────┤
30N│ G  │ H  │ I  │
   └────┴────┴────┘

Database stores:
- Restaurant 1: (35.5N, 75.2W) in cell E
- Restaurant 2: (35.1N, 74.9W) in cell D
- Restaurant 3: (40.2N, 75.5W) in cell B
- ...

Query: "Find restaurants near (35.5N, 75.5W) within 5 units"

Process:
1. Identify cell containing query point: E
2. Check neighboring cells around E: B, D, E, F, H, I
3. For each cell, retrieve all points
4. Filter by distance formula: sqrt((lat-lat_q)² + (lon-lon_q)²)

Problems with this approach:
```

### Drawbacks of Naive 2D Grid

#### 1. **Imbalanced Distribution**
```
Real world distribution:

Dense area (Manhattan):
┌────┬────┬────┐
│1000│2000│ 800│ Points per cell
│ pt │ pt │ pt │
└────┴────┴────┘

Sparse area (Desert):
┌────┬────┬────┐
│ 2  │ 0  │ 1  │ Points per cell
│ pt │ pt │ pt │
└────┴────┴────┘

Consequence:
- Manhattan cell needs 1000-object search
- Desert cell needs 1-object search
- Unbalanced performance (no better than sequential scan in dense areas)
```

#### 2. **Linear Search Within Cells**
```
Cell contains 1000 points:
Must compare query distance with all 1000 points
Time: O(1000) for range check

Grid doesn't help once inside cell - falls back to O(n)
```

#### 3. **Range Query Inefficiency**
```
Query: "Find restaurants in box [35-36N, 74-75W]"

Box spans multiple cells:
┌────┬────┬────┐
│    │ ✓  │    │
├────┼────┼────┤
│ ✓  │ ✓  │ ✓  │ ← Must check 6 cells
├────┼────┼────┤
│    │ ✓  │    │
└────┴────┴────┘

Algorithm:
1. For each cell in range: O(cells)
2. Scan all points in each cell: O(points per cell)
3. Test each against box: O(1)
Total: O(cells * points_per_cell)

No indexing benefit over linear scan!
```

#### 4. **Boundary Crossing Issues**
```
Query point near cell boundary:
Might need to check same distance in different cell

Point at (35.99N, 74.99W, query radius 0.5 units)
Relevant points in cells:
  ├─ Current cell E
  ├─ Neighboring cells B, D, F, H
  ├─ Diagonal cells A, C, G, I (even diagonals!)
  └─ Maybe cells beyond

Must check many cells, not just current cell
Leads to redundant calculations
```

## Quad Trees for Spatial Indexing

### What is a Quad Tree?

A **Quad Tree** is a tree data structure that recursively divides 2D space into 4 quadrants (hence "quad"). Each node either:
- Contains up to M points (leaf node)
- Has 4 children (internal node divisions)

### Quad Tree Structure

```
Entire Map (Root)
Points: 8 total (exceeds threshold M=4)
        ↓
    Split into 4 quadrants:

    ┌─────────┬─────────┐
    │  NW     │   NE    │ Up (North)
    │  (2pts) │  (4pts) │
    ├─────────┼─────────┤
    │  SW     │   SE    │ Down (South)
    │  (1pt)  │  (1pt)  │
    └─────────┴─────────┘
    
    ←(West) East(Right)→

Internal structure:
    Root
    ├─ NW: Leaf (can hold 4 points)
    ├─ NE: Internal node (3 points, threshold exceeded)
    │  ├─ NE.NW: Leaf
    │  ├─ NE.NE: Leaf
    │  ├─ NE.SW: Leaf
    │  └─ NE.SE: Leaf
    ├─ SW: Leaf
    └─ SE: Leaf
```

### Quad Tree Search Algorithm

```
Search for point (35.5N, 74.5W) within 10km

1. Start at root
   "Is (35.5, 74.5) in root's region?" YES
   → Continue

2. Determine which quadrant contains (35.5, 74.5)
   "In NW? SE? etc?"
   → Quadrant: SW
   → Navigate to SW node

3. Is SW a leaf?
   YES → Scan all points in SW, compute distances
        Return points within 10km
   
   NO → Repeat for each child of SW


Result: Never explore NE quadrant (wrong direction)
        Only traverse relevant branch
        Time: O(log n) instead of O(n)
```

### Building a Quad Tree

```
Insert points into Quad Tree:

Initial:
Root (empty)
Points: 0

Insert (30.5, 74.5):
Root → Leaf (1 point)

Insert (35.5, 75.5):
Root → Leaf (2 points)

Insert (40.5, 74.0):
Root → Leaf (3 points)

Insert (35.0, 73.0):
Root → Leaf (4 points) [At threshold M=4]

Insert (25.0, 76.0): [Exceeds threshold]
Root → Internal (must split)
Root has 4 children (NW, NE, SW, SE)
Distribute 4 existing points + new point into quadrants
Recurse if any quadrant exceeds M

Result: Balanced tree with points distributed by region
```

### Quad Tree Query Efficiency

```
Scenario: 1M geographic points stored in Quad Tree

Query: "Find all restaurants within 5km of (35.5, 74.5)"

Without Quad Tree:
└─ Linear scan: Compare (35.5, 74.5) against all 1M points
   → Calculate distance for each
   → 1M distance calculations
   → Time: ~100ms

With Quad Tree (M=50, ~4 levels):
└─ Start at root
   ├─ Quadrant NW: center too far, skip ✓
   ├─ Quadrant NE: center close, traverse
   │  ├─ Sub-quadrant NE-NW: too far, skip ✓
   │  ├─ Sub-quadrant NE-NE: relevant, scan ~50 points ✓
   │  ├─ Sub-quadrant NE-SW: relevant, scan ~50 points ✓
   │  └─ Sub-quadrant NE-SE: too far, skip ✓
   ├─ Quadrant SE: center close, traverse
   │  └─ Similar pruning...
   └─ Quadrant SW: too far, skip ✓

Result: ~5000 distances calculated (5% of linear)
Time: ~5ms (20x faster!)
```

### Quad Tree Complexity

| Operation | Complexity | Notes |
|-----------|-----------|-------|
| **Insert** | O(log n) average | O(n) worst case if unbalanced |
| **Range Query** | O(k + log n) | k = results, log n = tree traversal |
| **Update** | O(log n) | Delete + Insert |
| **Delete** | O(log n) average | May require tree rebalancing |

## Range Queries with Quad Trees

### Problem Definition

**Range Query**: Find all points within:
- Rectangular box: [lat_min, lat_max] × [lon_min, lon_max]
- Circular region: center (lat, lon) with radius r

### Rectangular Range Query

```
Query: Find restaurants in box [35-36N, 74-75W]

      35.5N
        ↑
   ┌─────────┐
74W│   BOX   │75W
   └─────────┘
        ↓
      35N

Algorithm:
1. Start at root Quad Tree node
2. Check if node's region overlaps with query box
   ├─ No overlap: Skip entire subtree
   ├─ Complete overlap: Include all points in subtree
   └─ Partial overlap: Recurse into children

3. For leaf nodes in resulting set:
   └─ Additional filtering if boundary cases

Result:
Quadrants completely outside box → Pruned
Quadrants completely inside box → All points included
Quadrants overlapping box → Recursive check

Time: O(k + log n) where k = result count
```

### Circular Range Query

```
Query: Restaurants within 5km of (35.5N, 74.5W)

         Circle
        ╱  5km  ╲
       ╱         ╲
      │ (35.5,   │
      │  74.5)   │
       ╲         ╱
        ╲       ╱

Algorithm:
1. For each Quad Tree node:
   ├─ Check if circle overlaps with node's bounding box
   │  (can use min distance from circle center to box edges)
   ├─ No overlap: Skip subtree
   ├─ Complete containment: Include all points
   └─ Partial overlap: Recurse

2. For candidate points:
   └─ Calculate exact distance, keep if < 5km

Optimization:
Bounding box check prevents expensive distance calculations
~95% of points eliminated at bounding box stage
```

### Range Query Example

```
Finding Uber drivers near pickup location (latitude 40.7N, -74W)

Query: "Find drivers within 2km"

Quad Tree:
         Root (North America)
        ├─ NW (Canada)      → No drivers
        ├─ NE (Atlantic)     → No drivers
        ├─ SW (West)         → Skip
        └─ SE (East)
           ├─ NW (Mid-Atlantic) → Recurse
           "Does circle overlap?" YES
           └─ Contains: quad_tree_new_york
              ├─ NW (Uptown) → Recurse
              │  "Does circle overlap?" NO → Skip
              ├─ NE (Queens) → Recurse
              │  "Does circle overlap?" PARTIAL → Recurse
              │  └─ Leaves with drivers D1, D2, D3
              │     Distances: 1.5km, 0.8km, 5km
              │     Return: D1 ✓, D2 ✓, D3 ✗
              └─ More quadrants...

Result: Only visited ~10% of tree, found 2 drivers
Alternative (linear): Check all 100k drivers in NYC → O(n) time
```

## Fractal Mapping: 2D to 1D Conversion

### Problem with 2D Indexes

```
Quad Trees efficient, but still:
- Multi-level tree traversal required
- Cache misses from pointer chasing
- Complex implementation

What if we could convert 2D coordinates to 1D?
Then use standard B+ Tree index!
```

### Hilbert Curve: Space-Filling Curve

**Hilbert Curve** maps 2D space to 1D line while preserving spatial locality (nearby 2D points remain near on 1D line).

### Basic Hilbert Curve Construction

```
Iteration 0 (Order 1):
  ┌───┐
  │   │
  └───┘
  Simple line from 0 to 3

Iteration 1 (Order 2):
  ┌───────┐
  │ 3 ─ 2 │
  │ │   │ │
  │ 0 ─ 1 │
  └───────┘
  
Curve path: 0→1→2→3 (goes around like "U" shape)

Iteration 2 (Order 4):
  ┌─────────────┐
  │ 3 ─ 2 | 6 ─ 7│
  │ │   │ │ │   │ │
  │ 0 ─ 1│4─5  14 15
  │         │   │  │
  │11─10│ 8──9 13─12
  │ │   │ │     │  │
  │ 8─ 9│12─13 12─11
  └─────────────┘

Curve visited in order: 0→1→2→3→...→15
Every adjacent 1D position corresponds to nearby 2D (spatial locality!)
```

### Why Hilbert Preserves Locality

```
2D Points:
A (35.0, 74.0)  ← Close nearby
B (35.1, 74.1)  ← to each
C (35.2, 74.2)  ← other

Converted to Hilbert coordinates:
A → 42
B → 43
C → 44

1D Property: Sequential Hilbert indices correspond to sequential 2D regions!
Now can use B+ Tree: [42, 43, 44] are contiguous
Range query [40-50] in 1D captures [A, B, C] in 2D!
```

### Hilbert vs. Other Curves

```
Row-Major (Z-order, Morton code):
  ┌─────────┐
  │0 1 │ 4 5│
  │2 3 │ 6 7│
  ├─────────┤
  │8 9 │12 13
  │10 11│14 15
  └─────────┘
  
Sequence: 0→1→2→3→4→5→...
Problem: Jump from 3→4 is far in 2D space (diagonal corner)
Poor locality

Hilbert Curve:
  ┌─────────┐
  │3─2│ 6─7 │
  │0─1│4─5  │
  ├─────────┤
  │11─10│8─9│
  │ 8─9 │12─13
  └─────────┘
  
Sequence: 0→1→2→3→4→5→...→15
Each step adjacent in 2D (preserves locality!)
Better for range queries
```

## Hilbert Curve Examples

### Example 1: Mapping Coordinates to Hilbert

```
Map size: 256×256 (order 8 Hilbert curve)

Point A: (20, 50)
  Apply Hilbert mapping function
  → Hilbert index: 5427

Point B: (21, 51)
  → Hilbert index: 5428

Point C: (200, 200)
  → Hilbert index: 45632

Observation:
A and B (nearby in 2D) → Indices 5427, 5428 (nearby in 1D) ✓
A and C (far in 2D) → Indices 5427, 45632 (far in 1D) ✓

Property: Spatial locality preserved!
```

### Example 2: Range Query Using Hilbert

```
Query: "Find restaurants in area [30-40, 60-80]"

Traditional 2D:
  └─ Check all points, compute distance → O(n)

Hilbert Curve Approach:

Step 1: Convert 2D box to Hilbert coordinates
  └─ [30-40, 60-80] maps to Hilbert range
  └─ Hilbert ranges: [h_min, h_max]

Step 2: Due to space-filling property, 2D box may map to
  multiple 1D intervals in Hilbert space
  └─ Intervals: [h1_min, h1_max], [h2_min, h2_max], ...
  └─ Usually 2-4 intervals for rectangular query

Step 3: Use B+ Tree to find points in each 1D range
  └─ Range query [h1_min, h1_max] in B+ Tree → O(log n + k1)
  └─ Range query [h2_min, h2_max] in B+ Tree → O(log n + k2)
  └─ Total points: k1 + k2

Step 4: Verify results (post-filter false positives)
  └─ Some 1D range results may technically outside 2D box

Result: O((log n + k)) using B+ Tree
Compare to: O(n) with naive approach, O(log n + k) with Quad Tree
```

### Example 3: Actual Database Usage (Google S2 Geometry)

```
Google Maps / Location Services use Hilbert curves:

Step 1: Convert (lat, lon, zoom_level) → Cell ID
  └─ Uses Hilbert curve for hierarchical cells
  └─ Example: (40.7128°N, -74.0060°W) → Cell ID: 123456789

Step 2: Store in database:
  ├─ Row Key: Hilbert Cell ID (sortable)
  └─ Value: {lat, lon, place_id, name, ...}

Step 3: Query "Find restaurants in Manhattan"
  └─ Get Hilbert cell IDs for Manhattan boundary
  └─ cells_to_query = [cell1, cell2, cell3, ...]
  └─ For each cell: Point Query in B+ Tree
  └─ Collect results from all cells

Step 4: Sort results by distance
  └─ Return top 10 restaurants

Benefit:
  - Single fixed-size index key (Cell ID instead of 2 coordinates)
  - Standard B+ Tree can be used
  - All database systems have efficient range query support
  - Hierarchical cells (zoom levels) automatic with Hilbert
```

## Complete Comparison: Data Structures for Location Queries

| Data Structure | Storage | Range Query | Insert | Memory | Complexity |
|---|---|---|---|---|---|
| **Linear Scan** | None | O(n) | O(1) | O(1) | Slow, simple |
| **Grid/Hash** | Hash table | O(k×cells) | O(1) amortized | O(n) | Unbalanced |
| **Quad Tree** | Tree pointers | O(k + log n) | O(log n) | O(n) | Balanced, complex |
| **R-Tree** | Tree pointers | O(k + log n) | O(log n) | O(n) | Multi-level, optimized |
| **Hilbert + B+ Tree** | Single index | O(k + log n) | O(log n) | O(n) | Simple, efficient |

## Performance Summary

```
Database with 1M locations, query "find nearby"

Without spatial index:
  Linear scan: 1M distance calculations
  Time: ~100ms
  
With Quad Tree:
  Tree traversal + pruning: ~10k calculations
  Time: ~5ms (20x faster)
  
With Hilbert + B+ Tree:
  1D range query + verification: ~5k calculations
  Time: ~3ms (30x faster)
  Simple to implement with standard B+ Tree!
```

## Key Takeaways

1. **Problem**: 2D spatial queries need efficient filtering
2. **Solution**: Quad Trees naturally partition 2D space
3. **Optimization**: Hilbert curves convert 2D to 1D, enabling standard indexes
4. **Trade-off**: More complex implementation vs. query performance
5. **Practice**: Google Maps, Uber, Lyft use variations of these techniques
