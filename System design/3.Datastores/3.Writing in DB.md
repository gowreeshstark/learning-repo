# Database Write Optimization

## Request Condensing

### The Problem: Write Amplification

Every write hitting disk individually creates performance bottleneck:

```
Individual Writes:
Write A → disk access (seek, write, fsync) → 10ms
Write B → disk access (seek, write, fsync) → 10ms  
Write C → disk access (seek, write, fsync) → 10ms
Write D → disk access (seek, write, fsync) → 10ms
────────────────────────────────────────────────────
Total for 4 writes: 40ms

Bottleneck:
- Each write = random disk I/O (~10ms latency)
- Throughput limited: 100 writes/second max
- CPU idle waiting for I/O
```

### Solution: Request Condensing (Batching)

```
Batch Writes:
Accumulate Request A, B, C, D in memory buffer
    ↓
Check buffer size or time elapsed
    ↓
Write entire batch to disk → 1 disk access (~10ms)
    ↓
ACK all 4 requests

Total for 4 writes: 10ms (4x improvement!)
Throughput: 400 writes/second
CPU utilization: Better (batch processing)
```

### Implementation Strategy

```
Write Path:

Client Request → ┌─────────────────────────────┐
Client Request → │   In-Memory Buffer Queue     │
Client Request → │   (LinkedList or deque)      │
Client Request → │   [Write1, Write2, ...]      │
                 └──────────────┬────────────────┘
                                ↓
                  ┌──────────────────────────┐
                  │ TRIGGER CONDITION        │
                  ├──────────────────────────┤
                  │ • Buffer size > N bytes   │
                  │ • Time elapsed > T ms     │
                  │ • Manual flush request    │
                  └──────────────┬────────────┘
                                ↓
                  ┌──────────────────────────┐
                  │ Serialize batch to disk   │
                  │ Format: Binary log        │
                  └──────────────┬────────────┘
                                ↓
                  ┌──────────────────────────┐
                  │ fsync to ensure durability│
                  └──────────────┬────────────┘
                                ↓
                  ACK to all requests in batch
```

### Tuning Parameters

```
Trade-off: Latency vs. Throughput

Low latency config (High-frequency trading):
  - Buffer size: 1 KB
  - Flush interval: 1 ms
  - Batch size: 1-2 writes
  - Latency: 1-2ms, Throughput: ~1000/sec

High throughput config (Analytics):
  - Buffer size: 1 MB
  - Flush interval: 100 ms
  - Batch size: 1000+ writes
  - Latency: 50-100ms, Throughput: 100k+/sec
```

### Benefits
1. **Reduced I/O Operations**: N writes → 1 I/O
2. **Increased Throughput**: 10-100x improvement
3. **Better Disk Utilization**: Sequential access patterns
4. **CPU Efficiency**: Batch processing more efficient than context switching

## Write-Ahead Logging (WAL) with Linked List

### Core Concept

**Write-Ahead Logging**: Before applying write to data structure, append to sequential log. If crash occurs, replay log to recover.

### Why Linked List for WAL?

```
Memory Structure for WAL:

Linked List (best for WAL):
┌──────┐    ┌──────┐    ┌──────┐    
│Write │───→│Write │───→│Write │───→ NULL
│  A   │    │  B   │    │  C   │
└──────┘    └──────┘    └──────┘
  ↓          ↓          ↓
[Get latest] [O(1)]     [Append O(1)]

Benefits:
- O(1) append (add to tail)
- O(1) traversal from latest (for recovery)
- No reallocation (like vector)
- Cache friendly for sequential access
```

### WAL Workflow

```
Step 1: Client sends write "UPDATE user SET age = 30"
          ↓
Step 2: WAL Entry created: {id: 1, cmd: UPDATE, data: {...}}
          ↓
Step 3: Append to Linked List (in-memory)
        ┌─────────┐
        │ Entry 1 │ ← Latest
        └─────────┘
          ↓
Step 4: Flush list to disk (sequential write)
        Disk Log: [Entry1 binary data]
          ↓
Step 5: Apply to in-memory data structure
        MemTable: {user: {age: 30}}
          ↓
Step 6: ACK to client "Write succeeded"

If crash happens:
  → Read WAL from disk
  → Replay all entries to recover in-memory state
  → Zero data loss (because log was durable first)
```

### Memory vs. Disk Layout

```
Memory (LinkedList):
┌─────────────────────────┐
│ Node1 → Node2 → Node3   │ O(1) append
│ (pointers)              │ Easy traversal
└─────────────────────────┘

Disk (Sequential):
┌──────────────────────────────────────┐
│ [Entry1 binary][Entry2 binary]...    │ Sequential I/O
│                                      │ Fast sequential read
└──────────────────────────────────────┘

Conversion on flush:
LinkedList → Serialize to bytes → Write sequentially to disk
```

### Recovery Process

```
System crashes during:
  Entry 1: Committed ✓
  Entry 2: Committed ✓
  Entry 3: Half-written ✗
  Entry 4: Not written ✗

On restart:

1. Read WAL from disk
   └─ Entries 1, 2 complete, 3/4 incomplete

2. For each complete entry:
   └─ Replay to in-memory state
   
3. Ignore incomplete entries
   └─ They were never ACKed to client
   └─ Client will retry if needed

Result: Exact state before crash, no data loss!
```

## B+ Tree vs Linked List

### Structural Differences

```
Linked List:
┌────┐   ┌────┐   ┌────┐   ┌────┐
│ 5  │──→│ 10 │──→│ 15 │──→│ 20 │ NULL
└────┘   └────┘   └────┘   └────┘

B+ Tree (Order 3):
          ┌──────────────┐
          │   10  │  20  │
          └────┬──┬────┬─┘
               │  │    │
       ┌───────┘  │    └────────┐
       ↓          ↓             ↓
    ┌─────┐  ┌─────────┐  ┌──────────┐
    │5  8 │  │12 15 18 │  │25 30 35  │
    └─────┘  └─────────┘  └──────────┘
```

### Comparison Table

| Operation | Linked List | B+ Tree |
|-----------|------------|---------|
| **Search** | O(n) | O(log n) |
| **Range Query** | O(n) - must traverse | O(log n + k) - use leaf ptrs |
| **Insert** | O(1) to known position | O(log n) |
| **Delete** | O(n) search + O(1) delete | O(log n) |
| **Disk Seeks** | Many (scattered) | Few (fan-out reduces height) |
| **Cache Locality** | Poor (random ptrs) | Good (sequential in node) |
| **Memory Usage** | Minimal | More (internal nodes) |
| **Sorted Scan** | O(n) efficient | O(n) efficient via leaves |

### When to Use Each

**Linked List Best For:**
- Write-Ahead Logs: Only append, no search needed
- Transaction queues: Sequential processing
- Real-time streams: Fast append
- FIFO operations: Queue/stack data structure

**B+ Tree Best For:**
- Primary indexes: Range queries common
- Database tables: Efficient access across sizes
- Secondary indexes: Need to find values quickly
- Sorted data: Natural ordering maintained

### Disk Access Example

```
Linked List search for "100":
┌────┐   ┌────┐   ┌────────┐   ┌────┐
│ 5  │──→│ 10 │──→│ key-100│──→│200 │
└────┘   └────┘   └────────┘   └────┘
  Disk1    Disk1    Disk2→      Disk3→
↓         ↓         ↓           ↓
Seek(1)   Seek(1)   Seek(2)     Seek(3)
Total: 4 seeks for 1 value!

B+ Tree search for "100":
Root (mem) → Check: 100 < 500 → go left
Disk1 → [100 fits in [50-150]] → go to leaf
Disk2 → [... 100 ...] → Found!
Total: 2 seeks for 1 value!
```

## Sorted String Table (SST)

### Overview

A **Sorted String Table** is an immutable file containing key-value pairs sorted by key. SSTs are the foundation of LSM (Log-Structured Merge) tree databases like RocksDB, LevelDB, Cassandra.

### SST Structure

```
SST File Format:

┌──────────────────────────────────────────────────┐
│ Block 1: Data Block                              │
│ ┌──────────────────────────────────────────────┐ │
│ │ [key1, value1]                               │ │
│ │ [key5, value5]                               │ │
│ │ [key10, value10]                             │ │
│ │ [key20, value20]                             │ │
│ └──────────────────────────────────────────────┘ │
│                                                  │
│ Block 2: Index Block (sparse)                   │
│ ┌──────────────────────────────────────────────┐ │
│ │ Offset: 0, Key: key1  ← Block 1 start       │ │
│ │ Offset: 500, Key: key15 ← Block 1 middle   │ │
│ │ Offset: 1000, Key: key25 ← Block 2 start   │ │
│ └──────────────────────────────────────────────┘ │
│                                                  │
│ Block 3: Filter Block (Bloom Filter)            │
│ ┌──────────────────────────────────────────────┐ │
│ │ Bloom filter of all keys                     │ │
│ └──────────────────────────────────────────────┘ │
│                                                  │
│ Block 4: Footer                                 │
│ ┌──────────────────────────────────────────────┐ │
│ │ Offset of Index: 1024                        │ │
│ │ Offset of Filter: 2048                       │ │
│ │ File checksum: 0xABC123                      │ │
│ └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

### LSM Tree Write Path

```
Write Flow:

Client: "Put(key=user:100, value={name: Alice})"
  ↓
In-Memory MemTable (typically RB-tree, sorted)
  ├─ user:100 → {name: Alice}
  ├─ user:101 → {name: Bob}
  └─ ... (50MB limit)
  ↓
MemTable full → Flush to disk
  ↓
Create SST File (Level 0)
  ├─ Sorted by key ✓
  ├─ Immutable ✓
  └─ Has Bloom filter for range queries
  ↓
Level 0 SST Files: [SST_1, SST_2, SST_3]
  ↓
Compaction triggered (background)
  ├─ Read SST_1, SST_2, SST_3 (may overlap)
  ├─ Merge sort by key
  └─> Combine into Level 1 SST (no overlap)
  ↓
Level 1 SST: [SST_L1_A, SST_L1_B, ...]
  ↓
Further compaction as needed
```

### Read Path with SSTs

```
Query: "Get(key=user:100)"
  ↓
Check MemTable: Is key present?
  └─ Hit: Return value ✓
  └─ Miss: Continue
  ↓
Check Level 0 SSTs:
  ├─ Check Bloom filter: Maybe in this SST?
  │   ├─ YES → Binary search within SST
  │   └─ NO → Skip SST
  ↓
Check Level 1 SSTs:
  ├─ No overlap, use index ✓
  ├─ Check Bloom filter
  │   ├─ YES → Binary search within SST
  │   └─ NO → Skip SST
  ↓
Check Level 2, 3, ... as needed
  ↓
Key not found: Return null
```

### Why SST is Optimal

1. **Sequential Writes**: Data written sequentially (fast disk access)
2. **Sorted Data**: Binary search within file, range queries efficient
3. **Immutable**: No locks needed, consistent snapshots easy
4. **Compressible**: Similar data near each other, better compression
5. **Deletable**: Entire file deleted when compacted away

## Compaction and Merging

### Problem: Too Many SST Files

```
After many writes, Level 0 might have:
SST_0: keys [1-50]
SST_1: keys [30-80]    ← Overlap!
SST_2: keys [40-100]   ← Overlap!
SST_3: keys [60-120]   ← Overlap!

Reading key=75:
Must check: SST_0 (no), SST_1 (maybe), SST_2 (maybe), SST_3 (maybe)
Inefficient: May check multiple files with Bloom filter misses
```

### Solution: Compaction

**Compaction** is background process merging overlapping SST files into larger, non-overlapping files.

```
Before Compaction:
Level 0: [SST_0: 1-50][SST_1: 30-80][SST_2: 40-100][SST_3: 60-120]

Process:
1. Read all Level 0 files in order
2. Merge-sort by key (combine overlaps)
3. Write to Level 1 files (non-overlapping)
4. Delete old Level 0 files

After Compaction:
Level 0: [Empty]
Level 1: [SST_L1_A: 1-30][SST_L1_B: 31-80][SST_L1_C: 81-120]
         (No overlap! Binary search works)

Reading key=75:
Direct to SST_L1_B based on range → 1 file instead of 4!
```

### Compaction Levels Strategy

```
LSM Tree Level Structure:

Level 0: Up to M files (can overlap)
   └─ When Level 0 full, compact to Level 1
      
Level 1: Up to M files (NO overlap)
   │  Total size: M × file_size
   ├─ When Level 1 full, compact to Level 2
      
Level 2: Up to M files (NO overlap)
   │  Total size: M^2 × file_size
   └─ Continues as needed

Level N: Largest files, minimal compaction
   Size: M^N × file_size
```

### Compaction Cost

```
Write Amplification Example:

Level 0 SST size: 10MB
Compact to Level 1: Read 10MB + write 10MB = 20MB I/O
Compact Level 1→2: Read 100MB + write 100MB = 200MB I/O
Compact Level 2→3: Read 1000MB + write 1000MB = 2000MB I/O

Total I/O for 10MB of user data: ~2.2GB (220x write amplification)

This is why SSDs preferred for LSM trees - many rewrites!
```

### Deletion Handling

```
Scenario: User deletes user:100

Normal write would update value, but can't do that in immutable SSTs.
Solution: Write "tombstone" marker

SST files:
  user:100: value_old (v1)
  user:100: DELETED (v2) ← Tombstone
  
During compaction, when merging:
  ├─ See user:100 in two SSTs
  ├─ Latest version is DELETED
  └─ Don't include in merged output → Effectively deleted!
```

## Bloom Filters in DB Reading/Writing

### How Bloom Filters Accelerate Reads

```
Query: "Get(key=user:500)"

Level 0 SST Files (can overlap):
  SST_0: Bloom filter indicates user:500 NOT present → Skip ✓
  SST_1: Bloom filter indicates user:500 MAYBE present → Check
         Binary search: Found or not found
  SST_2: Bloom filter indicates user:500 NOT present → Skip ✓
  
Level 1 SST File (no overlap):
  Use key range directly to pick file
  
Result: Bloom filter eliminates 2/3 of unnecessary file checks!
Saves 2 random disk seeks.
```

### False Positive Impact

```
False Positive Example:

User:501 query on SST containing user:500

Bloom filter says "Maybe have user:501"
Binary search in SST: "Not found"

Cost: 1 extra disk seek (but guaranteed find by binary search)

Since Bloom filters tuned to ~1-2% false positive rate:
  99-98% of queries avoid false reads
  1-2% do extra seek but still find answer correctly
  
Trade-off: Acceptable! Saves overall disk I/O.
```

### Writing with Bloom Filters

```
Write Path:

MemTable accumulates writes:
  ├─ user:100 → Alice
  ├─ user:200 → Bob
  └─ user:300 → Charlie

When flushing to SST:
  ├─ Serialize sorted data to disk
  ├─ Create Bloom filter of all keys
  │  (Add: user:100, user:200, user:300)
  └─ Attach Bloom filter to SST file footer
  
SST File Structure:
  ├─ Data blocks (user:100→300)
  ├─ Index block (offsets)
  ├─ Bloom filter block ← Reuses keys from data!
  └─ Footer (offsets of above)

Result: At write time, Bloom filter created once
        At read time, used to avoid disk seeks
```

### Performance Numbers

```
Database Read Performance Comparison:

Without Bloom Filters:
  Read "key that doesn't exist"
  Check Level 0: 4 files → 4 disk seeks → 40ms
  Found: Not in any file
  
With Bloom Filters (1% false positive):
  Read "key that doesn't exist"
  Check Level 0: 4 Bloom checks → 0.1ms
  1% chance of false positive (1 seek instead of 4)
  Average: 0.1ms + 0.01 * 10ms = 0.2ms
  
Improvement: 200x faster for missing keys!
This is critical for databases with 99%+ negative queries.
```

### Tuning Bloom Filter Parameters

```
False Positive Rate vs. Memory:

Memory = 10 bits/element:
  False positive rate ≈ 0.01 (1%)
  Minimal memory impact

Memory = 5 bits/element:
  False positive rate ≈ 0.03 (3%)
  More disk seeks, but smaller filter

Memory = 20 bits/element:
  False positive rate ≈ 0.001 (0.1%)
  More memory, fewer disk seeks

RocksDB Default: ~10 bits/element (balance)
```

## Complete Write-Read Flow Diagram

```
WRITE PATH:
Client Request → MemTable (sorted, in-memory)
                    ↓
              [Size threshold hit]
                    ↓
           Flush to L0 SST File
           + Bloom filter
           + Index blocks
                    ↓
           Background Compaction
           Merge overlapping SSTs
           Delete old files
                    ↓
           L1, L2, L3 SST Files
           (Larger, non-overlapping)

READ PATH:
Client Request → Check MemTable
                    ↓
              [Not found, check L0]
                    ↓
           Check Bloom filter
           [Maybe] → Binary search
           [NO] → Skip file
                    ↓
              [Not found, check L1-LN]
                    ↓
           Use index for range
           Check Bloom filter
           [Maybe] → Binary search
           [NO] → Skip file
                    ↓
           Return value or NotFound
```
