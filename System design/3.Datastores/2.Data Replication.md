# Data Replication in Databases

## Fundamental Concepts

### What is Replication?
Database replication is the process of creating and maintaining multiple copies of data across different database instances (nodes) to achieve:
- **High Availability**: System continues if one node fails
- **Read Scalability**: Distribute read load across multiple replicas
- **Disaster Recovery**: Maintain geo-distributed backups
- **Lower Latency**: Position replicas closer to users

### Key Terminology
- **Master/Primary**: Authoritative node that accepts writes
- **Slave/Replica/Secondary**: Copy of data, usually read-only
- **Replication Lag**: Time delay between write on master and update on replicas
- **Consistency**: How quickly replicas reflect changes from master

## Master-Slave Architecture

### Architecture Overview

```
Single Master, Multiple Slaves:

                    Writes
                      ↓
                   MASTER (Write authority)
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
      SLAVE 1      SLAVE 2      SLAVE 3
     (Read)       (Read)        (Read)
```

### How It Works

1. **Write Phase**:
   - Client sends write request to Master
   - Master applies write to its local storage
   - Master generates binary log entry
   - Master sends log entry to all Slaves

2. **Replication Phase**:
   - Each Slave receives binary log
   - Slave applies changes locally
   - Slave sends acknowledgment back to Master

3. **Read Phase**:
   - Clients can read from any Slave
   - Reduces load on Master

### Key Characteristics
- **Single Point of Write**: All writes go through Master (simpler consistency)
- **Read Scalability**: Unlimited Slaves can serve reads
- **Failover Complexity**: Electing new Master if primary fails
- **Simple to Implement**: Straightforward topology and behavior

## Synchronous Replication

### How Synchronous Replication Works

```
Timing Flow:

Time 0: Client sends write "UPDATE balance = 500"
        ↓
Time 1: Master applies write locally
        ↓
Time 2: Master sends write to Slave 1, Slave 2, Slave 3
        ↓
Time 3: Master WAITS for acknowledgment from ALL slaves
        ↓
Time 4: Slave 1 applies → sends ACK ✓
Time 5: Slave 2 applies → sends ACK ✓
Time 6: Slave 3 applies → sends ACK ✓
        ↓
Time 7: Master sends confirmation to client
```

### Characteristics

**Consistency Guarantee:**
- ALL replicas have identical data before client receives confirmation
- Strongest consistency model (strict serializability)
- ACID properties maintained across all nodes

**Latency:**
```
Total Latency = 
  Disk Latency (Master) +
  Network Latency (to slowest Slave) +
  Disk Latency (Slave) +
  Network Latency (back to Master)

Example: 
  - Master disk: 5ms
  - Network to Tokyo: 150ms
  - Tokyo slave disk: 5ms
  - Network back: 150ms
  ────────────────────
  Total: 310ms per write
```

### Advantages
1. **Strong Consistency**: Guaranteed all replicas are in sync
2. **No Data Loss**: Confirms only when replicas safely stored data
3. **ACID Guarantees**: Transactions work across replicas
4. **Financial Systems Safe**: Banks use this for transaction accounts

### Disadvantages
1. **High Latency**: Slowest replica determines overall latency
2. **Reduced Availability**: Single slow/failed replica blocks all writes
3. **Cascading Failures**: Problem with one slave affects whole system
4. **Network Dependency**: Remote replicas increase latency significantly
5. **Throughput Bottleneck**: Can't process next write until previous confirmed

### Use Cases
- **Financial Transactions**: Money transfers, account updates
- **Inventory Management**: Stock counting systems
- **Medical Records**: Patient data updates
- **Legal/Compliance**: Audit trails where data must be instantly replicated

## Asynchronous Replication

### How Asynchronous Replication Works

```
Timing Flow:

Time 0: Client sends write "UPDATE balance = 500"
        ↓
Time 1: Master applies write locally
        ↓
Time 2: Master sends immediate ACK to client ✓
        ↓
Time 3: (Background) Master sends write to Slaves
        ↓
Time 4: (Background) Slaves apply writes whenever ready
        ↓
Time 5+: Replicas eventually have latest data eventually
```

### Characteristics

**Eventual Consistency:**
```
Master State: [v1, v2, v3] ← Latest
Slave 1 State: [v1, v2] ← Lag 1 version
Slave 2 State: [v1] ← Lag 2 versions

After some time:
Master State: [v1, v2, v3]
Slave 1 State: [v1, v2, v3] ← Caught up
Slave 2 State: [v1, v2, v3] ← Caught up
```

**Replication Lag:**
- Typical lag: 1-100ms
- Can grow if Master is overloaded
- Can be seconds/minutes if network is slow

### Advantages
1. **Low Latency**: Client receives confirmation immediately
2. **High Availability**: Slow replicas don't block writes
3. **High Throughput**: Can process next write while replicating previous
4. **Fault Tolerance**: Master failure doesn't impact recent writes (data recovery)
5. **Geo-Distributed**: Works well with internet-latency replicas

### Disadvantages
1. **Eventual Consistency**: Temporary inconsistency between master and slaves
2. **Data Loss Risk**: Master fails before replicating → data lost
3. **Stale Reads**: If client reads from slave immediately after write, might miss update
4. **Complex Logic**: Application must handle eventual consistency
5. **Replication Lag Issues**: Replica lag can cause unexpected behaviors

### Use Cases
- **Social Media Feeds**: User posts appear immediately, propagate to followers slowly
- **E-commerce Product Catalog**: Inventory changes propagate with slight delay
- **Analytics Databases**: Speed matters more than real-time accuracy
- **Content Distribution**: Blog posts, articles can have propagation delay
- **User Activity Logs**: Log writes prioritized, real-time accuracy not critical

### Replication Lag Problem Example

```
Scenario: Asynchronous replication with 5-second lag

Time 0: User logs in, reads profile (Master)
        Profile version: v1
Time 0.1: User updates profile info (Master updated to v2)
         Client gets immediate confirmation
Time 0.5: User goes to another page, calls read replica
         Slave hasn't yet received v2 update
         Reads v1 (old info) ← STALE READ

Time 5: Slave receives and applies update
        Becomes v2

This race condition very common!
Session writes to master, reads from slave.
```

## Synchronous vs Asynchronous Comparison

| Aspect | Synchronous | Asynchronous |
|--------|-------------|--------------|
| **Latency** | High (100s of ms) | Low (<10ms) |
| **Consistency** | Strong | Eventual |
| **Availability** | Lower (dependent on slowest slave) | Higher |
| **Data Loss** | None | Possible |
| **Throughput** | Lower | Higher |
| **Complexity** | Simpler | Complex (handle inconsistency) |
| **Network Requirement** | Fast, reliable | Less demanding |
| **Use Case** | Financial systems | Social media, analytics |

## Peer-to-Peer Data Transfer

### Traditional Star Topology
```
All slaves replicate from master:

                    MASTER
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
      SLAVE-A      SLAVE-B      SLAVE-C
      
Master becomes bottleneck:
- Master must send to every slave
- Network bandwidth saturated
- Single point of failure
```

### Peer-to-Peer Topology

```
Slaves can replicate from each other:

                    MASTER
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
      SLAVE-A ←→  SLAVE-B      SLAVE-C
        ↓             ↓             ↓
        └─────────────┼─────────────┘
                  (cross replication)
```

### How P2P Replication Works

1. **Master Generates Log**: Binary log with transaction ID
2. **Slaves Replicate from Master**: Multiple slaves get updates
3. **Slaves Replicate from Each Other**: Slaves exchange missing updates
4. **Conflict Resolution**: If two slaves get different updates, merge/resolve

### Benefits

1. **Reduced Master Load**
```
Master → Slave A ← → Slave B ← → Slave C
                ←────────────→

Master sends once, slaves distribute among themselves
Bandwidth reduction: From N connections to ~log(N)
```

2. **Faster Propagation**
```
Without P2P:
Master → Slave A (10ms)
Master → Slave B (10ms)
Master → Slave C (10ms)
Master → Slave D (10ms)
All to master: 40ms total

With P2P:
Master → Slave A (10ms) ↓
                     Slave A → B (5ms)
                                  B → C (5ms)
                                       C → D (5ms)
Total for 4 nodes: 25ms (vs 40ms)
```

3. **Better Fault Tolerance**
```
If Master fails temporarily:
P2P: Slaves continue replicating from each other
Star: Replication stops completely
```

### Implementation Challenges

1. **Conflict Detection**: Two slaves updating same data
2. **Ordering**: Ensure transactions applied in correct order
3. **Duplicate Detection**: Don't apply same update twice
4. **Idempotency**: Updates must be safe to apply multiple times

## Split Brain Problem

### Understanding Split Brain

**Definition**: When network partition causes multiple nodes to act as authoritative master simultaneously, leading to conflicting updates.

### Scenario Walkthrough

```
Initial State: Network Health
┌──────────────────────────────────────┐
│ MASTER (authoritative write node)    │
│ └─→ Replicas {A, B, C}               │
└──────────────────────────────────────┘

All updates flow through master → replicas are consistent


NETWORK PARTITION OCCURS!
────────────────────────────────────────────────────


Partition State: Network Split

Zone 1:                         Zone 2:
┌──────────────────┐           ┌──────────────────┐
│ MASTER           │           │ Replica-A        │
│ (isolated)       │           │ (isolated)       │
│                  │           │                  │
│ Writes: A, B, C  │    ××××   │ Clients think A  │
│ Version: v3      │ Network X │ is master now!   │
│                  │           │ Accepts: X, Y, Z │
│ Q: Who is master?│           │ Version: v3'     │
└──────────────────┘           └──────────────────┘


Result when partition heals:
MASTER data: [A, B, C, v3]
Replica-A data: [X, Y, Z, v3']
────────────────────────────
CONFLICT! Two divergent histories!
```

### Detailed Problem Scenario

```
Time 0: Network healthy
Master: balance = $100
Replicas: balance = $100

Time 1: Network partitions (Master ↔ Zone A severed)
        Zone B with Replicas still connected

Time 2: User sends UPDATE balance = $120 to Master
Master: balance = $120 (stored)
Replicas (Zone B): Still $100 (no replication received)

Time 3: Different client updates through Zone B
Chooses Replica-A as new master (since Master unreachable)
Replica-A: balance = $80
Replicas (Zone C): balance = $80

Time 4: Network heals!

Now we have:
Master: $120
Zone A replicas: $80

Which is correct? BOTH updates assumed committed!
This is data inconsistency - bank account tally mismatch!
```

### Consequences of Split Brain

1. **Data Inconsistency**: Multiple conflicting versions
2. **Lost Transactions**: Some updates lost in merge
3. **Duplicate Transactions**: Some updates applied twice
4. **Business Logic Violations**: Account balances don't match
5. **Cascading Failures**: Dependent systems get bad data

### Solutions to Split Brain

#### Solution 1: Quorum-Based Consensus

```
Require majority vote to become master:

Cluster: 5 nodes

Before partition:
All 5 nodes: Zone has 5/5 → Majority ✓
Master writes proceed safely

After partition:
Zone 1: 3 nodes (3/5 = 60%) → MAJORITY ✓
        Can write, act as master
        
Zone 2: 2 nodes (2/5 = 40%) → NOT MAJORITY ✗
        Cannot write, reject requests
        
When healed:
Zone 2 rejoins: 3/5 still authoritative
Zone 2: Caught up from Zone 1
Result: Single authority maintained!
```

#### Solution 2: Heartbeat & Master Lease

```
Master sends periodic heartbeat: "I'm alive"

┌─────────────────────────────┬─────────────────────────────┐
│ Before Partition            │ After Partition             │
├─────────────────────────────┼─────────────────────────────┤
│ Master: heartbeat ✓         │ Master isolated             │
│ Lease: Valid (T+10s)        │ Lease: Expires in 5s        │
│                             │                             │
│ Replicas: heartbeat ✓       │ Replicas: No heartbeat ✗    │
│ Authority: None yet         │ Wait for lease expire       │
│                             │                             │
│                             │ After 5s:                   │
│                             │ Replicas: Lease expired ✓   │
│                             │ Elect new master ✓          │
│                             │ New writes allowed          │
│                             │                             │
│                             │ Original Master (old lease) │
│                             │ Cannot write (lease expired) │
```

**Benefits:**
- Original master automatically loses authority
- Prevents old master from accepting writes durning partition
- Clear time boundary

#### Solution 3: Automatic Failover with Fencing

```
Mechanism: Use external lock service (ZooKeeper, etc.)

Before partition:
┌─────────────────────────────────────────────┐
│ Master holds write lock in ZKeeperr         │
│ Lock TTL: 10s                               │
└─────────────────────────────────────────────┘

Network partitions Master ← → Replicas

After partition:
Master tries to write: ZK unreachable, can't renew lock
  ↓
Master: Cannot renew lock, STOP ACCEPTING WRITES

Replicas (connected to ZK):
  ↓
ZKeeper: Old master lock expires after 10s
  ↓
Replicas: Acquire lock as new master
  ↓
Replicas: NOW can accept writes

Result: Only one master writes at any time!
```

#### Solution 4: Last-Write-Wins (LWW) Conflict Resolution

```
During partition conflicts occur:

Version A (Master): {balance: 100, ts: 1000, id: master-001}
Version B (Replica): {balance: 80, ts: 1001, id: replica-002}

Merge Strategy:
Compare timestamps: ts(B) > ts(A)
→ Version B wins (300 is newer)

Result: Accepts higher timestamp, loses lower timestamp update
Trade-off: Data consistency over total update preservation
Used in: Dynamo DB, Cassandra, Riak
```

### Best Practices for Preventing Split Brain

1. **Use Quorum**: Require majority consensus for authority
2. **Set Lease Duration**: Choose based on network latency
3. **Monitor Network**: Alert on partition detection
4. **Graceful Degradation**: Reduce functionality vs. serving bad data
5. **Application Layer**: Handle inconsistency with idempotent operations
6. **Testing**: Regular chaos engineering to simulate partitions
