# Event-Driven Systems

## What is an event-driven system?
An event-driven system is an architecture where services communicate by producing and reacting to **events** (facts like `UserRegistered`, `PaymentSucceeded`, `OrderShipped`) instead of tight synchronous API chains.

An **event** usually means “something happened in the past” and should be immutable.

---

## Core building blocks

1. **Event Producer**
	- Emits domain events when state changes.

2. **Event Broker**
	- Kafka, RabbitMQ, Pulsar, SNS/SQS, etc.

3. **Event Consumer**
	- Subscribes and reacts (update DB, send email, trigger workflow).

4. **Schema / Contract**
	- Event format versioning (JSON schema, Avro, Protobuf).

5. **Dead Letter Queue**
	- Stores events that repeatedly fail processing.

---

## Request/flow style comparison

### Synchronous chain
`API -> Service A -> Service B -> Service C`

Pros: simple to reason about immediate result.
Cons: cascading latency/failures.

### Event-driven flow
`API -> Event Broker -> Consumers A/B/C independently`

Pros: decoupling and resilience.
Cons: eventual consistency and harder debugging.

---

## Event-driven patterns asked in interviews

### 1) Event Notification
Producer sends minimal event (“OrderPlaced with ID”). Consumers fetch details if needed.

### 2) Event-Carried State Transfer
Event contains enough data to avoid extra fetch.

### 3) Event Sourcing
Store state changes as append-only event log; current state is derived by replay.

### 4) CQRS (Command Query Responsibility Segregation)
Separate write model and read model; events synchronize read projections.

### 5) Saga Pattern
Distributed transaction via sequence of local transactions + compensating actions.

---

## Advantages

1. **Loose coupling**
	- Services evolve independently.

2. **Scalability**
	- Scale consumers independently by partition/group.

3. **Resilience**
	- Broker buffers spikes; temporary consumer outages don’t instantly fail producers.

4. **Extensibility**
	- New consumers can be added without changing producer.

5. **Auditability**
	- Event log provides historical trail and replay capability.

---

## Disadvantages

1. **Eventual consistency**
	- Read models can lag after writes.

2. **Operational complexity**
	- Broker operations, partitioning, retention, DLQ, schema registry.

3. **Idempotency requirements**
	- Duplicates are common with at-least-once delivery.

4. **Ordering challenges**
	- Global ordering is difficult; usually only per key/partition ordering.

5. **Difficult debugging**
	- Tracing business flow across async boundaries requires strong observability.

---

## Real-time examples

### 1) E-commerce order lifecycle
- `OrderPlaced` event
- Payment, inventory, shipping, notification consume independently
- Each service updates its own datastore

### 2) Ride-hailing platform
- Driver location updates as stream events
- Matching service consumes for nearest-driver assignment
- Pricing, ETA, analytics consume same stream

### 3) Video streaming platform
- `VideoUploaded` triggers transcoding pipeline
- Thumbnail generation, moderation, metadata extraction run asynchronously

### 4) Banking side-systems (not core ledger)
- Core ledger transaction remains strongly consistent
- Events feed fraud detection, notifications, reporting, AML workflows

---

## Reliability practices (interview must-mention)

1. **Transactional outbox pattern**
	- Write DB change + outbox record in same transaction; relay publishes event.

2. **Idempotent consumers**
	- Dedup by event ID/business key.

3. **Retry with exponential backoff**
	- Handle transient errors safely.

4. **DLQ and replay tools**
	- Recover from poison events.

5. **Schema versioning**
	- Backward/forward compatibility for independent deployments.

6. **Observability**
	- Correlation IDs, distributed tracing, consumer lag alerts.

---

## When to use vs avoid

Use event-driven when:
- Multiple downstream reactions are needed.
- High throughput and decoupling are priorities.
- Eventual consistency is acceptable.

Avoid pure event-driven for:
- Immediate strongly consistent multi-step transactions.
- Very simple systems where async complexity is unnecessary.

---

## One-line interview summary
“Event-driven architecture improves scalability and decoupling by turning workflows into asynchronous event reactions, but it requires strong discipline around idempotency, schema evolution, and observability to handle eventual consistency safely.”
