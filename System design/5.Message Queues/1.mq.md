# Message Queues / Task Queues

## Why message queues are needed
When traffic spikes, a synchronous app can become slow or fail because every request waits for downstream work (email, payment retry, image processing, notifications, etc.).

A **message queue (MQ)** decouples producer and consumer:
- Producer accepts request quickly and pushes a message to queue.
- Consumer processes message asynchronously.
- User gets fast response for non-critical background work.

This gives:
- Better reliability (requests are buffered, not dropped immediately)
- Better scalability (scale consumers independently)
- Better fault tolerance (retry failed messages)

---

## Core concepts (interview vocabulary)

### 1) Producer
Service that creates messages and publishes to queue.

### 2) Queue / Topic
Durable storage where messages wait to be processed.

### 3) Consumer / Worker
Service that polls/subscribes and processes messages.

### 4) Acknowledgment (ACK/NACK)
- **ACK**: message processed successfully, remove from queue.
- **NACK** or timeout: message can be retried or moved to dead-letter queue.

### 5) Retry + Dead Letter Queue (DLQ)
- Retry transient failures (network timeout, service unavailable).
- Move poison messages to DLQ after max attempts.

### 6) Visibility timeout / In-flight lock
When a consumer picks a message, it becomes temporarily invisible. If consumer crashes before ACK, message becomes visible again.

### 7) Ordering
Some systems support strict ordering (single partition/queue), others offer partition-level ordering.

## Asynchronous request handling (what you wrote, expanded)

Instead of rejecting requests when app is busy:

1. API receives request.
2. API validates and quickly enqueues job.
3. API returns `202 Accepted` (or job id) to client.
4. Background workers process queue at their own rate.

This pattern smooths burst traffic and prevents cascading failures.

## Priority queues

If some tasks are urgent (OTP, fraud alert) and others are non-urgent (analytics, thumbnail generation), use **priority queues**.

Typical approach:
- High-priority queue: critical low-latency jobs.
- Medium/Low queues: batch/non-critical jobs.
- Separate consumer pools per priority to avoid starvation.

Interview caveat:
- One queue with priority can still starve low-priority jobs.
- Prefer multiple queues + quotas for predictable fairness.

## Heartbeat, health checks, and load balancing

Your note mentions notifier + heartbeat + load balancing. These are related but distinct:

- **Heartbeat/health checks**: detect if worker/server is alive.
- **Load balancer**: routes client traffic to healthy app instances.
- **Queue broker**: stores and distributes messages to consumers.
- **Scheduler/notifier**: triggers delayed or periodic tasks.

In real architectures, these may be separate components, not a single thing called MQ.

### Practical flow
- Worker sends heartbeat every N seconds.
- Orchestrator/k8s marks unhealthy workers unavailable.
- Queue redistributes pending messages to healthy workers.
- LB only affects API traffic; broker handles job distribution.

## Message queue vs task queue

### Message Queue
General event/message transport between services.
Examples: Kafka, RabbitMQ, AWS SNS+SQS.

### Task Queue
Work execution model (jobs + retries + scheduling + result tracking).
Examples: Celery (with RabbitMQ/Redis), Sidekiq.

A task queue often uses an MQ internally.

## Delivery semantics (important interview point)

- **At-most-once**: may lose messages, no duplicates.
- **At-least-once**: no loss ideally, duplicates possible.
- **Exactly-once**: very hard end-to-end; often “effectively once” using idempotency + dedup.

Best practice:
- Design consumers as **idempotent** (same message processed twice should not corrupt state).

## Real-world examples

1. **E-commerce order flow**
	- Checkout API writes order, publishes `OrderPlaced`.
	- Consumers: payment, inventory, email, analytics.

2. **Video platform**
	- Upload triggers transcoding tasks in queue.
	- Worker pools process different resolutions.

3. **Ride hailing**
	- Trip events, location updates, notifications handled asynchronously.

## Common interview trade-offs

### Advantages
- Absorbs burst traffic
- Decouples services
- Enables retries and resilience
- Independent horizontal scaling

### Disadvantages
- Eventual consistency between services
- Operational complexity (broker, partitions, DLQ)
- Duplicate/out-of-order message handling
- Harder observability/debugging

---

## Common interview pitfalls and answers

### Q: “If queue is full, what do you do?”
- Apply backpressure, reject with `429`, autoscale consumers, shard queues.

### Q: “How do you avoid duplicate processing?”
- Idempotency keys, dedup store, transactional outbox/inbox pattern.

### Q: “How do you monitor MQ health?”
- Queue depth, consumer lag, processing latency, retry count, DLQ rate.

### Q: “Can queue replace load balancer?”
- No. LB handles request routing; queue handles async work distribution.

---

## One-line interview summary
“A message queue converts synchronous pressure into asynchronous, durable work processing. It improves reliability and scalability, but requires careful handling of retries, ordering, idempotency, and observability.”
