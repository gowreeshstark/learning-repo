# Publisher–Subscriber (Pub/Sub) Model

## What is Pub/Sub?
Pub/Sub is a messaging pattern where:
- **Publishers** send messages to a topic.
- **Subscribers** receive messages from that topic.
- Publisher and subscriber are decoupled (they don’t know each other directly).

Unlike point-to-point queues (one worker processes one message), pub/sub supports **fan-out**: one event can be consumed by many services.

---

## Core architecture

1. Producer publishes event to topic.
2. Broker persists/distributes event.
3. Multiple subscriber groups consume independently.

Example:
- Event: `OrderPlaced`
- Subscribers:
  - Notification service
  - Fraud detection
  - Analytics pipeline
  - Recommendation engine

Each subscriber processes same event for different purpose.

## RabbitMQ vs Kafka (interview comparison)

### RabbitMQ (RMQ)
Best for:
- Task queues
- Complex routing (topic/direct/fanout exchanges)
- Low-latency command/event delivery
- Per-message ACK patterns

Characteristics:
- Pull/push consumer model
- Strong routing flexibility
- Generally lower throughput than Kafka for huge streams

### Kafka
Best for:
- High-throughput event streaming
- Event logs, analytics, CDC pipelines
- Replayability (retention window)
- Decoupled consumer groups at scale

Characteristics:
- Partitioned append-only log
- Consumers track offsets
- Very high throughput and durable retention

Quick rule:
- “Task dispatch and routing complexity” → RabbitMQ
- “Large-scale event streaming and replay” → Kafka

## Advantages of Pub/Sub

1. **Loose coupling**
	- Producers evolve independently from consumers.

2. **Scalability**
	- Add more consumers without changing producer.

3. **Fan-out support**
	- Same event powers multiple downstream use-cases.

4. **Extensibility**
	- New services subscribe without touching core service.

5. **Resilience**
	- Consumer failure doesn’t always block producer.

---

## Disadvantages / challenges

1. **Eventual consistency**
	- Consumers may process later; immediate global consistency is hard.

2. **Duplicate messages**
	- At-least-once delivery can cause duplicate processing.

3. **Ordering complexity**
	- Global ordering is hard across partitions.

4. **Operational overhead**
	- Need schema management, retention policies, DLQ, monitoring.

5. **Debugging difficulty**
	- Tracing event path across services is harder than synchronous flows.

---

## Real-time use cases

1. **Social media timelines (Twitter/X style)**
	- User posts tweet → event published.
	- Subscribers update followers’ feeds, notifications, trends, analytics.

2. **E-commerce**
	- `OrderPlaced` fan-out to inventory, payment, shipping, email.

3. **IoT telemetry**
	- Sensor streams published continuously; consumers do alerting, storage, dashboards.

4. **Audit and analytics pipelines**
	- Business events feed both operational services and data lake.

---

## “Twitter uses it” - why it fits

Pub/sub fits social platforms because:
- Very high write volume of events
- Many downstream consumers per event
- Eventually consistent timelines are acceptable
- Analytics and recommendation pipelines benefit from stream replay

---

## “Banking can’t use this architecture?” (correct interview framing)

Better answer: **Banking can use pub/sub, but not as sole source of truth for core ledger updates.**

Why:
- Core banking needs strict consistency, ordering, and atomicity for money movement.
- Event-driven async flows may introduce delay or duplicates.

How banks use pub/sub safely:
- Use ACID transactional DB for ledger write.
- Publish events after commit (often via transactional outbox).
- Use pub/sub for notifications, reconciliation, reporting, fraud signals.

So:
- **Core transfer settlement**: strongly consistent transaction system
- **Side effects**: pub/sub is excellent

---

## Interview-ready decision checklist

Use pub/sub when:
- Multiple services need same event
- Loose coupling and independent scaling matter
- Eventual consistency is acceptable

Avoid relying on pure pub/sub when:
- You need synchronous confirmation of distributed side effects
- Strict global ordering across all events is mandatory
- Business-critical writes require immediate atomic consistency everywhere

---

## One-line interview summary
“Pub/sub is ideal for scalable fan-out event processing and service decoupling, but critical transactional workflows still need a strongly consistent source of truth with idempotent event publication around it.”
