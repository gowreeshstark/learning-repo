# Anomaly Detection in Distributed Systems

## What is anomaly detection?
Anomaly detection is the process of identifying unusual behavior in system metrics, logs, traces, or events that may indicate failures, attacks, performance regressions, or misconfigurations.

Interview one-liner:
“Anomaly detection catches ‘unknown unknowns’ by alerting on behavior that deviates from normal baselines, not only fixed thresholds.”

---

## Why anomaly detection is critical in distributed systems

Distributed systems are complex because:
- Many services interact asynchronously.
- Failures are partial (not full outages only).
- Latency issues can cascade across dependencies.
- Traffic patterns vary by time, region, and feature release.

Static threshold alerts alone are often insufficient.

---

## Signals used for anomaly detection

### 1) Metrics
- Request rate (RPS)
- Error rate
- Latency (p50/p95/p99)
- CPU, memory, disk, network
- Queue lag / consumer lag

### 2) Logs
- Error pattern spikes
- Rare exception signatures
- Authentication failures burst

### 3) Traces
- Increased span duration
- New failing dependency edges
- Tail-latency hotspots

### 4) Business KPIs
- Checkout success drop
- Payment authorization decline
- Session abandonment spike

Best practice:
Combine technical and business signals for better incident detection.

---

## Anomaly types (interview taxonomy)

1. **Point anomaly**
	- Single abnormal datapoint (sudden CPU spike).

2. **Contextual anomaly**
	- Value normal in general, abnormal in context.
	- Example: 60% CPU is normal daytime, abnormal at midnight.

3. **Collective anomaly**
	- Sequence pattern abnormal, even if each point looks normal.
	- Example: repeated retries causing saw-tooth latency pattern.

## Detection approaches

## 1) Static thresholds
Example: alert if error rate > 5% for 5 minutes.

Pros:
- Simple and transparent

Cons:
- Noisy under traffic seasonality
- Misses subtle regressions

## 2) Dynamic baselines (seasonal)
Compare current value against historical baseline for same hour/day.

Pros:
- Better for periodic workloads

Cons:
- Needs enough historical data

## 3) Statistical methods
- Z-score
- Moving average + standard deviation bands
- EWMA/CUSUM change detection

Useful for quick anomaly scoring with low overhead.

## 4) ML-based methods
- Isolation Forest
- Autoencoders
- Forecasting models (e.g., Prophet-style trend/seasonality)

Pros:
- Can detect complex multi-signal anomalies

Cons:
- Harder explainability, tuning, drift management

Interview-safe advice:
Start with robust statistical baselines; add ML only when needed.

## Practical architecture for anomaly detection

1. Instrument services (metrics/logs/traces).
2. Collect telemetry (Prometheus/OpenTelemetry/log pipeline).
3. Build baseline models per metric/service.
4. Score anomalies in near real-time.
5. Correlate across signals (error + latency + deploy event).
6. Alert with severity and probable root cause hints.
7. Trigger automation (rollback, autoscale, circuit break) when safe.

## Root cause narrowing (important interview depth)

Anomaly detection should not stop at alerting.

Use correlation dimensions:
- Service name/version
- Region/AZ
- Dependency graph edge
- Tenant/customer segment
- Deployment change window

Example:
- p99 latency anomaly only in `ap-south-1`
- starts 3 min after `checkout-service v42` rollout
- error rate spike on DB connection timeout

Likely root cause: bad release + connection pool regression in one region.

## Real-time examples

1. **E-commerce checkout**
	- Sudden rise in payment failure rate and queue lag.
	- Detector flags anomaly before full outage.

2. **Streaming platform**
	- CDN egress normal, but playback error anomalies in one ISP.
	- Route traffic away / open incident quickly.

3. **Ride-sharing**
	- Driver match latency anomaly in one city during event surge.
	- Trigger autoscale + fallback matching strategy.

4. **Security scenario**
	- Login attempts from unusual IP ranges with impossible travel pattern.
	- Security anomaly alert + adaptive MFA.

---

## False positives vs false negatives trade-off

- **False positive**: noisy alerts, alert fatigue.
- **False negative**: real incidents missed.

Tuning levers:
- Multi-window confirmation
- Composite alerts (require 2+ signal anomalies)
- Burn-rate style SLO alerts
- Per-service sensitivity calibration

---

## Operational best practices

1. Start with high-value services first.
2. Define SLOs and error budgets.
3. Track alert precision/recall over time.
4. Add deploy markers to dashboards.
5. Use runbooks with “what to check next.”
6. Run game-days/chaos tests to validate detectors.
7. Continuously retrain/rebaseline after major seasonality changes.

## Common interview questions + concise answers

### Q1: “Why not only threshold alerts?”
Answer:
“Thresholds catch obvious failures but miss contextual shifts and create noise under seasonality. Dynamic baselines detect subtle regressions earlier.”

### Q2: “How do you reduce alert fatigue?”
Answer:
“Use severity tiers, correlation-based composite alerts, dedup/grouping, and tune based on incident postmortems.”

### Q3: “How do you connect anomaly detection to action?”
Answer:
“Attach runbooks and guarded automation like canary rollback, autoscaling, or circuit breaking, with human approval for high-risk actions.”
