# Service Discovery

## What is service discovery?
**Service discovery** is the mechanism by which services in a distributed system dynamically find and communicate with each other without hardcoded IPs/hosts.

Interview one-liner:
“Service discovery maps a stable service name to healthy, changing service instances.”

---

## Why service discovery is needed

In modern systems (Kubernetes, autoscaling VMs, containers):
- Instances are ephemeral.
- IP addresses change frequently.
- Scale up/down happens dynamically.

Hardcoding endpoints fails quickly. Service discovery solves this by maintaining an up-to-date registry of healthy instances.

---

## Core components

1. **Service Registry**
	- Stores service name -> list of instance endpoints.
	- Examples: Consul, etcd, Eureka, Kubernetes API/DNS.

2. **Service Provider**
	- Registers itself on startup.
	- Sends heartbeat/TTL renewals.
	- Deregisters on shutdown.

3. **Service Consumer**
	- Queries registry (or DNS) to resolve target service.
	- Chooses an instance using load balancing policy.

4. **Health Checking**
	- Active or passive checks to avoid routing to unhealthy instances.

---

## Service discovery patterns

## 1) Client-side discovery
Client queries registry and picks instance.

Flow:
1. Client asks registry for `payment-service`.
2. Registry returns instances `[10.0.1.5, 10.0.1.8]`.
3. Client picks one (round robin/least loaded) and calls it.

Pros:
- Flexible routing logic at client.
- No extra network hop through centralized router.

Cons:
- Client needs discovery + LB logic library.
- More complexity in each service.

Examples:
- Netflix Eureka + Ribbon (classic pattern)

## 2) Server-side discovery
Client calls stable endpoint (LB/proxy), proxy handles discovery.

Flow:
1. Client calls `payment.internal`.
2. LB/service mesh resolves healthy backend instances.
3. Request routed to selected instance.

Pros:
- Simpler clients.
- Centralized traffic policies.

Cons:
- Proxy/LB layer becomes critical dependency.
- Extra hop possible.

Examples:
- Kubernetes Service + kube-proxy
- Envoy/Istio service mesh

---

## DNS-based discovery (very common)

Service names resolve via internal DNS:
- `payment-service.default.svc.cluster.local` -> virtual IP / endpoints

Pros:
- Standard protocol, language-agnostic
- Works well with Kubernetes

Caveats:
- DNS TTL caching delays instance updates
- Need proper health checks to avoid stale routing

---

## Registration models

### Self-registration
Service registers itself with registry.

Pros:
- Simple ownership model

Cons:
- App needs registry client logic

### Third-party registration
Sidecar/agent registers service on behalf of app.

Pros:
- App remains cleaner

Cons:
- More infrastructure components

---

## Health checks and heartbeats

Discovery quality depends on healthy endpoint data.

Techniques:
- HTTP health endpoint (`/health`, `/ready`)
- TCP checks
- Heartbeat TTL (instance removed if heartbeat missing)

Interview pitfall:
If stale instances remain in registry, discovery “works” but calls fail.

---

## Load balancing with service discovery

Common strategies:
- Round robin
- Least connections
- Latency-aware routing
- Weighted routing (canary/blue-green)
- Consistent hashing (session affinity)

Service discovery tells **where** instances are.
Load balancing decides **which** instance to use.

---

## Failure scenarios and handling

1. **Registry outage**
	- Mitigation: registry cluster quorum, local cache, fallback endpoints.

2. **Network partition**
	- Mitigation: TTL expiration, retry policies, circuit breaker.

3. **Thundering reconnect on restart**
	- Mitigation: jittered exponential backoff.

4. **Stale DNS cache**
	- Mitigation: tune TTL, connection draining, readiness gates.

---

## Security in service discovery

- mTLS between services (service mesh)
- AuthN/AuthZ for registry access
- Signed service identities (SPIFFE/SPIRE-like approaches)
- Namespace/network policies to prevent unauthorized east-west traffic

---

## Real-world examples

1. **Kubernetes**
	- Pods are dynamic.
	- Services + DNS provide stable discovery.

2. **Microservices in cloud VMs**
	- Consul registry tracks instance lifecycle.
	- Sidecars route to healthy backends.

3. **Service mesh deployments**
	- Envoy sidecars discover endpoints via control plane.
	- Fine-grained routing, retries, observability.

---

## Interview trade-offs to mention

Advantages:
- Removes hardcoded endpoints
- Supports autoscaling and self-healing
- Better resilience with health-aware routing

Challenges:
- Adds control-plane complexity
- Requires robust registry HA
- Debugging can involve DNS, LB, mesh, and app layers

---

## Common interview questions + concise answers

### Q1: “Why not just use static configs?”
Answer:
“Static configs break under autoscaling and instance churn. Discovery provides dynamic endpoint resolution and health-aware routing.”

### Q2: “Client-side vs server-side discovery?”
Answer:
“Client-side gives flexibility but adds client complexity. Server-side simplifies clients and centralizes traffic policy, often preferred with service mesh or managed LB.”

### Q3: “Can service discovery be a SPOF?”
Answer:
“Yes, if the registry is single-node or unavailable without cache. Use replicated registry quorum and client-side caching/fallback.”

“Service discovery enables dynamic, health-aware communication between ephemeral services by mapping stable names to live instances, and is foundational for reliable microservice architectures.”
