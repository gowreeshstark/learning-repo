# Single Point of Failure (SPOF)

## What is a Single Point of Failure?
A **Single Point of Failure (SPOF)** is any component in a system that, if it fails, causes the whole system (or a critical part of it) to become unavailable.

Interview one-liner:
“If one component can take down the user journey by itself, that component is a SPOF.”

---

## Why SPOF matters in system design

SPOFs directly impact:
- **Availability** (uptime)
- **Reliability** (failure tolerance)
- **Recovery objectives** (RTO/RPO)
- **Business continuity** (revenue and trust)

In interviews, SPOF discussion is expected whenever you design any production system.

---

## Common SPOF examples

1. **Single application server**
	- One VM/pod handling all traffic.
	- Crash = total outage.

2. **Single database instance**
	- No replica/failover.
	- DB down = entire product down.

3. **Single load balancer / API gateway instance**
	- Routing layer failure blocks all requests.

4. **Single cache node (no cluster/replication)**
	- Cache outage may overload DB (thundering herd).

5. **Single availability zone/region deployment**
	- Zone outage knocks out all services.

6. **Single DNS provider / misconfigured DNS**
	- Resolution failure appears as full outage.

7. **Single CI/CD pipeline or artifact registry**
	- Cannot deploy/fix incidents quickly.

8. **Single credential/secret authority without backup**
	- Access loss or compromise halts operations.

---

## Detecting SPOFs (interview approach)

Use this mental model:
1. Draw all critical request path components.
2. For each component ask:
	- “If this dies, can traffic still succeed?”
3. If answer is “No,” you found a SPOF.
4. Verify whether there is automatic failover.
5. Verify if failover is tested (not just configured).

Interview phrase:
“Redundancy without tested failover is potential SPOF.”

---

## How to remove SPOFs

### 1) Redundancy
Run at least 2 instances of every critical component.

### 2) Failover
Automatic health checks and failover routing.

### 3) Replication
Data replicated across nodes/zones/regions.

### 4) Stateless service design
Store session/state externally so any instance can serve requests.

### 5) Multi-AZ / Multi-region strategy
Deploy across failure domains.

### 6) Graceful degradation
Non-critical features fail softly while core flow remains available.

### 7) Circuit breakers and timeouts
Prevent one failing downstream from collapsing whole system.

### 8) Backups + restore drills
Backups are useless unless restore is tested regularly.

---

## Example: E-commerce checkout SPOF analysis

Critical path:
`Client -> LB -> App -> DB -> Payment provider`

Potential SPOFs:
- One LB instance
- Single primary DB with no standby
- Single payment integration endpoint

Fixes:
- LB in HA pair or managed multi-node LB
- DB primary + replicas + automatic failover
- Payment provider failover to secondary PSP

Result:
- Individual node failure no longer causes total checkout outage.

---

## Trade-offs of removing SPOFs

Advantages:
- Higher uptime
- Better fault tolerance
- Lower incident severity

Costs:
- Higher infrastructure cost
- More operational complexity
- More complex data consistency/failover handling

Interview tip:
Mention both resilience gain and complexity/cost impact.

## Metrics to prove SPOF risk is reduced

- Uptime SLO (e.g., 99.95%)
- MTTR (Mean Time To Recovery)
- Failover success rate
- Error rate during chaos/failover tests
- Recovery time during drills

## Common interview questions + strong answers

### Q1: “How do you identify SPOFs quickly?”
Answer:
“I map the critical request path end-to-end, then evaluate each dependency for redundancy and automatic failover. Any component that can’t fail without user impact is a SPOF.”

### Q2: “Is having 2 instances enough?”
Answer:
“Not always. They must be in different failure domains, with health checks and tested failover. Two instances in one AZ can still be a SPOF at AZ level.”

### Q3: “Can a database still be a SPOF with replicas?”
Answer:
“Yes, if failover is manual/slow, replication lag is too high, or app cannot reconnect automatically during role change.”

---

## One-line interview summary
“A SPOF is any single dependency whose failure breaks critical user flows; production-grade design removes SPOFs with redundancy, automated failover, and regular failure testing across fault domains.”
