# Database Indexes in System Design

## Overview

**Database indexes** are critical data structures that enable **fast data retrieval** by reducing the number of disk I/O operations. Without indexes, databases must scan every row (full table scan), which is prohibitively slow at scale.

> **Interview one-liner:** Indexes = trade memory for speed; let you find data in O(log n) time instead of O(n).

---

## Why Indexes Matter in System Design

In system design, query performance directly impacts:
- **Latency** – How fast can you respond to user requests?
- **Throughput** – How many concurrent queries can you handle?
- **Infrastructure cost** – Do you need fewer, more powerful servers?
- **User experience** – Do pages load in <200ms (indexed) or >5s (no indexes)?

### Performance Impact (Example: YouTube)

**Finding a user's videos without index:**
```
SELECT * FROM videos WHERE creator_id = 1234;
→ Must scan ALL 2 billion videos in the table
→ Read from disk: 2B rows × 1KB each = 2TB of data
→ Time: 10-60 seconds (UNACCEPTABLE)
```

**Finding a user's videos WITH index on creator_id:**
```
Index: creator_id → [video_id_1, video_id_2, ...]
→ B-tree lookup: O(log n) = ~30 disk reads (from 2B videos)
→ Time: 0.1-1 second (ACCEPTABLE)
```

**Impact: 100x to 1000x speed improvement!**

## Types of Indexes

### 1. **Primary Index**
Uniquely identifies each row; automatically created for primary key.

```
Primary Key: user_id (unique)
Index: user_id → row_pointer

Query: SELECT * FROM users WHERE user_id = 100;
→ Binary search on index: finds immediately
```

### 2. **Secondary Index (Non-Unique)**
Index on non-primary-key columns.

```
Non-unique Index: creator_id
Index: creator_id → [row_pointer_1, row_pointer_2, ...]

Query: SELECT * FROM videos WHERE creator_id = 5;
→ Finds all videos by that creator
```

### 3. **Composite Index (Multi-column)**
Index on multiple columns; efficient for multi-column queries.

```
Composite Index: (creator_id, upload_date)
Index structure: (creator_id, upload_date) → row_pointer

Query: SELECT * FROM videos 
       WHERE creator_id = 5 AND upload_date > '2025-01-01';
→ Very efficient: leverages both columns
```

### 4. **Full-Text Index**
Optimized for searching text content.

```
Full-Text Index: title, description
Index: word → [document_id_1, document_id_2, ...]

Query: SELECT * FROM videos WHERE MATCH(title) AGAINST('machine learning');
→ Finds all videos with "machine learning" in title
```

### 5. **Hash Index**
Uses hash function; best for equality searches.

```
Hash Index: email → row_pointer
Hash('alice@gmail.com') = bucket_123 → row_pointer

Query: SELECT * FROM users WHERE email = 'alice@gmail.com';
→ O(1) lookup (perfect hash)
```

**Trade-off:** Can't do range queries (WHERE email LIKE 'alice%')

### 6. **B-Tree Index** (Most Common)
Balanced tree structure; efficient for both equality and range queries.

```
B-Tree Index: user_id

           [50]
          /    \
      [20]      [80]
     /   \      /   \
  [10] [30] [60] [90]

Query: WHERE user_id > 50 AND user_id < 90
→ Navigates tree efficiently
```

## Index Data Structures

### 1. **B-Tree** (Default for most databases)
- **Balanced tree** – Left and right subtrees have similar height
- **Multi-way tree** – Each node has multiple children
- **Efficient range queries** – Traverse from left (min) to right (max)
- **Used by:** MySQL (InnoDB), PostgreSQL, Oracle

**Pros:**
- Good for both equality and range queries
- Guaranteed O(log n) lookup
- Automatically balanced

**Cons:**
- More complex than Hash
- Range queries require tree traversal

### 2. **Hash Index**
- **Direct lookup** – Hash function maps key to bucket
- **O(1) for equality** – Very fast for exact matches
- **No ordering** – Can't efficiently handle ranges

**Pros:**
- Super fast for equality (O(1) vs O(log n))
- Simple to understand

**Cons:**
- Can't do range queries (WHERE age > 20)
- Hash collisions require resolution
- Not sortable

### 3. **Bitmap Index**
- Uses bitmap (array of bits) for low-cardinality columns
- Efficient for boolean/categorical data

**Use:** Gender (M/F), Status (Active/Inactive), Priority (1-5)

```
Gender Index:
  Value | Bitmap (each bit = one row)
  ──────┼──────────────────────────
  M     | 1010101010...
  F     | 0101010101...

Count males: Sum bits in "1010101010..." = fast!
```

### 4. **Inverted Index**
- Maps terms to documents containing them
- Used for full-text search

```
Inverted Index: word → document_list

"machine" → [vid_1, vid_3, vid_7, vid_100]
"learning" → [vid_1, vid_5, vid_9]
"neural" → [vid_2, vid_3, vid_100]

Query: "machine learning"
→ Intersection: [vid_1, vid_3] ∩ [vid_1, vid_5, vid_9]
→ Result: [vid_1]
```

## When to Index (System Design Perspective)

### ✅ CREATE INDEX if:
1. Column is frequently in **WHERE clause** (filter)
   ```sql
   SELECT * FROM videos WHERE creator_id = 5;  -- Index creator_id
   ```

2. Column is in **JOIN condition**
   ```sql
   SELECT * FROM videos v JOIN creators c ON v.creator_id = c.id;
   -- Index: creator_id, id
   ```

3. Column is in **ORDER BY / GROUP BY**
   ```sql
   SELECT * FROM videos ORDER BY upload_date;  -- Index upload_date
   ```

4. Column is in **aggregations** (COUNT, SUM, AVG)
   ```sql
   SELECT COUNT(*) FROM videos WHERE status = 'published';
   -- Index: status
   ```

5. Large table with infrequent updates
   ```sql
   -- Users table (100M rows, rarely updated)
   CREATE INDEX idx_user_email ON users(email);  -- YES
   ```

### ❌ AVOID INDEX if:
1. Column has **low cardinality** (few distinct values)
   ```sql
   -- Gender column (only 2-3 values for millions of rows)
   -- Index wastes space, minimal benefit
   ```

2. Table is **small** (<10K rows)
   ```sql
   -- Full scan is often faster than index lookup
   ```

3. Column is **frequently updated**
   ```sql
   -- Index must be updated with every write
   -- Slows down inserts/updates
   ```

4. Query uses **wildcard at start**
   ```sql
   WHERE video_title LIKE '%random%';  -- Requires full-text search, not index
   ```

## YouTube Indexing Strategy (System Design Example)

YouTube has 2+ billion videos, billions of users. Without smart indexing, it would be impossibly slow.

### Videos Table Indexes

```sql
CREATE TABLE videos (
  video_id BIGINT PRIMARY KEY,      -- Primary index (implicit)
  creator_id BIGINT,                -- Many queries filter by creator
  title VARCHAR(500),               -- Full-text search
  description TEXT,                 -- Full-text search
  upload_date TIMESTAMP,            -- Recent videos often queried
  view_count BIGINT,                -- Leaderboard queries
  status VARCHAR(20),               -- Published/Draft/Deleted
  category VARCHAR(50),             -- Browse by category
  duration INT,                     -- Filter by length
  created_at TIMESTAMP,             -- Sort by newest
  updated_at TIMESTAMP              -- Maintenance
);

-- CRITICAL INDEXES:
CREATE INDEX idx_creator_id ON videos(creator_id);
  -- Query: "Show all videos by alice"
  -- Without: 2B scan; With: instant
  
CREATE FULLTEXT INDEX idx_title ON videos(title, description);
  -- Query: Search videos for "machine learning"
  
CREATE INDEX idx_upload_date ON videos(upload_date DESC);
  -- Query: Show newest videos first
  
CREATE INDEX idx_creator_upload (creator_id, upload_date);
  -- Query: Videos by creator, sorted by date
  -- Composite index for multi-filter queries
  
CREATE INDEX idx_status ON videos(status);
  -- Query: Count published videos (status = 'published')
  
CREATE INDEX idx_category ON videos(category);
  -- Query: Browse videos by category
```

### Users Table Indexes

```sql
CREATE TABLE users (
  user_id BIGINT PRIMARY KEY,
  email VARCHAR(255),
  username VARCHAR(100),
  created_at TIMESTAMP
);

-- CRITICAL INDEXES:
CREATE UNIQUE INDEX idx_email ON users(email);
  -- Query: Login by email (must be unique and fast)
  
CREATE UNIQUE INDEX idx_username ON users(username);
  -- Query: Profile lookup by username
```

### Engagement Table Indexes

```sql
CREATE TABLE engagements (
  engagement_id BIGINT PRIMARY KEY,
  video_id BIGINT,
  user_id BIGINT,
  action VARCHAR(20),        -- 'like', 'watch', 'share'
  timestamp TIMESTAMP
);

-- CRITICAL INDEXES:
CREATE INDEX idx_video_user ON engagements(video_id, user_id);
  -- Query: Did user_123 like video_456?
  
CREATE INDEX idx_user_timestamp ON engagements(user_id, timestamp);
  -- Query: Show user's watch history (most recent first)
```

### Index Impact on YouTube Performance

| Query | Without Index | With Index | Speedup |
|-------|---------------|-----------|---------|
| Show videos by creator | 2-10 seconds | 10-100ms | 100x+ |
| Full-text search videos | 5-30 seconds | 100-500ms | 20x+ |
| Count user likes | 1-5 seconds | 10-50ms | 100x+ |
| Recent videos first | 3-15 seconds | 100-200ms | 50x+ |

## Index Trade-offs (System Design)

### Memory vs Speed

```
No Index:
  Memory used: Low (data only)
  Query speed: Slow (O(n) full scan)
  Write speed: Fast (no index update)
  
With Index:
  Memory used: High (data + index)
  Query speed: Fast (O(log n) lookup)
  Write speed: Slower (update index too)
```

**YouTube Example:**
- 2 billion videos without indexes: 2TB data
- Same with 10 indexes: 2TB data + 500GB indexes = 2.5TB
- **Worth it:** 10x cost for 100x speed

### Write Amplification

```
Insert video without index:
  1 write to table = 1 operation

Insert video WITH 5 indexes:
  1 write to table + 5 writes to indexes = 6 operations
  Write cost: 6x higher
```

**For YouTube:**
- Writes: 500 hours/minute = ~8 hours/second
  - Without indexes: 8 disk writes/sec
  - With indexes: 8 × 5 = 40 writes/sec (still manageable)
- Reads: Millions/second
  - With indexes: Fast; Without: impossible

**Decision: Indexes are CRITICAL**

## Complex Indexing Scenarios

### Covering Index
Index contains all columns needed for query; no table lookup required.

```sql
Query: SELECT title, view_count FROM videos WHERE creator_id = 5;

Without Covering Index:
  1. Look up creator_id=5 in index → [video_id_1, video_id_2, ...]
  2. For each video_id, fetch from table: title, view_count
  3. Returns to user

With Covering Index (creator_id, title, view_count):
  1. Look up creator_id=5 in index → [title, view_count, title, view_count, ...]
  2. Return immediately (no table lookup needed!)
```

**Benefit:** Eliminates the table lookup; faster queries

### Partial Index
Index only rows matching a condition.

```sql
-- Only index published videos (90% of queries look up published)
CREATE INDEX idx_published_creator 
ON videos(creator_id) WHERE status = 'published';

Saves index space (only 90% of rows indexed)
Faster inserts (don't index draft/deleted videos)
```

### Sparse Index
Index only certain rows (one entry per block).

```sql
Table: 1 billion rows
Sparse Index: 1 entry per 1000 rows = 1 million index entries
Binary search on index: O(log 1M) ≈ 20 comparisons
```

## Monitoring Indexes (System Design)

### Which Indexes Are Being Used?

```sql
-- PostgreSQL:
SELECT schemaname, tablename, indexname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan DESC;

-- MySQL:
SELECT * FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_name = 'videos';
```

### Remove Unused Indexes

```sql
-- If idx_scan = 0, index is never used
-- Delete it to save memory and speed up writes

DROP INDEX idx_category ON videos;  -- If never queried
```

### Handle Hot Tables

YouTube's videos table grows 500 hours/minute:

```
Problem: Millions of inserts/second slow down with indexes
Solution 1: Batch inserts (insert 10K at once)
Solution 2: Disable indexes during bulk load, rebuild after
Solution 3: Use write-optimized storage (LSM trees)
```

## Interview Quick-Fire Q&A

**Q: Why use indexes?**
Trade memory for speed; O(log n) lookup vs O(n) full scan = 100x+ faster.

**Q: When NOT to index?**
Low cardinality (gender), small table, frequently updated column, wildcard search.

**Q: Primary vs secondary index?**
Primary uniquely identifies rows (implicit, usually B-tree). Secondary is explicit index on any column.

**Q: Composite index vs single-column?**
Composite: efficient for multi-column queries. Single: simpler, takes less space.

**Q: Hash vs B-tree index?**
Hash: O(1) equality, can't do ranges. B-tree: O(log n), handles range queries.

**Q: YouTube: How many indexes on videos table?**
10-20 indexes covering: creator_id, upload_date, status, category, full-text search, composite.

**Q: Cost of maintaining indexes?**
Write amplification: 1 insert × 10 indexes = 10 writes. Offset by 100x read speedup.

**Q: Covering index benefit?**
No table lookup needed; query answered entirely from index (faster).

**Q: How to find unused indexes?**
Look at idx_scan count; if 0, index unused. Delete to save space.

## Key Takeaways

- **Indexes** = critical for query speed (10-1000x faster)
- **Index on:** WHERE columns, JOIN columns, ORDER BY, GROUP BY
- **Avoid:** Low cardinality, small tables, frequently updated
- **B-tree:** Most common; good for range queries
- **Hash:** Fastest for equality, can't do ranges
- **Composite index:** Efficient for multi-column queries
- **Write trade-off:** More indexes = slower inserts/updates
- **YouTube strategy:** 10+ indexes per table, carefully monitored
- **Monitor:** Find unused indexes, delete to save memory
