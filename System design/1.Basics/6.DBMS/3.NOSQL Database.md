# NoSQL Database in System Design

## Overview

**NoSQL** databases are non-relational, distributed data stores designed for **massive scale, high performance, and flexible schemas**. They are essential in system design for handling big data, real-time applications, and scenarios where traditional SQL databases hit scalability limits.

> **Interview one-liner:** NoSQL = schema-flexible, horizontally scalable databases built for high throughput and availability, sacrificing strict ACID for performance.

---

## When to Use NoSQL vs SQL

| Scenario | SQL | NoSQL |
|----------|-----|-------|
| **Structured, relational data** | ✅ | ❌ |
| **Complex joins, transactions** | ✅ | ❌ |
| **Massive scale (millions of users)** | ❌ | ✅ |
| **Flexible/evolving schema** | ❌ | ✅ |
| **Real-time big data** | ❌ | ✅ |
| **High write throughput** | ❌ | ✅ |

## Four Types of NoSQL Databases

### 1. **Key-Value Stores**
Simplest data model: key → value pairs.

**Use Cases:**
- Caching (Redis, Memcached)
- Session storage
- Real-time leaderboards
- Rate limiting

**Examples:** Redis, DynamoDB, Riak, Memcached

**Pros:**
- Ultra-fast (O(1) lookup)
- Horizontal scalability
- Simple data model

**Cons:**
- No complex queries
- Limited to key lookups
- No relational joins

**YouTube Example:**
```
users:101:profile → { name: "Alice", email: "alice@youtube.com" }
users:101:subscriptions → ["channel_1", "channel_2", ...]
videos:trending:1h → ["vid_1", "vid_2", "vid_3", ...]
```

---

### 2. **Document Stores**
Store semi-structured data as JSON/BSON documents.

**Use Cases:**
- User profiles and metadata
- Product catalogs
- Content management
- Real-time analytics

**Examples:** MongoDB, CouchDB, Firebase, DynamoDB (also supports documents)

**Data Model:**
```json
{
  "_id": "vid_12345",
  "title": "How to Design YouTube",
  "creator": "john_doe",
  "views": 1234567,
  "likes": 45678,
  "comments": [
    { "user": "alice", "text": "Great!", "timestamp": "2025-01-15T10:30:00Z" },
    { "user": "bob", "text": "Very helpful", "timestamp": "2025-01-15T11:00:00Z" }
  ],
  "tags": ["system-design", "youtube", "tutorial"],
  "metadata": {
    "duration": 1234,
    "resolution": "1080p",
    "uploadDate": "2025-01-10"
  }
}
```

**Pros:**
- Flexible schema (nested data)
- Query language (MongoDB query syntax)
- Easy for developers (JSON-like)
- Horizontal scaling via sharding

**Cons:**
- Lacks ACID across documents (eventual consistency)
- Joins are expensive / require denormalization
- Storage overhead (duplicate data across documents)

---

### 3. **Column-Family (Wide-Column) Stores**
Store data in columns rather than rows; optimized for writes and analytics.

**Use Cases:**
- Time-series data (metrics, logs, IoT)
- Analytics and reporting
- Historical data

**Examples:** Cassandra, HBase, Google Bigtable

**Data Model:**
```
Row Key          | Timestamp | CPU  | Memory | Disk
─────────────────┼───────────┼──────┼────────┼────
server_1:10:00   | 1641234000| 45%  | 78%    | 23%
server_1:10:05   | 1641234300| 52%  | 82%    | 25%
server_2:10:00   | 1641234000| 12%  | 34%    | 89%
server_2:10:05   | 1641234300| 18%  | 40%    | 91%
```

**Pros:**
- Highly compressed (column storage)
- Fast for time-series queries
- Massive scale (petabytes)
- Write-optimized

**Cons:**
- Complex to use
- Not good for transactional reads
- Steep learning curve

---

### 4. **Graph Databases**
Store data as nodes and edges (relationships first-class).

**Use Cases:**
- Social networks (friends, followers)
- Recommendations (users who liked X also liked Y)
- Knowledge graphs
- Fraud detection

**Examples:** Neo4j, Amazon Neptune, ArangoDB

**Data Model:**
```
Node (User):
  alice (id: 1, name: "Alice", age: 30)
  bob (id: 2, name: "Bob", age: 25)

Edge (Relationship):
  alice --[FOLLOWS]--> bob
  alice --[LIKES]--> video_123
  bob --[LIKES]--> video_456
  
Query: "Find videos liked by users that alice follows"
Result: video_456 (bob likes it, alice follows bob)
```

**Pros:**
- Natural for relational data
- Fast for relationship queries
- Powerful graph algorithms

**Cons:**
- Not ideal for large-scale distributed queries
- Harder to scale horizontally than document stores
- Limited horizontal sharding support

---

## Comparison: All Four Types

| Type | Speed | Scaling | Query | Schema | Best For |
|------|-------|---------|-------|--------|----------|
| **Key-Value** | Very Fast | ∞ | Key only | None | Cache, sessions |
| **Document** | Fast | Very Good | Flexible | Semi-structured | Content, metadata |
| **Wide-Column** | Moderate | Excellent | Row ranges | Flexible | Time-series, analytics |
| **Graph** | Moderate | Good* | Relationships | Fixed | Social, recommendations |

## YouTube's NoSQL Strategy (System Design Example)

YouTube needs multiple databases for different purposes:

### 1. **Key-Value Store (Redis)**
**Use:** Leaderboards, feed cache, user sessions

```
trending:videos:1h → ["video_1", "video_2", "video_3", ...]
user:101:watchlist → ["video_a", "video_b", "video_c"]
leaderboard:creators:28d → {"alice": 5M, "bob": 4M, "charlie": 3M}
```

### 2. **Document Store (MongoDB / CouchDB)**
**Use:** Video metadata, user profiles, comments

```json
{
  "_id": "vid_abc123",
  "title": "System Design Tutorial",
  "creator": "john_doe",
  "description": "...",
  "views": 2345678,
  "likes": 123456,
  "comments": [{ "user": "alice", "text": "...", "likes": 50 }],
  "tags": ["tutorial", "system-design"],
  "category": "Education"
}
```

### 3. **Wide-Column Store (Cassandra / HBase)**
**Use:** View counts, engagement metrics, time-series analytics

```
video_123:2025-01-15:00:00 → views: 5000, likes: 234, shares: 12
video_123:2025-01-15:01:00 → views: 6200, likes: 289, shares: 18
video_123:2025-01-15:02:00 → views: 5800, likes: 267, shares: 15
```

### 4. **Graph Database (Neo4j)**
**Use:** Recommendations, social graph

```
alice --[FOLLOWS]--> john_doe
bob --[LIKES]--> video_abc123
alice --[WATCHED]--> video_xyz789
video_abc123 --[RELATED_TO]--> video_xyz789

Query: Recommend videos that friends have watched
```

## NoSQL Design Patterns

### 1. **Denormalization**
Store redundant data to avoid joins.

**SQL Approach (normalized):**
```
User table:     {user_id: 1, name: "alice"}
Channel table:  {channel_id: 1, name: "Alice's Channel", user_id: 1}

Query: SELECT * FROM users u JOIN channels c ON u.user_id = c.user_id
```

**NoSQL Approach (denormalized):**
```json
{
  "_id": "channel_1",
  "name": "Alice's Channel",
  "creator": {
    "user_id": 1,
    "name": "alice",
    "email": "alice@youtube.com"
  }
}
```

**Pro:** Faster reads (no joins)  
**Con:** Data duplication, update anomalies

### 2. **Sharding / Partitioning**
Split data across multiple servers by a shard key.

```
Videos by creator:
  Shard 1: alice, bob, charlie
  Shard 2: david, emma, frank
  Shard 3: grace, henry, iris

Query: Find videos by alice
→ Routes to Shard 1 (shard key: creator)
```

### 3. **Read Replicas**
Copy data across servers for read scaling.

```
Master (writes):   Primary HBase instance
Replica 1 (reads): Secondary HBase instance
Replica 2 (reads): Tertiary HBase instance
```

## ACID vs BASE Trade-offs

| ACID (SQL) | BASE (NoSQL) |
|-----------|--------------|
| **A**tomicity | **B**asically Available |
| **C**onsistency | **S**oft state |
| **I**solation | **E**ventual consistency |
| **D**urability | |

**Eventual Consistency:** Replicas converge over time; a read might return stale data.

**YouTube Example:**
```
User uploads video
→ Metadata written to primary MongoDB
→ Replicas eventually sync (0.1-1 second later)
→ During sync window, some users see old metadata
→ After sync, all users see new metadata (eventually consistent)
```

## Scaling NoSQL Databases

### Horizontal Scaling (Sharding)
```
Videos Database (MongoDB):
Shard 1: video IDs 1-1M (creator: alice-david)
Shard 2: video IDs 1M-2M (creator: emma-henry)
Shard 3: video IDs 2M-3M (creator: iris-zoe)

Query: Find video_1500000
→ Hash("video_1500000") = Shard 2
→ Fetch from Shard 2 database
```

### Vertical Scaling
```
Single MongoDB server:
- CPU: 2 cores → 64 cores
- RAM: 8 GB → 1 TB
- Disk: 100 GB → 100 TB
```

Most NoSQL systems **prefer horizontal** (sharding) because it's cheaper and scales to infinity.

## CAP Theorem in NoSQL

NoSQL systems choose two of three:
- **C**onsistency (all nodes see same data)
- **A**vailability (system always up)
- **P**artition tolerance (survives network splits)

**YouTube's Choice: AP (Availability + Partition Tolerance)**
- Prefers availability over consistency
- Doesn't matter if video views count is off by 100 for 1 second
- Matters if video is unavailable for users

**Example:**
```
Network partition between US and EU data centers
- Cassandra (AP): US continues serving users, EU continues serving users
  After network heals, data eventually syncs
  
- HBase (CP): US stops accepting writes, waits for EU
  Consistent, but less available
```

YouTube chooses **AP** because:
- Users > consistency
- "Video unavailable" is worse than "view count slightly off"

## Interview Quick-Fire Q&A

**Q: Why use NoSQL over SQL?**
Scale, flexibility, high write throughput, distributed architecture.

**Q: Which NoSQL type for YouTube?**
Key-Value (cache), Document (metadata), Wide-Column (analytics), Graph (recommendations).

**Q: Denormalization: pro and con?**
Pro: Fast reads, no joins. Con: Data duplication, update anomalies.

**Q: What is eventual consistency?**
Replicas converge over time; reads might return stale data temporarily.

**Q: How do you shard a NoSQL database?**
Choose shard key (e.g., user_id), hash it to determine which shard.

**Q: CAP: consistency vs availability?**
Depends on use case. YouTube chooses availability (AP).

**Q: Can you do ACID transactions in NoSQL?**
Limited; most NoSQL trades ACID for performance.

**Q: How to handle hot shards?**
Use better shard key, add more replicas to hot shard, implement caching.

## Key Takeaways

- **NoSQL** = flexible schema, horizontal scaling, high throughput
- **Four types:** Key-Value (fast), Document (flexible), Wide-Column (analytical), Graph (relational)
- **YouTube uses all four** for different purposes
- **Denormalization** common in NoSQL to avoid expensive joins
- **BASE not ACID** – eventual consistency is acceptable for most use cases
- **Sharding** = horizontal scaling; choose shard key carefully
- **CAP theorem:** Choose 2 of Consistency, Availability, Partition Tolerance
- **Most systems choose AP** (availability over consistency)
