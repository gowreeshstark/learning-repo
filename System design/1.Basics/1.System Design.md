# System Design Fundamentals

## What is System Design?

**System Design** is the process of designing the **architecture and infrastructure** of a software application to meet functional and non-functional requirements efficiently. It involves making decisions about **how components interact**, **how data flows**, **how the system scales**, and **how it handles failures**.

> **Interview one-liner:** System Design = building scalable, reliable, maintainable software systems that work at scale.

---

## Why System Design Matters?

- **Scalability** – Handle millions of users/requests without crashing
- **Reliability** – System remains operational despite failures
- **Maintainability** – Code is easy to understand, modify, debug
- **Performance** – Low latency, high throughput
- **Cost efficiency** – Optimal use of resources
- **User experience** – Fast, responsive applications

---

## Key Concepts in System Design

### 1. **Scalability**
The ability to handle **growing amounts of data/users/traffic** without performance degradation.
- **Vertical Scaling** (scale up): Add more resources to a single machine
- **Horizontal Scaling** (scale out): Add more machines

### 2. **Availability & Reliability**
- **Availability** – System is operational and serving requests (uptime %)
- **Reliability** – System performs correctly without failures
- Achieved through redundancy, load balancing, replication

### 3. **Performance**
- **Latency** – Response time (how fast is a request answered?)
- **Throughput** – Number of requests processed per second
- Optimized via caching, indexing, async processing

### 4. **Consistency**
- Data remains valid and synchronized across replicas
- Trade-offs: CAP theorem (Consistency, Availability, Partition tolerance)

### 5. **Fault Tolerance**
- System continues working despite hardware/software failures
- Mechanisms: replication, backup, failover

### 6. **Security**
- Authentication, authorization, encryption
- Protection against attacks and data breaches

## Key Components in System Design

### 1. **Load Balancer**
Distributes incoming traffic across multiple servers.
- Ensures no single server gets overloaded
- Enables horizontal scaling
- Example: NGINX, AWS ELB

### 2. **Web Servers / Application Servers**
Handle HTTP requests, execute business logic.
- Stateless to enable horizontal scaling
- Example: Node.js, Python Flask, Java Spring

### 3. **Databases**
Store persistent data.
- **SQL**: Structured, ACID, relational (MySQL, PostgreSQL)
- **NoSQL**: Flexible schema, distributed (MongoDB, Cassandra)
- See [Database folder](../../Database) for details

### 4. **Cache** (critical for performance)
Store frequently accessed data in fast memory.
- **Application cache**: Redis, Memcached
- **CDN**: Cloudflare, Akamai (static content)
- Reduces DB load, improves response time

### 5. **Message Queues**
Decouple components, enable async processing.
- **Pub/Sub**: RabbitMQ, Kafka
- Tasks processed asynchronously, improving responsiveness

### 6. **Replication & Backup**
Data redundancy for availability.
- Master-slave replication
- Multi-region replication
- See [Database Replication](../../Database/11.Replication.md)

### 7. **API Gateway**
Single entry point for all APIs.
- Rate limiting, authentication, routing
- Example: AWS API Gateway, Kong

## Design Approaches

### Monolithic Architecture
```
┌─────────────────────────┐
│   Monolithic App        │
│ ├─ Auth module          │
│ ├─ Order module         │
│ ├─ Payment module       │
│ ├─ Shipping module      │
│ └─ Notification module  │
└──────────┬──────────────┘
           │
        Database
```

**Pros:** Simple, easy to develop initially, cohesive  
**Cons:** Hard to scale, tightly coupled, difficult to deploy

### Microservices Architecture
```
┌──────────────┐
│ Auth Service │
└──────┬───────┘
       │
┌──────────────┐      ┌──────────────┐
│Order Service ├─────▶│Payment Svc   │
└──────┬───────┘      └──────────────┘
       │
┌──────────────┐      ┌──────────────┐
│Shipping Svc  │      │Notification  │
└──────────────┘      └──────────────┘
```

**Pros:** Scalable, independent deployment, tech flexibility  
**Cons:** Complexity, distributed transaction issues, network latency

## Non-Functional Requirements (NFRs)

What we optimize for (beyond just "it works"):

| NFR | Definition | Example |
|-----|-----------|---------|
| **Scalability** | Handle growth in users/data | Support 1M concurrent users |
| **Availability** | System uptime % | 99.99% uptime (4 nines) |
| **Latency** | Response time | <200ms for API calls |
| **Throughput** | Requests per second | 100K requests/sec |
| **Consistency** | Data accuracy | All users see same data |
| **Durability** | Data persistence | No data loss on failure |
| **Security** | Protection from attacks | HTTPS, authentication |
| **Cost** | Infrastructure cost | <$0.01 per user/month |

## Common Design Patterns

### 1. **Load Balancing**
Distribute traffic across servers. Essential for scaling.

### 2. **Caching**
Store hot data in fast memory. Reduces DB load.

### 3. **Database Replication**
Copy data across servers for availability.

### 4. **Sharding / Partitioning**
Split data across multiple databases for horizontal scaling.

### 5. **Async Processing**
Use message queues for time-consuming tasks.

### 6. **Circuit Breaker**
Prevent cascading failures by stopping calls to failing services.

### 7. **Rate Limiting**
Control request rate to prevent abuse and overload.

### 8. **API Versioning**
Support multiple API versions for backward compatibility.

## System Design Interview Process

**Typical Question:** "Design a system like Twitter / Uber / Netflix"

### Step 1: Clarify Requirements
- **Functional**: What features? ("Tweet, like, follow")
- **Non-functional**: Scale? ("100M users, 1M concurrent")

### Step 2: High-Level Architecture
- Draw boxes (client, load balancer, servers, DB, cache)
- Show data flow

### Step 3: Deep Dive
- Database schema
- API endpoints
- Caching strategy
- How to handle scale?

### Step 4: Address Trade-offs
- Consistency vs Availability (CAP)
- Cost vs performance
- Simplicity vs scalability

### Step 5: Handle Failures
- What if cache fails?
- What if database crashes?
- Network partitions?

## Interview Quick-Fire Q&A

**Q: Vertical vs horizontal scaling?**
Vertical = bigger machine; Horizontal = more machines. See [2.Horizontal vs Vertical Scaling.md](2.Horizontal%20vs%20Vertical%20Scaling.md)

**Q: Why is caching important?**
Reduces database load, improves response time by serving hot data from fast memory.

**Q: Monolithic vs microservices?**
Monolithic is simpler initially; microservices scale better but add complexity.

**Q: What is a load balancer?**
Distributes incoming traffic across servers to prevent overload.

**Q: How do you ensure high availability?**
Replication, load balancing, failover mechanisms, multiple data centers.

**Q: SQL vs NoSQL?**
SQL for structured, transactional data; NoSQL for flexible, large-scale data.

**Q: What is CAP theorem?**
In distributed systems: pick 2 of Consistency, Availability, Partition tolerance.

**Q: Why decouple with message queues?**
Enables async processing, prevents cascading failures, improves responsiveness.

## Key Takeaways

- **System Design** = building scalable, reliable systems for millions of users.
- **Core pillars:** Scalability, Availability, Performance, Consistency, Security.
- **Load balancers, caches, databases, message queues** are essential components.
- **Trade-offs** everywhere: consistency vs availability, cost vs performance.
- **Design iteratively**: clarify requirements → architecture → deep dive → trade-offs.
