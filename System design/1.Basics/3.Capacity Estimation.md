# Capacity Estimation in System Design

## Overview

**Capacity Estimation** is the process of calculating **how much infrastructure (servers, storage, bandwidth)** a system needs to handle a given load. It's a critical component of system design that bridges business requirements to technical architecture.

> **Interview one-liner:** Capacity Estimation = math to figure out how many servers, storage, and bandwidth you need.

---

## Why Capacity Estimation Matters

- **Cost Planning** – Know infrastructure budget upfront
- **Resource Allocation** – Don't over-provision or under-provision
- **Performance Guarantees** – Ensure system meets latency/throughput requirements
- **Scaling Strategy** – Know when to add servers
- **Failure Planning** – Account for redundancy and backups

---

## Key Metrics to Estimate

### 1. **Daily Active Users (DAU)**
Users who use the system at least once per day.

### 2. **Monthly Active Users (MAU)**
Users who use the system at least once per month.

### 3. **Concurrent Users**
Users accessing the system **at the same time**.

Formula:
```
Concurrent Users = (DAU × 1) / Seconds in a day
                 = DAU × (1 / 86,400)

Example:
If 500M DAU uniformly distributed across 24 hours:
Concurrent = 500M / 86,400 = ~5,787 concurrent users
```

But in reality, traffic is **non-uniform** (peak hours):
```
Concurrent Users (Peak) = Concurrent Users × Peak Multiplier
                        = 5,787 × 3 (3x during peak hours)
                        = ~17,361 concurrent users
```

### 4. **Requests Per Second (RPS)**
How many requests hit the servers per second.

Formula:
```
RPS = Concurrent Users × Average Requests per User per Second
    = 17,361 × 2  (assuming each user makes 2 requests/sec on average)
    = ~34,722 RPS
```

### 5. **Storage Requirements**
How much disk space is needed for data.

Formula:
```
Total Storage = (DAU × Time Period × Data per User) + Redundancy
              = (500M × 365 days × 2KB per day) + 3x redundancy
```

### 6. **Bandwidth / Network Throughput**
Data transferred per second.

Formula:
```
Bandwidth (per request) = Average Response Size
Bandwidth (total) = RPS × Average Response Size
                  = 34,722 RPS × 1 MB
                  = ~34.7 GB/sec
```

## YouTube Capacity Estimation Example

YouTube is a great case study because it involves **massive scale** with diverse requirements.

### Step 1: Define the Requirements

#### Functional Requirements
- Users can upload videos
- Users can watch videos
- Users can like, comment, subscribe
- Recommendations/suggestions

#### Non-Functional Requirements
- 2 billion monthly active users (MAU)
- 500 million daily active users (DAU)
- Support peak traffic (3x average)
- 99.9% availability (few nines)
- <2 second video start time (latency)

### Step 2: Calculate Concurrent Users

```
DAU = 500M users

Uniformly distributed (24 hours):
  Concurrent = 500M / 86,400 seconds
             = ~5,787 concurrent users

Peak hours (assume 3x during 8 peak hours, 1x during 16 off-peak):
  Average concurrent = (500M × 8 × 3 + 500M × 16 × 1) / (24 × 86,400)
                     = (12B + 8B) / 2.07M
                     = ~9,615 concurrent users (average)

Peak concurrent = 9,615 × 3 = ~28,845 concurrent users
```

### Step 3: Calculate Requests Per Second (RPS)

```
Average user behavior:
- Watches 3-5 videos per day → 4 videos/day average
- Each video = 1 view request
- Plus metadata requests (comments, recommendations, etc.)
- ~10 API calls per video

RPS per user = (4 videos × 10 calls) / 86,400 seconds
             = 40 calls / 86,400 seconds
             = ~0.0005 calls/sec per user

Peak RPS = 28,845 concurrent users × 0.0005 calls/sec
         = ~14 RPS (seems low!)

Actually, let's think differently:
Peak concurrent = 28,845 users
Each user browses YouTube, watches previews, checks feed
Average: 0.5-1 request per second per user

Peak RPS = 28,845 × 1 = ~28,845 RPS (more realistic)
Add 20% for internal requests, retries:
Total Peak RPS ≈ 35,000 RPS
```

### Step 4: Calculate Storage Requirements

```
Video storage (the BIG one):
- Average video length: 5 minutes
- Average bitrate: 1 Mbps (considering multiple resolutions)
- New videos uploaded per day:
  
  Assume 500 hours of video uploaded per minute
         = 500 × 60 hours per day
         = 30,000 hours per day
  
  Storage per day = 30,000 hours × 1 Mbps × 60 minutes
                  = 30,000 × 60 minutes × 1 Mbps
                  = 1,800,000 minutes × 1 Mbps
                  = 1,800,000 Mb = 225 GB per day
  
  Storage per year = 225 GB × 365 = ~82 TB per year
  
Cumulative (assuming YouTube has been around for ~15 years):
  Total video = 82 TB × 15 = 1,230 TB ≈ 1.2 PB (petabytes)
  
  With 3x replication (for availability):
  Total storage needed = 1.2 PB × 3 = 3.6 PB

Add metadata (comments, likes, thumbnails, descriptions):
  ~20% extra = 3.6 PB × 1.2 = 4.32 PB

Actual YouTube storage ≈ Several exabytes (EB) due to:
- Multiple bitrate versions (720p, 1080p, 4K, etc.)
- Backup copies
- CDN caches worldwide
```

### Step 5: Calculate Bandwidth / Network Throughput

```
Video streaming (the PRIMARY use case):

Peak concurrent viewers = 28,845 users
Average video bitrate = 1 Mbps (considering different resolutions/quality)

Bandwidth = 28,845 × 1 Mbps
          = 28,845 Mbps
          = ~28.8 Gbps (gigabits per second)

Add metadata, recommendations, ads:
  ~10% extra = 28.8 × 1.1 = ~31.7 Gbps

Accounting for non-peak and peak multiplier:
  Daytime average = 31.7 / 3 ≈ 10.6 Gbps (average)
  Peak = 31.7 Gbps (3x multiplier already applied)

YouTube actual bandwidth: Several petabits per second (PBps)
- Multiple CDNs worldwide
- Redundancy and load balancing
```

### Step 6: Server Count Estimation

```
Web/API servers:

RPS per server (typical web server):
- With HTTP/2, async processing: ~1,000 RPS per server
- With good caching, it could be higher

Servers needed for peak = Peak RPS / RPS per server
                       = 35,000 / 1,000
                       = 35 servers

With redundancy (3x):
Total web servers ≈ 35 × 3 = ~105 servers

Video streaming servers:

Concurrent video streams = 28,845
Connections per server = ~100-200 concurrent streams
Servers needed = 28,845 / 150 ≈ 192 servers

With redundancy (3x):
Total streaming servers ≈ 192 × 3 = ~576 servers

Cache/CDN edge servers:
- YouTube has edge caches in every major city
- Hundreds to thousands of edge locations worldwide

Database servers:

Metadata (users, videos, comments):
- Sharded across multiple databases
- Assume: 300 TB of metadata (small vs video storage)
- Database server capacity: ~1 TB
- Databases needed: 300
- With replication (3x): 300 × 3 = 900 database servers

Total Infrastructure Estimate:
- Web/API servers: 105
- Video streaming servers: 576
- Cache/Edge servers: 1,000+
- Database servers: 900
- Total: ~2,500+ servers (just for one data center!)
- Globally: 10,000+ servers across multiple data centers
```

### Step 7: Detailed Capacity Summary Table

| Component | Calculation | Result |
|-----------|------------|--------|
| **Daily Active Users** | Given | 500M |
| **Concurrent Users (Average)** | 500M / 86,400 | ~5,787 |
| **Concurrent Users (Peak)** | 5,787 × 3 | ~17,361 |
| **Peak RPS** | 17,361 × 1-2 | ~35,000 |
| **Video Storage (cumulative)** | 1.2 PB × 3 replication | ~3.6 PB |
| **Metadata Storage** | 300 TB × 3 replication | ~900 TB |
| **Total Storage** | 3.6 PB + 0.9 PB + backups | ~4-5 PB |
| **Bandwidth (Peak)** | 28,845 concurrent × 1 Mbps | ~30 Gbps |
| **Web Servers Needed** | 35,000 RPS / 1,000 RPS/server × 3x redundancy | ~105 |
| **Video Servers Needed** | 28,845 streams / 150 connections × 3x | ~576 |
| **Database Servers Needed** | (300 TB / 1 TB per server) × 3x | ~900 |

## Capacity Estimation Formula Cheat Sheet

### Traffic Estimation
```
Daily Active Users (DAU) → Given
Concurrent Users = DAU / 86,400

Peak Concurrent = Concurrent × Peak Multiplier (usually 2-3x)

Requests Per Second (RPS) = Peak Concurrent × Avg Requests/User/Sec
```

### Storage Estimation
```
Daily data generated = DAU × Data per User per Day
Yearly data = Daily data × 365
Cumulative = Years of service × Yearly data
With redundancy = Cumulative × Replication Factor (2-3x)
```

### Bandwidth Estimation
```
Internet Bandwidth = Peak Concurrent × Avg Response Size
Example: 10,000 users × 100 KB per request = 1,000 MB/s = 1 Gbps
```

### Server Count Estimation
```
Servers Needed = (Total RPS) / (RPS per Server) × (Redundancy Factor)
Example: 35,000 RPS / 1,000 RPS/server × 3 = 105 servers
```

### Database Server Estimation
```
DB Servers = (Total Data Size) / (Data per Server) × (Replication Factor)
Example: (300 TB) / (1 TB per server) × 3 = 900 DB servers
```

## Capacity Estimation Tips for Interviews

### 1. **Start with Numbers You Know**
- DAU / MAU from problem statement
- Average user behavior (requests per day)
- Data size (video length, file size)

### 2. **Back-of-the-Envelope Calculation**
```
"500M users per day
÷ 86,400 seconds
≈ 5,800 concurrent users
× 3x peak multiplier
≈ 17,400 concurrent users
× 2 requests per user
≈ 35,000 RPS"
```

### 3. **Break Down by Component**
- Web servers for API
- Database servers for storage
- Cache servers for hot data
- CDN for content delivery

### 4. **Account for Redundancy**
- 2x replication minimum (master + backup)
- 3x for high availability
- Geographic distribution

### 5. **Be Ready to Adjust**
```
Interviewer: "How would you reduce storage?"
You: "Compress videos, implement tiered storage,
     delete old/unpopular videos after N months"

Interviewer: "What if traffic doubles?"
You: "Add more servers (horizontal scaling),
     improve caching strategy, optimize queries"
```

### 6. **Order of Magnitude**
State assumptions clearly:
```
"Assuming:
- 500M DAU uniformly distributed (likely 3x peak)
- 5 minutes average viewing per session
- 1 Mbps average bitrate
- 3x replication for availability

Estimated: ~30 Gbps bandwidth, ~4 PB storage"
```

## Interview Quick-Fire Q&A

**Q: What is capacity estimation?**
Calculating how much infrastructure (servers, storage, bandwidth) needed for a given load.

**Q: How do you calculate concurrent users?**
DAU / 86,400 seconds. For peak, multiply by 2-3x.

**Q: How do you calculate RPS (requests per second)?**
Concurrent users × average requests per user per second.

**Q: YouTube stores 4.5 PB; how does it manage this?**
Sharding (split across servers), replication (3x copies), compression, CDN caching.

**Q: How do you reduce storage requirements?**
Compress videos, tiered storage (hot/warm/cold), delete old content, use derivatives.

**Q: What's the relationship between concurrent users and RPS?**
Concurrent users × requests/second per user = RPS.

**Q: Why do we assume 3x peak multiplier?**
Traffic during peak hours (8pm-11pm) typically 2-3x average; must design for peak.

**Q: How much redundancy to plan for?**
Minimum 2x (one backup), prefer 3x for critical systems, 5x for ultra-high availability.

## Key Takeaways

- **Capacity estimation** = translating user numbers to infrastructure needs.
- **Start with DAU** → calculate concurrent users → RPS → server count.
- **YouTube example:** 500M DAU → 17K concurrent users → 35K RPS → 105 web servers.
- **Always account for:**
  - Peak multiplier (2-3x)
  - Redundancy (2-3x replication)
  - Geographic distribution
  - Growth headroom
- **Storage is huge** for media platforms; prioritize compression and caching.
- **Bandwidth is precious**; design CDN first, then regional expansion.
- **Practice with real numbers** – internalize order of magnitude estimates.
