# Docker Image Creation

This guide covers two primary methods for creating Docker images: taking snapshots from existing containers and building images using Dockerfiles.

---

## Method 1: Creating Images from Container Snapshots

### Overview
You can create a new image by committing the changes made to a running container. This is useful for:
- Quick prototyping
- Capturing manual configurations
- Creating backups of container states

### Step-by-Step Process

#### 1. Start with a Base Container
```bash
docker run -it --name mycontainer ubuntu:latest /bin/bash
```

#### 2. Make Changes Inside the Container
```bash
# Inside the container
apt-get update
apt-get install -y nginx
apt-get install -y python3
# Make any other customizations
exit
```

#### 3. Commit the Container as an Image
```bash
docker commit [OPTIONS] CONTAINER_ID NEW_IMAGE_NAME:TAG
```

**Example:**
```bash
docker commit mycontainer myapp:v1.0
```

**Common Options:**
- `-a "Author Name"` - Specify the author
- `-m "Commit message"` - Add a commit message
- `-c` - Apply Dockerfile instructions

**Full Example:**
```bash
docker commit -a "John Doe" -m "Added nginx and python3" mycontainer myapp:v1.0
```

#### 4. Verify the New Image
```bash
docker images
```

#### 5. Run Container from New Image
```bash
docker run -it myapp:v1.0 /bin/bash
```

### Pros and Cons

**✅ Advantages:**
- Quick and simple
- Useful for experimentation
- No Dockerfile needed

**❌ Disadvantages:**
- Not reproducible
- No version control
- Manual process
- Difficult to maintain
- Image history is unclear

## Method 2: Creating Images with Dockerfile (Recommended)

### Overview
A Dockerfile is a text file containing instructions to build a Docker image automatically. This is the **recommended approach** for production environments.

### Basic Dockerfile Structure

```dockerfile
# Comment
INSTRUCTION arguments
```

---

## Dockerfile Instructions Reference

### 1. FROM
**Purpose:** Specifies the base image for your build.

**Syntax:**
```dockerfile
FROM image_name:tag
```

**Example:**
```dockerfile
FROM ubuntu:22.04
FROM node:18-alpine
FROM python:3.11-slim
```

**Notes:**
- Must be the first instruction (except comments and ARG for build-time variables)
- Every Dockerfile must have a FROM instruction
- Use specific tags instead of `latest` for reproducibility

---

### 2. LABEL
**Purpose:** Adds metadata to the image (maintainer, version, description).

**Syntax:**
```dockerfile
LABEL key="value"
```

**Example:**
```dockerfile
LABEL maintainer="john@example.com"
LABEL version="1.0"
LABEL description="My web application"
```

---

### 3. RUN
**Purpose:** Executes commands during image build time.

**Syntax:**
```dockerfile
RUN command
RUN ["executable", "param1", "param2"]  # exec form
```

**Example:**
```dockerfile
RUN apt-get update && apt-get install -y \
    nginx \
    curl \
    vim \
    && rm -rf /var/lib/apt/lists/*

RUN pip install flask requests pandas
RUN npm install express
```

**Best Practices:**
- Chain commands with `&&` to reduce layers
- Clean up package manager cache in the same RUN command
- Use `\` for multi-line commands

---

### 4. CMD
**Purpose:** Specifies the default command to run when container starts.

**Syntax:**
```dockerfile
CMD ["executable", "param1", "param2"]  # exec form (recommended)
CMD command param1 param2              # shell form
```

**Example:**
```dockerfile
CMD ["nginx", "-g", "daemon off;"]
CMD ["python", "app.py"]
CMD ["node", "server.js"]
```

**Important:**
- Only the last CMD instruction takes effect
- Can be overridden at runtime with `docker run`
- Difference from ENTRYPOINT: CMD can be fully replaced

---

### 5. ENTRYPOINT
**Purpose:** Configures the container to run as an executable.

**Syntax:**
```dockerfile
ENTRYPOINT ["executable", "param1", "param2"]  # exec form
ENTRYPOINT command param1 param2              # shell form
```

**Example:**
```dockerfile
ENTRYPOINT ["python", "app.py"]
ENTRYPOINT ["nginx", "-g", "daemon off;"]
```

**CMD + ENTRYPOINT Together:**
```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
# Result: python app.py (CMD provides default arguments to ENTRYPOINT)
```

**Difference from CMD:**
- ENTRYPOINT is harder to override (requires `--entrypoint` flag)
- Best for containers that should run as executables

---

### 6. COPY
**Purpose:** Copies files/directories from host to container filesystem.

**Syntax:**
```dockerfile
COPY <src> <dest>
COPY ["<src>", "<dest>"]  # Use for paths with spaces
```

**Example:**
```dockerfile
COPY package.json /app/
COPY . /app
COPY requirements.txt /usr/src/app/
COPY ["my file.txt", "/app/"]  # For filenames with spaces
```

**Notes:**
- Source path is relative to build context
- Creates destination directory if it doesn't exist
- Preserves file metadata

---

### 7. ADD
**Purpose:** Similar to COPY, but with additional features.

**Syntax:**
```dockerfile
ADD <src> <dest>
```

**Example:**
```dockerfile
ADD app.tar.gz /app/  # Automatically extracts tar files
ADD https://example.com/file.txt /app/  # Can download from URLs
```

**When to Use:**
- Use COPY for simple file copying (recommended)
- Use ADD only when you need auto-extraction or URL download

---

### 8. WORKDIR
**Purpose:** Sets the working directory for subsequent instructions.

**Syntax:**
```dockerfile
WORKDIR /path/to/directory
```

**Example:**
```dockerfile
WORKDIR /app
COPY . .
RUN npm install
```

**Notes:**
- Creates directory if it doesn't exist
- Affects RUN, CMD, ENTRYPOINT, COPY, and ADD instructions
- Can be used multiple times

---

### 9. ENV
**Purpose:** Sets environment variables.

**Syntax:**
```dockerfile
ENV key=value
ENV key1=value1 key2=value2
```

**Example:**
```dockerfile
ENV NODE_ENV=production
ENV APP_HOME=/app PORT=8080
ENV PYTHONUNBUFFERED=1
```

**Notes:**
- Available during build and runtime
- Can be overridden with `docker run -e`

---

### 10. ARG
**Purpose:** Defines build-time variables.

**Syntax:**
```dockerfile
ARG variable_name
ARG variable_name=default_value
```

**Example:**
```dockerfile
ARG VERSION=1.0
ARG BUILD_DATE
RUN echo "Building version ${VERSION}"
```

**Usage:**
```bash
docker build --build-arg VERSION=2.0 -t myapp .
```

**Difference from ENV:**
- ARG is only available during build
- ENV persists in the container at runtime

---

### 11. EXPOSE
**Purpose:** Documents which ports the container listens on.

**Syntax:**
```dockerfile
EXPOSE port [port/protocol...]
```

**Example:**
```dockerfile
EXPOSE 80
EXPOSE 443
EXPOSE 8080/tcp
EXPOSE 53/udp
```

**Notes:**
- Does NOT actually publish the port
- Use `-p` flag in `docker run` to publish ports
- Serves as documentation

---

### 12. VOLUME
**Purpose:** Creates a mount point for persistent data.

**Syntax:**
```dockerfile
VOLUME ["/path/to/volume"]
VOLUME /path/to/volume
```

**Example:**
```dockerfile
VOLUME ["/data"]
VOLUME /var/log /var/db
```

**Notes:**
- Data persists beyond container lifecycle
- Can be shared between containers

---

### 13. USER
**Purpose:** Sets the user (and optionally user group) to use.

**Syntax:**
```dockerfile
USER username[:groupname]
USER UID[:GID]
```

**Example:**
```dockerfile
RUN useradd -m appuser
USER appuser
WORKDIR /home/appuser
```

**Security Best Practice:**
- Don't run containers as root
- Create and switch to non-privileged user

---

### 14. SHELL
**Purpose:** Overrides the default shell used for commands.

**Syntax:**
```dockerfile
SHELL ["executable", "parameters"]
```

**Example:**
```dockerfile
SHELL ["/bin/bash", "-c"]
SHELL ["powershell", "-command"]  # For Windows containers
```

---

### 15. HEALTHCHECK
**Purpose:** Tells Docker how to test if container is healthy.

**Syntax:**
```dockerfile
HEALTHCHECK [OPTIONS] CMD command
```

**Example:**
```dockerfile
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost/ || exit 1

HEALTHCHECK CMD wget --quiet --tries=1 --spider http://localhost:8080/health || exit 1
```

**Options:**
- `--interval=DURATION` (default: 30s)
- `--timeout=DURATION` (default: 30s)
- `--start-period=DURATION` (default: 0s)
- `--retries=N` (default: 3)

---

### 16. ONBUILD
**Purpose:** Adds trigger instructions for child images.

**Syntax:**
```dockerfile
ONBUILD instruction
```

**Example:**
```dockerfile
ONBUILD COPY . /app
ONBUILD RUN npm install
```

**Notes:**
- Executes when image is used as base for another build
- Useful for creating reusable base images

## Complete Dockerfile Example

### Example 1: Node.js Application

```dockerfile
# Use official Node.js runtime as base image
FROM node:18-alpine

# Set metadata
LABEL maintainer="developer@example.com"
LABEL version="1.0"
LABEL description="Node.js web application"

# Create app directory
WORKDIR /usr/src/app

# Copy package files
COPY package*.json ./

# Install dependencies
RUN npm ci --only=production

# Copy application source
COPY . .

# Create non-root user
RUN addgroup -g 1001 appgroup && \
    adduser -D -u 1001 -G appgroup appuser

# Change ownership
RUN chown -R appuser:appgroup /usr/src/app

# Switch to non-root user
USER appuser

# Expose port
EXPOSE 3000

# Define environment variable
ENV NODE_ENV=production

# Health check
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s \
  CMD node healthcheck.js || exit 1

# Run application
CMD ["node", "server.js"]
```

### Example 2: Python Flask Application

```dockerfile
# Base image
FROM python:3.11-slim

# Set working directory
WORKDIR /app

# Set environment variables
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# Install system dependencies
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    && rm -rf /var/lib/apt/lists/*

# Copy requirements and install Python dependencies
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Create non-root user
RUN useradd -m -u 1000 appuser && chown -R appuser:appuser /app
USER appuser

# Expose port
EXPOSE 5000

# Run the application
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]
```

## Building and Running Images from Dockerfile

### Build the Image
```bash
# Basic build
docker build -t myapp:1.0 .

# Build with custom Dockerfile name
docker build -t myapp:1.0 -f Dockerfile.prod .

# Build with build arguments
docker build --build-arg VERSION=2.0 -t myapp:2.0 .

# Build without cache
docker build --no-cache -t myapp:1.0 .
```

### Run the Container
```bash
# Run with port mapping
docker run -d -p 8080:3000 --name myapp-container myapp:1.0

# Run with environment variables
docker run -d -e DATABASE_URL=postgres://... myapp:1.0

# Run with volume mounting
docker run -d -v /host/path:/container/path myapp:1.0
```

## Best Practices

### 1. Use .dockerignore File
Create a `.dockerignore` file to exclude unnecessary files:

```
node_modules
npm-debug.log
.git
.gitignore
.env
*.md
Dockerfile
.dockerignore
```

### 2. Multi-stage Builds
Reduce image size by using multi-stage builds:

```dockerfile
# Build stage
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# Production stage
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY package*.json ./
RUN npm ci --only=production
CMD ["node", "dist/server.js"]
```

### 3. Minimize Layers
- Combine RUN commands with `&&`
- Order instructions from least to most frequently changing
- Clean up in the same layer

### 4. Use Specific Tags
```dockerfile
# Bad
FROM node:latest

# Good
FROM node:18.16.0-alpine
```

### 5. Security Best Practices
- Don't run as root
- Scan images for vulnerabilities
- Use minimal base images (alpine, slim)
- Don't include secrets in images
- Keep images updated

## Comparison: Snapshot vs Dockerfile

| Aspect | Container Snapshot | Dockerfile |
|--------|-------------------|------------|
| **Reproducibility** | ❌ Low | ✅ High |
| **Version Control** | ❌ Difficult | ✅ Easy |
| **Documentation** | ❌ Poor | ✅ Excellent |
| **Automation** | ❌ Manual | ✅ Automated |
| **Best For** | Quick experiments | Production use |
| **Maintainability** | ❌ Hard | ✅ Easy |
| **Size Optimization** | ❌ Difficult | ✅ Easy |
| **Collaboration** | ❌ Difficult | ✅ Easy |

## Quick Reference Commands

```bash
# Build image from Dockerfile
docker build -t image_name:tag .

# Build with no cache
docker build --no-cache -t image_name:tag .

# Commit container to image
docker commit container_id image_name:tag

# Tag an image
docker tag source_image:tag target_image:tag

# Push image to registry
docker push registry/image_name:tag

# View image history
docker history image_name:tag

# Inspect image details
docker inspect image_name:tag

# Remove image
docker rmi image_name:tag
```

---

**Recommendation:** Always use Dockerfiles for production images. Container snapshots are useful only for quick testing and experimentation.
