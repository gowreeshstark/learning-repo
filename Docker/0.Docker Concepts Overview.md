## Core Concepts

### Fundamental Understanding

#### Containerization
- Lightweight virtualization technology that packages applications with their dependencies
- Provides consistent behavior across different environments
- More efficient than traditional virtual machines

#### Docker Architecture
- **Docker Client** - Command-line interface for interacting with Docker
- **Docker Daemon (dockerd)** - Background service managing containers
- **Docker REST API** - Interface between client and daemon
- Client-server architecture enabling remote management

#### Docker Engine
- Core runtime and tooling for building and running containers
- Consists of:
  - Server (daemon process)
  - REST API
  - CLI (command-line interface)

#### Container vs Virtual Machine

| Aspect | Containers | Virtual Machines |
|--------|-----------|------------------|
| **Size** | Lightweight (MB) | Heavy (GB) |
| **Startup** | Seconds | Minutes |
| **Isolation** | Process-level | Hardware-level |
| **OS** | Shares host kernel | Full OS per VM |
| **Resource Usage** | Efficient | Resource-intensive |
| **Portability** | Highly portable | Less portable |

#### Isolation
- **Process Isolation** - Each container runs in its own process space
- **Filesystem Isolation** - Containers have their own filesystem
- **Network Isolation** - Separate network namespaces
- **Resource Isolation** - CPU, memory, and I/O limits

## Images

### Docker Images
- **Read-only templates** containing everything needed to run an application
- Composed of multiple layers stacked on top of each other
- Used as the basis for creating containers
- Immutable once built

### Image Layers
- Each Dockerfile instruction creates a new layer
- Layers are cached for faster builds
- Only changed layers need to be rebuilt
- Layers are shared between images to save space

### Base Images
- Starting point for building custom images
- Common base images:
  - **Alpine** - Minimal size (~5MB)
  - **Ubuntu** - Full-featured Debian-based
  - **Debian** - Stable and reliable
  - **Scratch** - Empty base for static binaries
  - **Official language images** - Node, Python, Java, etc.

### Image Registry
- **DockerHub** - Public registry with millions of images
- **Private Registries** - Self-hosted or cloud-based
- **Amazon ECR** - AWS Elastic Container Registry
- **Google GCR** - Google Container Registry
- **Azure ACR** - Azure Container Registry

### Image Tags
- Version identifiers for images (e.g., `nginx:1.21.0`)
- **latest** - Points to most recent version (avoid in production)
- **Semantic versioning** - major.minor.patch format
- Multiple tags can point to same image

### Image Optimization
- Use minimal base images (alpine, slim)
- Minimize number of layers
- Combine RUN commands
- Remove unnecessary files in same layer
- Use multi-stage builds
- Leverage build cache

### Multi-stage Builds
```dockerfile
# Build stage
FROM node:18 AS builder
WORKDIR /app
COPY . .
RUN npm install && npm run build

# Production stage
FROM node:18-alpine
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/server.js"]
```

### Image Security
- Scan for vulnerabilities regularly
- Use trusted base images
- Keep images updated
- Don't include secrets in images
- Run as non-root user
- Use minimal attack surface

## Containers

### Container Lifecycle

```
CREATE → START → RUNNING → STOP → REMOVE
                    ↓
                 PAUSE/UNPAUSE
```

**Lifecycle Commands:**
```bash
docker create    # Create but don't start
docker start     # Start existing container
docker stop      # Gracefully stop (SIGTERM)
docker kill      # Force stop (SIGKILL)
docker restart   # Stop and start
docker pause     # Pause processes
docker unpause   # Resume processes
docker rm        # Remove stopped container
```

### Container States
- **Created** - Container exists but not started
- **Running** - Container is actively running
- **Paused** - Processes are suspended
- **Stopped** - Container has exited
- **Dead** - Container failed to remove properly

### Container Processes
- **PID 1** - Main process that runs in container
- If PID 1 exits, container stops
- **Foreground** - Interactive processes (with `-it`)
- **Background** - Detached mode (with `-d`)

### Container Logs
```bash
docker logs CONTAINER_ID           # View logs
docker logs -f CONTAINER_ID        # Follow logs
docker logs --tail 100 CONTAINER_ID # Last 100 lines
docker logs --since 1h CONTAINER_ID # Last hour
```

### Container Exec
```bash
docker exec CONTAINER_ID command         # Run command
docker exec -it CONTAINER_ID bash        # Interactive shell
docker exec -u root CONTAINER_ID command # Run as root
```

### Container Inspection
```bash
docker inspect CONTAINER_ID      # Full details in JSON
docker inspect --format '{{.State.Status}}' CONTAINER_ID
docker top CONTAINER_ID          # Running processes
docker port CONTAINER_ID         # Port mappings
```

### Container Resource Limits
```bash
# CPU limits
docker run --cpus="1.5" IMAGE
docker run --cpu-shares=512 IMAGE

# Memory limits
docker run -m 512m IMAGE
docker run --memory-swap 1g IMAGE

# I/O limits
docker run --device-read-bps /dev/sda:1mb IMAGE
```

### Container Restart Policies
```bash
docker run --restart=no IMAGE           # Never restart
docker run --restart=on-failure IMAGE   # Restart on error
docker run --restart=always IMAGE       # Always restart
docker run --restart=unless-stopped IMAGE
```

## Dockerfile

### Dockerfile Instructions

All major instructions covered in detail:

#### Essential Instructions
- **FROM** - Base image
- **RUN** - Execute commands during build
- **CMD** - Default command when container starts
- **ENTRYPOINT** - Configure container as executable
- **COPY** - Copy files from host to image
- **ADD** - Copy with URL support and auto-extraction
- **WORKDIR** - Set working directory
- **ENV** - Set environment variables
- **ARG** - Build-time variables
- **EXPOSE** - Document ports
- **VOLUME** - Create mount points
- **USER** - Set user/group
- **LABEL** - Add metadata

#### Advanced Instructions
- **SHELL** - Override default shell
- **HEALTHCHECK** - Container health monitoring
- **ONBUILD** - Trigger for child images
- **STOPSIGNAL** - Signal to stop container

### Build Context
- Directory sent to Docker daemon during build
- Contains Dockerfile and files to COPY/ADD
- Use `.dockerignore` to exclude files
- Keep context small for faster builds

### Layer Caching
- Docker caches each layer after build
- If instruction unchanged, cached layer is used
- Cache invalidates if any instruction changes
- Order instructions from least to most frequently changing

### .dockerignore File
```
# Dependencies
node_modules/
vendor/

# Build outputs
dist/
build/
*.o

# Version control
.git/
.gitignore

# Secrets and configs
.env
*.pem
*.key

# Documentation
README.md
docs/

# Development files
Dockerfile*
docker-compose*.yml
```

### Build Arguments (ARG)
- Available only during build time
- Can be passed with `--build-arg`
- Not persisted in final image
```dockerfile
ARG VERSION=latest
FROM node:${VERSION}
ARG BUILD_DATE
LABEL build_date=${BUILD_DATE}
```

### Environment Variables (ENV)
- Available during build AND runtime
- Persisted in final image
- Can be overridden with `docker run -e`
```dockerfile
ENV NODE_ENV=production
ENV PORT=3000
```

### ENTRYPOINT vs CMD

**Key Differences:**

| Aspect | CMD | ENTRYPOINT |
|--------|-----|------------|
| **Override** | Easy (just add args) | Hard (needs `--entrypoint`) |
| **Purpose** | Default command | Container executable |
| **Arguments** | Can provide defaults | Receives all args |
| **Best For** | Flexible commands | Fixed executables |

**Combined Usage:**
```dockerfile
ENTRYPOINT ["python"]
CMD ["app.py"]
# Result: python app.py
# Can override: docker run image script.py → python script.py
```

## Networking

### Network Types

#### Bridge Network (Default)
- Default network for containers
- Isolated network on host
- Containers can communicate via IP
- Need port publishing for external access

#### Host Network
```bash
docker run --network=host IMAGE
```
- Container shares host's network
- No network isolation
- Better performance
- Port conflicts with host

#### Overlay Network
- Multi-host networking
- Used in Swarm/Kubernetes
- Containers on different hosts communicate
- Requires key-value store

#### Macvlan Network
- Assigns MAC address to container
- Container appears as physical device
- Direct connection to physical network

#### None Network
```bash
docker run --network=none IMAGE
```
- No networking
- Complete isolation
- For maximum security

### Container-to-Container Communication

**Using Container Names:**
```bash
docker network create mynet
docker run --network=mynet --name=app1 nginx
docker run --network=mynet --name=app2 alpine ping app1
```

### Port Mapping
```bash
# Single port
docker run -p 8080:80 IMAGE

# Multiple ports
docker run -p 8080:80 -p 443:443 IMAGE

# All exposed ports
docker run -P IMAGE

# Specific IP
docker run -p 127.0.0.1:8080:80 IMAGE

# UDP ports
docker run -p 53:53/udp IMAGE
```

### DNS Resolution
- Automatic DNS for user-defined networks
- Containers discover each other by name
- Built-in DNS server (127.0.0.11)
- Supports service discovery

### Custom Networks
```bash
# Create network
docker network create --driver bridge mynetwork

# Create with subnet
docker network create --subnet=172.18.0.0/16 mynetwork

# Connect container
docker network connect mynetwork container1

# Disconnect
docker network disconnect mynetwork container1

# Inspect
docker network inspect mynetwork
```

## Storage & Volumes

### Volume Types

#### Named Volumes
```bash
# Create
docker volume create mydata

# Use
docker run -v mydata:/app/data IMAGE

# List
docker volume ls

# Inspect
docker volume inspect mydata

# Remove
docker volume rm mydata
```

**Characteristics:**
- Managed by Docker
- Stored in `/var/lib/docker/volumes/`
- Best for production
- Can be shared between containers

#### Bind Mounts
```bash
docker run -v /host/path:/container/path IMAGE
docker run -v "$(pwd)":/app IMAGE  # Current directory
```

**Characteristics:**
- Direct mapping to host filesystem
- Full path required
- Good for development
- Host changes reflected immediately

#### tmpfs Mounts
```bash
docker run --tmpfs /app/temp IMAGE
docker run --mount type=tmpfs,destination=/app/temp IMAGE
```

**Characteristics:**
- Stored in host memory
- Not persisted to disk
- Fast but temporary
- Good for sensitive data

### Data Persistence
- Volumes outlive containers
- Data survives container deletion
- Can be backed up and restored
- Enable data sharing

### Volume Management Best Practices
- Use named volumes for production data
- Use bind mounts for development
- Back up important volumes regularly
- Use volume drivers for cloud storage
- Clean up unused volumes

### Volume Drivers
- **local** - Default driver
- **nfs** - Network File System
- **cifs** - SMB/CIFS shares
- **Third-party** - AWS EFS, GlusterFS, etc.

## Docker Compose

### docker-compose.yml Structure

```yaml
version: '3.8'

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html
    networks:
      - frontend
    environment:
      - ENV_VAR=value
    depends_on:
      - api
    restart: always

  api:
    build: ./api
    ports:
      - "3000:3000"
    volumes:
      - api-data:/app/data
    networks:
      - frontend
      - backend
    env_file:
      - .env

  db:
    image: postgres:14
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - backend
    environment:
      POSTGRES_PASSWORD: secret

volumes:
  api-data:
  db-data:

networks:
  frontend:
  backend:
```

### Services
- Each service is a container definition
- Can use image or build
- Supports all Docker run options
- Automatic service discovery by name

### Networks in Compose
- Creates default network for all services
- Services can communicate using service names
- Can define multiple custom networks
- Control service connectivity

### Volumes in Compose
- Named volumes defined at top level
- Reused across services
- Persisted between deployments

### Environment Variables
```yaml
# Inline
environment:
  - NODE_ENV=production
  - PORT=3000

# From file
env_file:
  - .env
  - .env.local

# Variable substitution
environment:
  - DATABASE_URL=${DB_URL}
```

### Dependencies (depends_on)
```yaml
services:
  web:
    depends_on:
      - db
      - cache
```
- Controls startup order
- Does NOT wait for service to be "ready"
- Use health checks for readiness

### Scaling Services
```bash
docker-compose up --scale web=3
```

### Override Files
- `docker-compose.yml` - Base configuration
- `docker-compose.override.yml` - Auto-merged overrides
- `docker-compose.prod.yml` - Production config
```bash
docker-compose -f docker-compose.yml -f docker-compose.prod.yml up
```

```

```

docker.io/library/ubuntu:22.04       # Full DockerHub path

## Container Orchestration

### Docker Swarm
- Native Docker clustering solution
- Built into Docker Engine
- Easy setup and management
- Good for simple orchestration needs

**Key Concepts:**
- **Nodes** - Swarm members (managers + workers)
- **Services** - Desired state of application
- **Tasks** - Individual container instances
- **Stack** - Multi-service applications

**Basic Commands:**
```bash
# Initialize swarm
docker swarm init

# Add worker
docker swarm join --token TOKEN

# Deploy service
docker service create --replicas 3 --name web nginx

# Scale service
docker service scale web=5

# Deploy stack
docker stack deploy -c docker-compose.yml myapp
```

### Kubernetes Integration
- Industry standard for orchestration
- More complex but more powerful
- Docker containers run in pods
- Extensive ecosystem

### Service Discovery
- Automatic DNS-based discovery
- Load balancing across replicas
- Health checking
- Dynamic updates

### Load Balancing
- Automatic load distribution
- Round-robin by default
- Session affinity support
- External and internal load balancing

### Rolling Updates
```bash
docker service update --image nginx:1.21 web
```
- Zero-downtime deployments
- Gradual rollout
- Automatic rollback on failure
- Configurable update parameters

### Scaling
```bash
# Manual scaling
docker service scale web=10

# Auto-scaling (with external tools)
# Based on CPU, memory, or custom metrics
```

## Security

### Container Isolation
- **Namespaces** - Process, network, mount isolation
- **Cgroups** - Resource limiting
- **Capabilities** - Fine-grained permissions
- Not as strong as VM isolation

### User Namespaces
```bash
# Run as non-root user
docker run --user 1000:1000 IMAGE

# Create user in Dockerfile
RUN useradd -m appuser
USER appuser
```

### AppArmor / SELinux
- Mandatory Access Control (MAC)
- Restrict container capabilities
- Define security policies
```bash
docker run --security-opt apparmor=docker-default IMAGE
```

### Seccomp
- System call filtering
- Limits syscalls container can make
- Default profile blocks dangerous calls
```bash
docker run --security-opt seccomp=profile.json IMAGE
```

### Docker Content Trust
```bash
# Enable content trust
export DOCKER_CONTENT_TRUST=1

# Images must be signed
docker pull nginx  # Verifies signature
```

### Security Scanning
```bash
# Scan with Docker Scout
docker scout cves IMAGE

# Third-party tools
trivy image IMAGE
grype IMAGE
clair-scanner IMAGE
```

### Secrets Management
```bash
# Docker Swarm secrets
echo "mysecret" | docker secret create db_password -

# Use in service
docker service create --secret db_password IMAGE

# Kubernetes secrets
kubectl create secret generic db-password --from-literal=password=secret
```

### Resource Constraints
```bash
docker run --memory=512m --cpus=1 IMAGE
```
- Prevents resource exhaustion
- Protects host system
- Limits impact of compromised containers

### Read-only Filesystems
```bash
docker run --read-only IMAGE
docker run --read-only --tmpfs /tmp IMAGE
```

### Network Security
- Use custom networks
- Minimize exposed ports
- Enable encrypted overlay networks
- Use network policies (Kubernetes)

## Best Practices

### One Process Per Container
- Single responsibility principle
- Easier to scale individual components
- Better resource management
- Simpler debugging

### Immutable Infrastructure
- Containers are disposable
- Never modify running containers
- Rebuild and redeploy instead
- Configuration via environment variables

### Configuration Management
- Externalize configuration
- Use environment variables
- Config files via volumes
- Never hardcode secrets

### Small Base Images
```dockerfile
# Good
FROM alpine:3.18
FROM node:18-alpine
FROM python:3.11-slim

# Avoid
FROM ubuntu:latest
FROM node:18
```

### Layer Optimization
```dockerfile
# Bad - Multiple layers
RUN apt-get update
RUN apt-get install -y nginx
RUN apt-get clean

# Good - Single layer
RUN apt-get update && \
    apt-get install -y nginx && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*
```

### Order Instructions Properly
```dockerfile
# Place least frequently changing instructions first
FROM node:18-alpine
WORKDIR /app

# Dependencies (cached if package.json unchanged)
COPY package*.json ./
RUN npm ci

# Source code (changes frequently)
COPY . .

# Runtime
CMD ["node", "server.js"]
```

### CI/CD Integration
- Automated builds on commits
- Run tests in containers
- Scan for vulnerabilities
- Automated deployment
- Version tagging

### Version Pinning
```dockerfile
# Bad - unpredictable
FROM node:latest
RUN npm install express

# Good - reproducible
FROM node:18.16.0-alpine
RUN npm install express@4.18.2
```

### Documentation
- **README** - Setup and usage instructions
- **Labels** - Metadata in Dockerfile
- **Comments** - Explain complex instructions
```dockerfile

LABEL version="1.0"
LABEL description="Application description"
```

### Testing Strategies
- Unit tests during build
- Integration tests with Docker Compose
- E2E tests in containers
- Security scanning
- Performance testing

## Performance

### Image Optimization Techniques

**1. Use Multi-stage Builds:**
```dockerfile
FROM node:18 AS builder
COPY . .
RUN npm install && npm run build

FROM node:18-alpine
COPY --from=builder /app/dist ./dist
RUN npm ci --only=production
```

**2. Minimize Layers:**
- Combine RUN commands
- Clean up in same layer
- Use .dockerignore

**3. Leverage Build Cache:**
- Order from least to most frequently changing
- Copy dependencies before source code

**4. Choose Appropriate Base:**
- Alpine for minimal size
- Slim for balance
- Full only when necessary

### Build Cache
- Docker caches each layer
- Reuses unchanged layers
- Significantly faster rebuilds
- Invalidated by any change in instruction or files

### Storage Drivers
- **overlay2** - Recommended, default on most systems
- **aufs** - Older, compatibility
- **devicemapper** - RHEL/CentOS
- **btrfs** - Advanced features
- **zfs** - High performance

**Check driver:**
```bash
docker info | grep "Storage Driver"
```

### CPU and Memory Management

**Set Limits:**
```bash
# CPU
docker run --cpus="2" IMAGE          # 2 CPUs
docker run --cpu-shares=512 IMAGE    # Relative weight

# Memory
docker run -m 1g IMAGE               # 1GB limit
docker run --memory-swap 2g IMAGE    # Swap limit
docker run --oom-kill-disable IMAGE  # Disable OOM killer
```

**Monitor Usage:**
```bash
docker stats --no-stream
```

### Network Performance

**Host Network:**
- Best performance
- No network translation
- Direct host network access
```bash
docker run --network=host IMAGE
```

**Bridge Network:**
- Default, good balance
- Some overhead from NAT
- Isolated from host

**Overlay Network:**
- Multi-host networking
- More overhead
- Required for orchestration

### Filesystem Performance
- **Bind mounts** - Fast, direct access
- **Named volumes** - Good performance, managed by Docker
- **tmpfs** - Fastest, in-memory
