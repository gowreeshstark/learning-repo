## Beginner Level Questions

### Q1: What is Docker? Explain its benefits.

**Answer:**

Docker is a containerization platform that packages applications and their dependencies into isolated containers. These containers run consistently across different environments.

**Benefits:**
- **Lightweight** - Containers use fewer resources than VMs
- **Fast Startup** - Containers start in milliseconds
- **Portability** - Run anywhere - dev, test, production
- **Consistency** - "It works on my machine" problem solved
- **Scalability** - Easy horizontal scaling
- **Isolation** - Applications don't interfere with each other
- **Faster Development** - Quick deployment cycles
- **Cost Effective** - Better resource utilization

**Real-world analogy:**
```
Traditional shipping: Different containers for different cargo types
Docker shipping: Standardized containers that work anywhere
```

### Q2: What is the difference between Docker Image and Docker Container?

**Answer:**

| Aspect | Image | Container |
|--------|-------|-----------|
| **Definition** | Blueprint/template | Running instance |
| **State** | Static, immutable | Dynamic, mutable |
| **Creation** | Built from Dockerfile | Created from image |
| **Storage** | Stored on disk/registry | Runs in memory |
| **Persistence** | Persistent | Temporary (unless volumes used) |
| **Size** | Smaller | Larger (runtime overhead) |
| **Analogy** | Movie template | Playing the movie |

**Example:**
```bash
# Image - like a recipe
docker images  # Lists all images

# Container - like cooked food
docker run image-name  # Creates and runs a container
docker ps  # Lists running containers
```

**Diagram:**
```
Dockerfile → Build → Image → Run → Container
  (recipe)  (compile)  (file)  (execute)  (process)
```

### Q3: What is a Dockerfile? Explain the most common instructions.

**Answer:**

A Dockerfile is a text file containing instructions to build a Docker image.

**Common Instructions:**

```dockerfile
# Base image
FROM ubuntu:20.04

# Set working directory
WORKDIR /app

# Copy files
COPY source destination

# Run commands during build
RUN apt-get update && apt-get install -y python3

# Set environment variables
ENV key=value

# Expose port info (not actually open)
EXPOSE 8080

# Set the command to run
CMD ["python3", "app.py"]

# Entry point - default executable
ENTRYPOINT ["python3"]

# Create volume mount point
VOLUME ["/data"]

# Add metadata
LABEL maintainer="email@example.com"

# Add user
USER appuser

# Health check
HEALTHCHECK CMD curl -f http://localhost || exit 1
```

**Key Differences:**
- `CMD` - Default command, can be overridden
- `ENTRYPOINT` - Configure container to run as executable, harder to override
- `RUN` - Execute during build
- `COPY/ADD` - Add files during build

### Q5: How do you reduce Docker image size?

**Answer:**

**Strategies:**

1. **Use Alpine Linux** (5MB vs 100MB+)
   ```dockerfile
   # ✗ Large (100+ MB)
   FROM ubuntu:20.04
   
   # ✓ Small (5 MB)
   FROM alpine:3.14
   ```

2. **Multi-stage Builds**
   ```dockerfile
   # Stage 1: Build
   FROM golang:1.16 as builder
   COPY . /app
   WORKDIR /app
   RUN go build -o app
   
   # Stage 2: Runtime (smaller)
   FROM alpine:3.14
   COPY --from=builder /app/app /app
   CMD ["/app"]
   ```

3. **Minimize Layers**
   ```dockerfile
   # ✗ Creates multiple layers
   RUN apt-get update
   RUN apt-get install -y package1
   RUN apt-get install -y package2
   RUN apt-get clean
   
   # ✓ Single layer
   RUN apt-get update && \
       apt-get install -y package1 package2 && \
       apt-get clean && \
       rm -rf /var/lib/apt/lists/*
   ```

4. **Use .dockerignore**
   ```
   node_modules
   .git
   .env
   *.log
   ```

5. **Remove Unnecessary Files**
   ```dockerfile
   RUN apt-get clean && \
       rm -rf /var/lib/apt/lists/* /tmp/* /var/tmp/*
   ```

**Size Comparison:**
```
Full Ubuntu image: 77 MB
Alpine Linux: 5 MB
Python slim: 43 MB
Node.js alpine: 100 MB
```

## Intermediate Level Questions

### Q6: Explain Docker Volumes and their types.

**Answer:**

Docker Volumes are mechanisms to persist data beyond container lifecycle.

**Three Types:**

#### 1. **Named Volumes**
```bash
# Create named volume
docker volume create my-volume

# Use in container
docker run -v my-volume:/app/data ubuntu

# List volumes
docker volume ls

# Inspect volume
docker volume inspect my-volume
```
- Managed by Docker
- Stored in `/var/lib/docker/volumes/`
- Recommended for production
- Easy to backup

#### 2. **Bind Mounts**
```bash
# Mount local directory
docker run -v /host/path:/container/path ubuntu

# Read-only bind mount
docker run -v /host/path:/container/path:ro ubuntu
```
- Map host directory to container
- Full host path required
- Performance depends on OS
- Useful for development

#### 3. **tmpfs Mounts**
```bash
# Temporary in-memory storage
docker run --tmpfs /tmp ubuntu
```
- Only in memory, not on disk
- Lost when container stops
- Fast, useful for caching
- Cannot be shared

**Comparison Table:**

| Aspect | Named Volume | Bind Mount | tmpfs |
|--------|-------------|-----------|-------|
| **Lifecycle** | Persistent | Persistent | Temporary |
| **Storage** | Docker managed | Host filesystem | Memory |
| **Performance** | Good | Depends on OS | Excellent |
| **Portability** | High | Low | N/A |
| **Use Case** | Production DB | Development | Cache/temp |

**Real Example:**
```yaml
version: '3.8'
services:
  mysql:
    image: mysql:8.0
    volumes:
      # Named volume for persistence
      - db-data:/var/lib/mysql
      # Bind mount for backups
      - ./backups:/backups
      # tmpfs for temp files
      - type: tmpfs
        target: /dev/shm

volumes:
  db-data:
```

### Q7: What are Docker Networks? Types and use cases.

**Answer:**

Docker Networks enable container-to-container communication and external connectivity.

**Four Types:**

#### 1. **Bridge Network** (Default)
```bash
# Create bridge network
docker network create my-bridge

# Connect containers
docker run --network my-bridge --name web nginx
docker run --network my-bridge --name app myapp

# Containers discover each other by name
```
- Default network type
- Isolated from other networks
- Good for single-host deployments
- Containers communicate via IP or DNS

#### 2. **Host Network**
```bash
# Use host network directly
docker run --network host nginx
```
- No network isolation
- Container uses host's network stack
- Best performance
- Limited portability

#### 3. **Overlay Network**
```bash
# For Swarm/Kubernetes
docker network create --driver overlay my-overlay

# Services communicate across hosts
docker service create --network my-overlay web:latest
```
- Spans multiple hosts
- For distributed systems
- Encrypted by default
- Used in orchestration

#### 4. **None Network**
```bash
# No network access
docker run --network none ubuntu
```
- Complete isolation
- No network communication
- Useful for security-sensitive tasks

**Network Communication:**

```bash
# Containers on same bridge network
docker network create app-net
docker run --name web --network app-net nginx
docker run --name db --network app-net postgres

# From web to db (uses DNS)
docker exec web curl http://db:5432
# Works because Docker resolves 'db' to container IP
```

### Q8: Explain Docker Compose networking.

**Answer:**

Docker Compose creates a dedicated network for all services and enables DNS-based service discovery.

**Default Behavior:**
```yaml
version: '3.8'

services:
  web:
    image: nginx
    # Accessible as: web, web:80, http://web
  
  db:
    image: postgres
    # Accessible as: db, db:5432
```

**Service Discovery:**
```bash
# Web can reach database
docker compose exec web curl http://db:5432

# Database name automatically resolved by Docker DNS
```

**Advanced Networking:**
```yaml
version: '3.8'

services:
  frontend:
    image: nginx
    networks:
      - frontend-network
    ports:
      - "80:80"
  
  backend:
    image: myapp
    networks:
      - backend-network
      - middle-network
  
  db:
    image: postgres
    networks:
      - backend-network

networks:
  frontend-network:
    driver: bridge
  backend-network:
    driver: bridge
  middle-network:
    driver: bridge
```

**Network Isolation:**
- Frontend can't reach backend directly
- Backend can't reach database (needs them on same network)
- Explicit network joining for security

### Q9: How does Docker handle resource limits and what happens when exceeded?

**Answer:**

Docker allows limiting CPU, memory, and I/O resources.

**Memory Limits:**
```bash
# Limit to 512MB
docker run -m 512m nginx

# Soft limit (reservation) and hard limit
docker run --memory-reservation 256m -m 512m nginx
```

**When Memory Exceeded:**
- Container killed by Out-Of-Memory (OOM) killer
- Exit code: 137
- Data loss if no persistence

**CPU Limits:**
```bash
# Limit to 0.5 CPU
docker run --cpus="0.5" apache

# Specific CPUs
docker run --cpuset-cpus="0,1" ubuntu

# CPU shares (relative priority)
docker run --cpu-shares=512 ubuntu
```

**I/O Limits:**
```bash
# Block read/write limits
docker run --blkio-weight=100 ubuntu
docker run --device-read-bps=/dev/sda:10mb ubuntu
```

**Docker Compose:**
```yaml
services:
  app:
    image: myapp
    deploy:
      resources:
        limits:
          cpus: '1'
          memory: 512M
        reservations:
          cpus: '0.5'
          memory: 256M
```

**Real-world Impact:**

| Scenario | Result |
|----------|--------|
| Memory exceeds limit | Container killed, restart on failure |
| CPU at limit | Throttled, reduced performance |
| Disk full | Write failures, container errors |

### Q10: Explain Docker security best practices.

**Answer:**

**Key Security Practices:**

1. **Run as Non-Root User**
   ```dockerfile
   # ✗ Runs as root
   FROM ubuntu
   CMD ["app"]
   
   # ✓ Create and run as user
   FROM ubuntu
   RUN useradd -m appuser
   USER appuser
   CMD ["app"]
   ```

2. **Use Secrets for Sensitive Data**
   ```bash
   # Don't use ENV for secrets in production
   # Use Docker secrets in Swarm
   docker secret create db_password <(echo "SecurePass123")
   
   docker service create \
     --secret db_password \
     myapp:latest
   ```

3. **Scan Images for Vulnerabilities**
   ```bash
   docker scan myimage:latest
   ```

4. **Use Read-Only Filesystem**
   ```bash
   docker run --read-only nginx
   docker run --read-only --tmpfs /tmp nginx
   ```

5. **Limit Capabilities**
   ```bash
   # Drop unnecessary capabilities
   docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx
   ```

6. **Use Official Images**
   ```bash
   # ✓ Official from Docker Hub
   docker pull nginx
   
   # ✗ Unknown source
   docker pull random-username/nginx
   ```

7. **Sign Images**
   ```bash
   export DOCKER_CONTENT_TRUST=1
   docker push myimage:latest
   ```

8. **Regular Updates**
   ```bash
   # Keep base images updated
   FROM ubuntu:20.04  # ✗ Old
   FROM ubuntu:22.04  # ✓ Latest LTS
   ```

9. **Resource Isolation**
   ```yaml
   services:
     app:
       deploy:
         resources:
           limits:
             cpus: '1'
             memory: 512M
   ```

10. **Network Isolation**
    ```bash
    docker network create isolated-net
    docker run --network isolated-net nginx
    ```

## Advanced Level Questions

### Q11: How does Docker handle process isolation and namespace?

**Answer:**

Docker uses Linux namespaces to provide process isolation.

**Six Main Namespaces:**

1. **PID Namespace** - Process ID isolation
   ```bash
   # Container sees only its own processes
   docker run ubuntu ps aux
   # Shows only processes inside container, not host
   ```

2. **Network Namespace** - Network isolation
   ```bash
   # Isolated network stack
   # Own IP, ports, routing tables
   docker run ubuntu ip addr
   ```

3. **Mount Namespace** - Filesystem isolation
   ```bash
   # Isolated filesystem
   docker run -v /host:/container ubuntu ls /
   # Only sees container's filesystem
   ```

4. **UTS Namespace** - Hostname isolation
   ```bash
   docker run --hostname mycontainer ubuntu hostname
   # Returns 'mycontainer', not host hostname
   ```

5. **User Namespace** - User ID mapping
   ```bash
   # Map container root to non-root user
   docker run --userns-remap=default ubuntu id
   ```

6. **IPC Namespace** - IPC communication isolation
   ```bash
   # Isolated message queues, semaphores
   ```

**Namespace Inspection:**
```bash
# View namespaces of running container
docker inspect <container> | grep -i namespace

# See namespace details
ls -la /proc/<pid>/ns/
```

**Cgroup Integration:**
```bash
# Cgroups enforce resource limits
# Namespaces provide process view isolation
# Together: Safe, isolated containers
```

### Q12: Explain Docker storage drivers and their differences.

**Answer:**

Storage drivers manage container layers and data persistence.

**Popular Storage Drivers:**

| Driver | Filesystem | Performance | Use Case |
|--------|-----------|----------|----------|
| **overlay2** | Ext4, XFS | Fastest | Default, recommended |
| **aufs** | Any | Good | Legacy Ubuntu |
| **devicemapper** | LVM | Medium | RHEL, CentOS |
| **btrfs** | Btrfs | Slow | Advanced features |
| **zfs** | ZFS | Medium | BSD, enterprise |

**Overlay2 (Recommended):**
```
Lower layer: Base image (read-only)
Middle layers: Dependencies (read-only)
Upper layer: Container changes (writable)
Work layer: Temporary files
```

**How Layers Work:**
```
Image layers:
- Layer 0 (ubuntu base): 77MB
- Layer 1 (apt install): 50MB
- Layer 2 (app code): 10MB
Total image: 137MB

Container writable layer created on top
Changes written to container layer, not base image
```

**Inspect Storage:**
```bash
# Check storage driver
docker info | grep "Storage Driver"

# View layer details
docker history myimage:latest

# Inspect container storage
docker inspect <container> | grep -i storage
```

**Performance Implications:**
```bash
# Fastest: Use volumes for data
docker run -v data:/app/data myimage

# Slower: Write to container layer
docker run myimage (all writes to container layer)

# Medium: Bind mount
docker run -v /host/path:/app/data myimage
```

### Q13: How does Docker implement container isolation at runtime?

**Answer:**

Docker uses multiple Linux technologies for runtime isolation:

**1. Namespaces** (What the container can see)
```
- PID: Own process tree
- Network: Own network stack
- Mount: Own filesystem
- IPC: Own IPC channel
- UTS: Own hostname
- User: Own user IDs
```

**2. Cgroups** (Resource limits)
```
- CPU: CPU shares, limits
- Memory: Memory limits
- Disk I/O: Block device I/O limits
- Network: Bandwidth limits
```

**3. Capabilities** (What privileged operations allowed)
```bash
# Drop all capabilities, add only needed
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx

# Check capabilities
getcap /usr/bin/ping
```

**4. Seccomp** (Syscall filtering)
```bash
# Run with default seccomp profile
docker run nginx

# Run with no seccomp (unsafe)
docker run --security-opt seccomp=unconfined nginx
```

**5. AppArmor/SELinux** (Mandatory access control)
```bash
# Run with AppArmor profile
docker run --security-opt apparmor=your-profile nginx
```

**6. chroot** (Filesystem root)
```
Container filesystem becomes new root /
Cannot access parent filesystem
```

**Isolation Diagram:**
```
┌─────────────────────────────────────┐
│         Container                    │
│  ┌─────────────────────────────┐    │
│  │ PID Namespace (process 1)   │    │
│  │ Network NS (isolated stack) │    │
│  │ Mount NS (container root)   │    │
│  │ User NS (mapped uids)       │    │
│  │ Cgroups (resource limits)   │    │
│  │ Seccomp (syscall filter)    │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
         ↓
    Host Kernel
```

### Q14: Explain Docker multi-stage builds and optimization strategies.

**Answer:**

Multi-stage builds reduce image size by using multiple build stages.

**Standard Build (Large Image):**
```dockerfile
FROM golang:1.16
WORKDIR /app
COPY . .
RUN go build -o app

# Final image includes entire Go toolchain
# Image size: 800MB+
```

**Multi-Stage Build (Optimized):**
```dockerfile
# Stage 1: Builder (can be large)
FROM golang:1.16 as builder
WORKDIR /app
COPY . .
RUN go build -o app

# Stage 2: Runtime (minimal)
FROM alpine:3.14
WORKDIR /app
COPY --from=builder /app/app /app
CMD ["/app"]

# Final image size: 370MB (base image + binary)
```

**Complex Multi-Stage Example:**
```dockerfile
# Stage 1: Dependencies
FROM ubuntu:20.04 as dependencies
RUN apt-get update && \
    apt-get install -y build-essential git

# Stage 2: Build
FROM dependencies as builder
COPY . /src
WORKDIR /src
RUN make build

# Stage 3: Test
FROM builder as tester
RUN make test

# Stage 4: Runtime (minimal, only binary)
FROM ubuntu:20.04
COPY --from=builder /src/build/app /app/binary
CMD ["/app/binary"]
```

**Size Comparison:**
```
Single stage: 850MB
Multi-stage:  45MB (94% reduction!)
```

**Build Cache Optimization:**
```dockerfile
# Order matters for cache efficiency
FROM python:3.9

# Copy requirements first (changes less frequently)
COPY requirements.txt .
RUN pip install -r requirements.txt

# Copy code (changes frequently)
COPY . .

RUN python setup.py install
```

### Q15: How do you debug a Docker container?

**Answer:**

**Debugging Techniques:**

1. **View Logs**
   ```bash
   # All logs
   docker logs container-id
   
   # Follow logs
   docker logs -f container-id
   
   # Last 100 lines with timestamps
   docker logs -n 100 -t container-id
   
   # Compose logs
   docker compose logs web -f
   ```

2. **Execute Commands**
   ```bash
   # Interactive shell
   docker exec -it container-id bash
   
   # Run single command
   docker exec container-id curl http://localhost
   
   # Debug process
   docker exec container-id ps aux
   ```

3. **Inspect Container**
   ```bash
   # Full container info
   docker inspect container-id
   
   # Format output
   docker inspect -f '{{.State.Pid}}' container-id
   
   # Environment variables
   docker inspect -f '{{.Config.Env}}' container-id
   ```

4. **Health Check Status**
   ```bash
   # Check health
   docker inspect --format='{{.State.Health.Status}}' container-id
   
   # Detailed health
   docker inspect container-id | grep -A 5 Health
   ```

5. **Network Debugging**
   ```bash
   # Check network details
   docker exec container-id ip addr
   
   # DNS resolution
   docker exec container-id nslookup other-service
   
   # Port listening
   docker exec container-id netstat -tlnp
   ```

6. **Resource Usage**
   ```bash
   # Real-time stats
   docker stats container-id
   
   # Peak memory/CPU
   docker stats --no-stream container-id
   ```

7. **Build Debugging**
   ```bash
   # Stop on error to inspect
   docker build -t myimage . --progress=plain
   
   # Run intermediate layer
   docker run -it layer-id bash
   ```

8. **Compose Debugging**
   ```bash
   # Validate syntax
   docker compose config
   
   # Show resolved values
   docker compose config | grep -A 10 services
   
   # Rebuild and debug
   docker compose up --build --no-log-prefix
   ```

## Real-Time Application Puzzles

### Puzzle 1: The Mysterious Port Binding Issue

**Scenario:**
```
You have a multi-container application:
- Frontend (nginx): expose port 80
- Backend API: expose port 3000
- Database: expose port 5432

docker-compose.yml:
services:
  frontend:
    image: nginx:latest
    ports:
      - "80:80"
  
  backend:
    image: api:latest
    ports:
      - "3000:3000"
  
  db:
    image: postgres:latest
    ports:
      - "5432:5432"

Problem: Frontend can't connect to backend using 'backend:3000'.
Backend can connect to database fine using 'db:5432'.
```

**Puzzle Questions:**
1. What's the likely cause?
2. How would you debug this?
3. What's the solution?

**Answer:**

**Likely Cause:**
Frontend and backend might not be on the same network.

**Debugging:**
```bash
# Check networks
docker compose ps --all

# Check service network connectivity
docker compose exec frontend curl http://backend:3000

# If it fails, check networks
docker network ls
docker network inspect <network-id>
docker compose exec frontend nslookup backend
```

**Solution:**

**Problem:** Frontend tries to reach backend:3000, but there's network isolation.

**Fix 1: Explicit Network Declaration**
```yaml
version: '3.8'

services:
  frontend:
    image: nginx:latest
    networks:
      - app-network
    ports:
      - "80:80"
  
  backend:
    image: api:latest
    networks:
      - app-network
    ports:
      - "3000:3000"
  
  db:
    image: postgres:latest
    networks:
      - app-network
    ports:
      - "5432:5432"

networks:
  app-network:
    driver: bridge
```

**Fix 2: Update Frontend Config**
```nginx
# nginx.conf
upstream backend {
    server backend:3000;  # Service name resolution
}

server {
    listen 80;
    location /api {
        proxy_pass http://backend;
    }
}
```

**Key Learning:**
- Docker Compose creates isolated bridge networks
- Service names resolve within the network DNS
- All services on same compose stack are usually on same network by default
- Explicit network definition for clarity

### Puzzle 2: Data Loss After Container Restart

**Scenario:**
```
You deploy a database container:

docker run -d \
  --name mydb \
  -e MYSQL_ROOT_PASSWORD=password \
  -p 3306:3306 \
  mysql:8.0

Data is stored for days. You then:
docker stop mydb
docker start mydb

After restart, original data is gone!

You check:
docker ps -a  # Container exists
docker volume ls  # No volumes
```

**Puzzle Questions:**
1. Why is data lost after restart?
2. Check data from a new container - what happens?
3. How would you prevent data loss?

**Answer:**

**Why Data is Lost:**

When you run `docker run` without volumes:
```
Docker creates container with writable layer
All writes go to container's ephemeral layer
When container removed, layer is deleted
Data is lost!
```

**Container Restart Behavior:**
```bash
docker stop mydb      # Stops container, keeps it
docker start mydb     # Restarts same container

# If container still exists, data persists in that container
# But if new container created:

docker rm mydb        # Remove old container
docker run ...        # New container = new data, no old data
```

**Check from New Container:**
```bash
# Old data appears only in original container
# New container starts fresh
docker run mysql:8.0 mysql -h original-container ...
# Can't connect because connection lost
```

**Prevention Solution:**

**Option 1: Named Volume**
```bash
# Create persistent volume
docker volume create mysql-data

# Use in container
docker run -d \
  --name mydb \
  -v mysql-data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=password \
  mysql:8.0

# Data persists across restarts and even container removal
docker stop mydb
docker rm mydb
docker run -d \
  --name mydb \
  -v mysql-data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=password \
  mysql:8.0
# Old data is restored!
```

**Option 2: Docker Compose**
```yaml
version: '3.8'

services:
  db:
    image: mysql:8.0
    volumes:
      - db-data:/var/lib/mysql  # Persistent
    environment:
      MYSQL_ROOT_PASSWORD: password
    restart: unless-stopped

volumes:
  db-data:
```

**Option 3: Bind Mount**
```bash
docker run -d \
  --name mydb \
  -v /host/mysql/data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=password \
  mysql:8.0
```

**Key Learning:**
- Containers without volumes are ephemeral
- Data in container layer is lost if container is removed
- Use named volumes or bind mounts for persistence
- Docker Compose manages volumes automatically
- Always use volumes for stateful applications (databases)

### Puzzle 3: CPU Throttling Mystery

**Scenario:**
```
You have a compute-intensive Docker application:

docker run --cpus="1" \
  --name heavy-compute \
  mycompute:latest

Previously, this task completed in 2 minutes.
Now it takes 8+ minutes!

Monitoring shows:
- CPU usage: 95-100% constantly
- Memory: Plenty available (4GB free out of 8GB)
- Disk: Not saturated
- Network: No activity

What changed: You moved from 4-CPU host to 2-CPU host.
```

**Puzzle Questions:**
1. What's causing the slowdown?
2. Is it really CPU throttling or something else?
3. How would you optimize?

**Answer:**

**Root Cause: CPU Throttling + Reduced Host Capacity**

```
Old host: 4 CPUs total, container gets 1 CPU
- 25% of machine allocated to container
- Other services running fine

New host: 2 CPUs total, container gets 1 CPU
- 50% of machine allocated to container
- Other Docker/system services contending for 1 remaining CPU
- Context switching overhead increases
- Overall machine becomes slower
```

**Verification:**
```bash
# Check CPU limits
docker inspect --format='{{.HostConfig.CpuQuota}}' heavy-compute
docker inspect --format='{{.HostConfig.CpuPeriod}}' heavy-compute

# Monitor CPU throttling
docker stats --no-stream

# Check if throttled
cat /sys/fs/cgroup/cpu/docker/*/cpu.stat | grep throttled

# High throttled_count = container is CPU-limited
```

**Optimization Options:**

**Option 1: Increase CPU Allocation**
```bash
docker run --cpus="1.5" \  # Now has 1.5 CPUs if available
  --name heavy-compute \
  mycompute:latest
```

**Option 2: Remove CPU Limit**
```bash
docker run --cpus=""  # No limit, but risks starving other containers
  --name heavy-compute \
  mycompute:latest
```

**Option 3: Use CPU Shares (Soft Limit)**
```bash
docker run --cpu-shares=2048 \  # Soft limit, not hard limit
  --name heavy-compute \
  mycompute:latest
```

**Option 4: Upgrade Host**
```
Moving to 4-CPU or 8-CPU host would solve it
Better approach: Load balance across multiple hosts
```

**Option 5: Optimize Application**
```bash
# Use fewer threads or async I/O
# Optimize algorithms
# Profile application to find bottlenecks
```

**Monitoring Solution:**
```bash
# Script to monitor throttling
docker stats heavy-compute --no-stream

# In compose file, add monitoring
services:
  heavy-compute:
    deploy:
      resources:
        limits:
          cpus: '1'
        reservations:
          cpus: '0.5'  # Guaranteed 0.5, can burst to 1.0
```

**Key Learning:**
- CPU limits are hard limits (container can't exceed)
- CPU shares are soft (can burst if available)
- Throttling causes performance degradation
- Monitor `cpu.stat` throttled metrics
- Host capacity affects container performance
- Balancing resource allocation is critical

### Puzzle 4: The Intermittent Connection Failure

**Scenario:**
```
Your Docker Compose setup has:
- Load balancer
- 3 backend replicas
- Database
- Cache

Randomly, you see errors:
"Connection refused"
"Cannot reach service"

But when you check:
docker compose ps
# All containers show "Up"

The errors appear randomly, about 10% of requests fail.
Re-running the same request works.
```

**Puzzle Questions:**
1. Why are connections randomly failing?
2. Is it a network issue?
3. What's the root cause?

**Answer:**

**Root Cause: Race Condition - Service Not Ready**

```
Scenario:
1. docker compose up starts services in parallel
2. Load balancer starts before backend services are ready
3. Connection attempts fail before backend initializes
4. After a few retries, backends are ready
5. Connections succeed

OR

Service crash and restart:
1. Backend crashes or is restarted
2. DNS still resolves to container, but container not accepting connections
3. Connection attempt fails
4. Connection succeeds on retry (after container fully ready)
```

**Debugging:**

```bash
# Check startup order
docker compose logs --tail=50 | grep "accepting connections"

# Health status
docker compose ps
# Some might show "Up (unhealthy)" instead of "Up"

# Test connectivity
docker compose exec loadbalancer curl http://backend:3000
docker compose exec loadbalancer curl http://backend:3000
docker compose exec loadbalancer curl http://backend:3000

# Some might fail, some succeed
```

**Solution 1: Add Health Checks**

```yaml
version: '3.8'

services:
  backend:
    image: myapi:latest
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 5s
      timeout: 3s
      retries: 3
      start_period: 10s  # Wait before starting health checks
    depends_on:
      - db
      - cache

  load-balancer:
    image: nginx
    depends_on:
      backend:
        condition: service_healthy  # Wait for healthy status
```

**Solution 2: Implement Retry Logic**

```python
# In your application
import time
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

def requests_with_retry(max_retries=3):
    session = requests.Session()
    retry = Retry(
        total=max_retries,
        backoff_factor=0.1,
        status_forcelist=(500, 502, 503, 504)
    )
    adapter = HTTPAdapter(max_retries=retry)
    session.mount('http://', adapter)
    return session

# Use it
s = requests_with_retry()
response = s.get('http://backend:3000/api')
```

**Solution 3: Startup Wait Script**

```bash
#!/bin/bash
# wait-for-it.sh

host=$1
port=$2
shift 2
cmd="$@"

while ! nc -z "$host" "$port"; do
  echo "Waiting for $host:$port..."
  sleep 1
done

echo "$host:$port is available"
exec $cmd
```

```dockerfile
ENTRYPOINT ["./wait-for-it.sh", "db", "5432", "--"]
CMD ["python", "app.py"]
```

```yaml
services:
  backend:
    command: >
      sh -c "
        until curl http://db:5432; do
          echo 'Waiting for db...'
          sleep 1
        done &&
        npm start
      "
```

**Solution 4: Implement Circuit Breaker**

```python
from pybreaker import CircuitBreaker

breaker = CircuitBreaker(fail_max=5, reset_timeout=60)

@breaker
def call_backend(url):
    return requests.get(url)

try:
    response = call_backend('http://backend:3000/api')
except Exception as e:
    handle_failure(e)
```

**Key Learning:**
- Service "Up" ≠ Service "Ready"
- Health checks are essential
- Implement retry logic in clients
- Use `depends_on: condition: service_healthy`
- Service discovery doesn't guarantee service readiness
- Circuit breakers prevent cascading failures

### Puzzle 5: The Memory Leak in Containerized Application

**Scenario:**
```
Your Node.js application runs in Docker:

docker run -d \
  -m 512m \
  --memory-swap 512m \
  --name nodejs-app \
  myapp:latest

Status: Works fine for first 2 hours
After 2 hours: Container becomes sluggish
After 3 hours: Container gets killed

Logs show:
"Cannot allocate memory"

docker stats shows:
- Memory: 98% of 512MB
- Still consuming more

Check code: No obvious memory leak
```

**Puzzle Questions:**
1. How to confirm it's a memory leak?
2. Is it container-level or application-level?
3. How to debug and fix?

**Answer:**

**Diagnosis: Memory Leak in Node.js Application**

```
Symptoms indicate application-level memory leak
(not container configuration issue)

Container limit is 512MB (hard limit)
After 3 hours, touches limit and gets OOM killed
```

**Verification:**

```bash
# Check memory trend over time
docker stats --no-stream nodejs-app

# Monitor memory growth
watch 'docker stats --no-stream | grep nodejs-app'

# Check exit reason
docker inspect nodejs-app | grep -i exitcode
# 137 = OOM kill

# Check container logs for OOM
dmesg | grep "Out of memory"
docker logs nodejs-app | tail -20
```

**Deep Debugging:**

```bash
# Enter container and inspect processes
docker exec -it nodejs-app bash

# Check memory usage
ps aux
top
free -h

# Check Node.js memory
node -e "console.log(process.memoryUsage())"

# Heap dump
node --max-old-space-size=512 app.js
```

**Root Cause Analysis:**

**Common Node.js Memory Leaks:**

```javascript
// Problem 1: Global variables accumulating
var cache = {};  // Never cleaned up

function handleRequest(data) {
  cache[data.id] = data;  // Keeps growing forever
}

// Problem 2: Event listeners not removed
function setupListener() {
  emitter.on('event', handler);  // Never removed
}

// Problem 3: Timers not cleared
setInterval(() => {
  list.push(expensiveObject);  // Grows forever
}, 1000);

// Problem 4: Circular references
var obj = {};
obj.self = obj;  // GC might not collect it
```

**Fix 1: Add Memory Monitoring**

```javascript
// monitoring.js
setInterval(() => {
  const usage = process.memoryUsage();
  console.log(`
    RSS: ${Math.round(usage.rss / 1024 / 1024)}MB
    Heap Used: ${Math.round(usage.heapUsed / 1024 / 1024)}MB
    Heap Total: ${Math.round(usage.heapTotal / 1024 / 1024)}MB
  `);
}, 5000);
```

**Fix 2: Use Proper Caching (LRU)**

```javascript
// Use npm package: lru-cache
const LRU = require('lru-cache');

const cache = new LRU({
  max: 500,  // Maximum 500 items
  maxSize: 50 * 1024 * 1024,  // 50MB max
  ttl: 1000 * 60  // 1 minute TTL
});

cache.set(key, value);
```

**Fix 3: Clean Up Event Listeners**

```javascript
// ✓ Good: Remove listener when done
const handler = () => { /* ... */ };
emitter.on('event', handler);

// Later, clean up
emitter.off('event', handler);

// ✓ Good: Use once for one-time events
emitter.once('event', handler);
```

**Fix 4: Force GC (if serious)**

```javascript
// Add flag to enable manual GC
// node --expose-gc app.js

if (global.gc) {
  setInterval(() => {
    global.gc();
    console.log('Garbage collected');
  }, 30000);
}
```

**Docker Fix:**

```yaml
version: '3.8'

services:
  app:
    image: myapp:latest
    deploy:
      resources:
        limits:
          memory: 512M
        reservations:
          memory: 256M  # Alert if exceeds this
    environment:
      - NODE_OPTIONS=--expose-gc  # Enable manual GC
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
    restart: on-failure
```

**Profiling Tools:**

```bash
# Install clinic (Node.js profiling)
npm install --save-dev clinic

# Run with profiler
clinic doctor -- node app.js

# Generate flame graph
clinic flame -- node app.js

# Check with heap snapshot tool
node --inspect app.js
# Opens DevTools inspector
```

**Key Learning:**
- Memory leak indicators: Gradient increase, crashes after time
- Container OOM kill = exit code 137
- Monitor memory growth trends, not just current usage
- Use LRU caches, clean up listeners, set TTLs
- Profiling tools identify leaky functions
- Increase memory limit is temporary, fix app is permanent

## Quick Reference Q&A

### Q&A Section: Rapid-Fire Questions

**Q: What does `-it` mean in `docker run -it`?**
```
-i: --interactive (keep STDIN open even without attached terminal)
-t: --tty (allocate pseudo-terminal)

Together: Allow interactive terminal access
docker run -it ubuntu bash  # Get bash shell access
```

**Q: Difference between ADD and COPY?**
```
COPY: Just copies files
ADD: Copies files + can extract tars + can fetch URLs

Recommendation: Use COPY (simpler, more predictable)
Unless you truly need ADD's features
```

**Q: How to pass environment variables?**
```
docker run -e VAR=value image
docker run --env-file .env image
docker-compose: environment: - VAR=value
```

**Q: How to mount a file (not directory)?**
```
docker run -v /path/to/file.conf:/etc/config.conf image
Works same as directories
```

**Q: How to see what changed in container?**
```
docker diff container-id
# Shows: A (added), D (deleted), C (changed) files
```

**Q: How to create image from running container?**
```
docker commit container-id new-image:tag
# NOT recommended (use Dockerfile instead)
```

**Q: How to limit container output in logs?**
```
docker logs --tail 50 container  # Last 50 lines
docker logs -f --tail 20 container  # Follow last 20
```

**Q: Can you run privileged container?**
```
docker run --privileged image
# Container has access to all host devices
# Security risk, use only when necessary
```

**Q: How to share data between containers?**
```
# ✓ Named volume
docker run -v shared-volume:/data cont1
docker run -v shared-volume:/data cont2

# ✓ Bind mount
docker run -v /shared/path:/data cont1
docker run -v /shared/path:/data cont2

# ✗ Don't: volumes_from (deprecated)
```

**Q: What's the difference between EXPOSE and -p?**
```
EXPOSE 8080      # Documentation: port is used
-p 8080:8080     # Actually maps port

EXPOSE doesn't publish, -p does
Use both: EXPOSE for docs, -p for actual publish
```

**Q: How to force remove container?**
```
docker rm -f container-id
# Forcefully stops and removes
# Use when docker stop doesn't work
```

**Q: How to monitor container resource usage?**
```
docker stats                    # Real-time
docker stats --no-stream       # One snapshot
docker top container-id        # Running processes
```

**Q: Can you have multiple main processes in container?**
```
✓ Technically yes (use supervisord, systemd)
✗ Recommended to have single main process
✓ Use multiple containers instead
```

   - "When you say container crash, do you mean..."

   - Discuss resource limits

   - Show you can troubleshoot
   - Demonstrate log reading skills
   - Explain how you'd diagnose issues

### Common Mistakes to Avoid:

1. ❌ "Containers are just lightweight VMs"
   - ✓ They're isolated processes, not hypervisor-based

2. ❌ Assuming all images are safe
   - ✓ Verify source, run security scans

3. ❌ Running everything with root
   - ✓ Create and use non-root users

4. ❌ Binding to 0.0.0.0 without authentication
   - ✓ Restrict access, use authentication

5. ❌ Storing secrets in Dockerfile
   - ✓ Use secrets management systems

6. ❌ Single container for multiple services
   - ✓ One service per container (Unix philosophy)
