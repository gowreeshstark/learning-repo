# Transactions and ACID Properties in DBMS

## Overview
A transaction is a sequence of database operations that are executed as a single unit of work. The ACID properties ensure that database transactions are processed reliably and maintain data integrity even in case of failures.

---

## What is a Transaction?

A transaction is a logical unit of work that consists of one or more SQL statements. It either completes successfully (COMMIT) or fails completely (ROLLBACK), ensuring data consistency.

**States of a Transaction:**
```
START → EXECUTING → COMMITTED (or ROLLED BACK)
```

---

## ACID Properties

### **1. Atomicity (All or Nothing)**

**Definition:** A transaction is either completely executed or not executed at all. No partial updates.

**Example: Bank Transfer**

**Before Transaction:**
| AccountID | AccountHolder | Balance |
|-----------|---------------|---------|
| 101 | Alice | $1000 |
| 102 | Bob | $500 |

**Transaction Code:**
```sql
BEGIN TRANSACTION;
  UPDATE Accounts SET Balance = Balance - 200 
  WHERE AccountID = 101;  -- Debit from Alice
  
  UPDATE Accounts SET Balance = Balance + 200 
  WHERE AccountID = 102;  -- Credit to Bob
COMMIT;
```

**Scenario 1 - Success:**
```
Debit Alice: $1000 - $200 = $800 ✓
Credit Bob: $500 + $200 = $700 ✓
COMMIT - Transaction complete
```

**After Successful Transaction:**
| AccountID | AccountHolder | Balance |
|-----------|---------------|---------|
| 101 | Alice | $800 |
| 102 | Bob | $700 |

**Scenario 2 - Failure (Power Outage After Debit):**
```
Debit Alice: $1000 - $200 = $800 ✓
Credit Bob: FAILED (System crash)
ROLLBACK - All changes reverted
```

**After Rollback:**
| AccountID | AccountHolder | Balance |
|-----------|---------------|---------|
| 101 | Alice | $1000 |
| 102 | Bob | $500 |

---

### **2. Consistency (Valid State to Valid State)**

**Definition:** A transaction transforms the database from one valid state to another valid state. All rules and constraints are satisfied.

**Example: Order Processing**

**Before Transaction:**
| OrderID | ProductID | Quantity | Status |
|---------|-----------|----------|--------|
| O1 | P101 | 5 | Pending |

| ProductID | StockQuantity |
|-----------|---------------|
| P101 | 100 |

**Transaction Code:**
```sql
BEGIN TRANSACTION;
  UPDATE Orders SET Status = 'Confirmed' 
  WHERE OrderID = 'O1';
  
  UPDATE Products SET StockQuantity = StockQuantity - 5 
  WHERE ProductID = 'P101';
COMMIT;
```

**Valid State (Consistent):**
```
Order status = Confirmed
Stock reduced by 5 units
Inventory matches order quantity
✓ All business rules satisfied
```

**After Transaction:**
| OrderID | ProductID | Quantity | Status |
|---------|-----------|----------|--------|
| O1 | P101 | 5 | Confirmed |

| ProductID | StockQuantity |
|-----------|---------------|
| P101 | 95 |

**Invalid State (Inconsistent - Would be Prevented):**
```
Order status = Confirmed
Stock NOT reduced
✗ Inventory mismatch - Violates consistency rule
Transaction would ROLLBACK
```

---

### **3. Isolation (Independent Execution)**

**Definition:** Concurrent transactions do not interfere with each other. Each transaction executes as if it's the only one running.

**Example: Concurrent Bank Transfers**

**Initial State:**
| AccountID | Balance |
|-----------|---------|
| 101 | $1000 |

**Transaction 1 (T1):** Transfer $200 from Account 101
```sql
BEGIN TRANSACTION T1;
  READ Balance from Account 101  -- Reads $1000
  -- Process time: 5 seconds
  UPDATE Account 101 SET Balance = Balance - 200;
COMMIT T1;
```

**Transaction 2 (T2):** Transfer $100 from Account 101
```sql
BEGIN TRANSACTION T2;
  READ Balance from Account 101  -- Should read after T1
  UPDATE Account 101 SET Balance = Balance - 100;
COMMIT T2;
```

**With Isolation (Serializable):**
```
T1 Starts → T2 Waits (locked)
T1 Commits: Balance = $800
T2 Reads: $800
T2 Updates: Balance = $700 ✓ Correct
```

**Final State (Correct):**
| AccountID | Balance |
|-----------|---------|
| 101 | $700 |

**Isolation Levels:**

```
1. READ UNCOMMITTED (Dirty Read)
   - Can read uncommitted changes from other transactions
   - Fastest, least safe

2. READ COMMITTED (Non-Repeatable Read)
   - Can only read committed data
   - Default in most databases

3. REPEATABLE READ
   - Prevents non-repeatable reads
   - Can see phantom rows

4. SERIALIZABLE (Strictest)
   - Complete isolation
   - Transactions execute sequentially
   - Slowest, most safe
```

**Example with Different Isolation Levels:**

**Dirty Read (READ UNCOMMITTED):**
```
T1: UPDATE Salary SET amount = 5000 WHERE EmployeeID = 1
T2: SELECT * FROM Salary WHERE EmployeeID = 1  -- Reads $5000 (uncommitted)
T1: ROLLBACK  -- Changes reversed
T2: Just read data that never existed! ✗
```

**Repeatable Read (REPEATABLE READ):**
```
T1: BEGIN TRANSACTION
T1: SELECT * FROM Salary WHERE EmployeeID = 1  -- Reads $4000
T2: BEGIN TRANSACTION
T2: UPDATE Salary SET amount = 5000 WHERE EmployeeID = 1
T2: COMMIT
T1: SELECT * FROM Salary WHERE EmployeeID = 1  -- Still reads $4000 ✓
T1: COMMIT
```

### **4. Durability (Persistent)**

**Definition:** Once a transaction is committed, the changes are permanent and survive any failures (power outage, system crash, etc.).

**Example: Flight Booking**

**Transaction:**
```sql
BEGIN TRANSACTION;
  INSERT INTO BookingHistory VALUES ('B123', '2026-06-15', 'Confirmed');
  UPDATE Flights SET AvailableSeats = AvailableSeats - 1 
  WHERE FlightID = 'F456';
COMMIT;  -- Written to disk immediately
```

**Durability Guarantee:**
```
Transaction Committed at 14:30:00
↓
Data written to disk
↓
System crashes at 14:30:05
↓
After recovery, booking still exists ✓
Data is safe and permanent
```

**Before Transaction:**
| BookingID | FlightID | Status |
|-----------|----------|--------|
| B122 | F455 | Confirmed |

**After COMMIT (Durable):**
| BookingID | FlightID | Status |
|-----------|----------|--------|
| B122 | F455 | Confirmed |
| B123 | F456 | Confirmed |

**Even after crash:**
```
Restart Database
↓
Check Transaction Logs
↓
Booking B123 committed before crash
↓
B123 persists in database ✓
```

## Transaction Control Commands

```sql
-- 1. BEGIN TRANSACTION
BEGIN TRANSACTION;

-- 2. COMMIT (Save changes)
COMMIT;

-- 3. ROLLBACK (Undo changes)
ROLLBACK;

-- 4. SAVEPOINT (Create checkpoint)
SAVEPOINT SavePoint1;

-- 5. ROLLBACK TO SAVEPOINT
ROLLBACK TO SavePoint1;
```

## Transaction Example: Online Shopping

**Scenario:** Customer purchases an item

**Complete Transaction:**
```sql
BEGIN TRANSACTION BuyingItem;
  -- 1. Create order
  INSERT INTO Orders (OrderID, CustomerID, OrderDate, Status) 
  VALUES ('ORD789', 'CUST123', '2026-06-15', 'Pending');
  
  -- 2. Create order items
  INSERT INTO OrderItems (OrderID, ProductID, Quantity, Price) 
  VALUES ('ORD789', 'PROD001', 2, 50.00);
  
  -- 3. Update inventory
  UPDATE Products SET Stock = Stock - 2 
  WHERE ProductID = 'PROD001';
  
  -- 4. Update customer transaction
  INSERT INTO Transactions (TransactionID, CustomerID, Amount, Type) 
  VALUES ('TXN456', 'CUST123', 100.00, 'Debit');
  
  -- 5. Update account balance
  UPDATE Accounts SET Balance = Balance - 100.00 
  WHERE CustomerID = 'CUST123';

  -- If all successful
  COMMIT BuyingItem;
END;

-- If any statement fails, entire transaction rolls back
-- ROLLBACK BuyingItem;
```

**Before Transaction:**
| OrderID | Status | ProductID | Stock | CustomerBalance |
|---------|--------|-----------|-------|-----------------|
| - | - | PROD001 | 50 | $500 |

**After Successful COMMIT:**
| OrderID | Status | ProductID | Stock | CustomerBalance |
|---------|--------|-----------|-------|-----------------|
| ORD789 | Pending | PROD001 | 48 | $400 |

**After ROLLBACK (on failure):**
| OrderID | Status | ProductID | Stock | CustomerBalance |
|---------|--------|-----------|-------|-----------------|
| - | - | PROD001 | 50 | $500 |

## Transaction with Savepoints

```sql
BEGIN TRANSACTION;
  -- Step 1: Create customer
  INSERT INTO Customers VALUES ('C100', 'John Doe', 'john@email.com');
  SAVEPOINT SP1;
  
  -- Step 2: Create account
  INSERT INTO Accounts VALUES ('ACC100', 'C100', 5000);
  SAVEPOINT SP2;
  
  -- Step 3: Add transaction record
  INSERT INTO TransactionLog VALUES ('T100', 'ACC100', 5000, 'Opening');
  
  -- If Step 3 fails, rollback only Step 3, keep Steps 1 & 2
  -- ROLLBACK TO SP2;
  
  -- Or commit everything
  COMMIT;
END;
```

## ACID in Real-World Scenarios

### **Banking System**
- **Atomicity:** Transfer either succeeds completely or not at all
- **Consistency:** Account balances always match ledger
- **Isolation:** Concurrent transfers don't interfere
- **Durability:** Committed transfer survives crash

### **E-Commerce Platform**
- **Atomicity:** Order + Payment + Inventory updated together
- **Consistency:** Stock never goes negative
- **Isolation:** Multiple concurrent orders don't interfere
- **Durability:** Order persists after confirmation

### **Hospital Records**
- **Atomicity:** Patient admission + admission fee processed together
- **Consistency:** All patient data valid and complete
- **Isolation:** Multiple records updated independently
- **Durability:** Patient records permanently saved

## Best Practices

✓ Keep transactions short and focused  
✓ Avoid nested transactions if possible  
✓ Use appropriate isolation levels  
✓ Handle exceptions with ROLLBACK  
✓ Use SAVEPOINTS for complex operations  
✓ Monitor transaction logs regularly  
✓ Test failure scenarios
