# Concurrency Control in DBMS

## Overview
Concurrency control is a mechanism that ensures multiple transactions can execute simultaneously without interfering with each other, while maintaining data consistency and integrity. It prevents conflicts and ensures the ACID properties are maintained.

---

## Why is Concurrency Control Needed?

**Problems Without Concurrency Control:**

1. **Dirty Read** - Reading uncommitted data
2. **Non-Repeatable Read** - Data changes between reads
3. **Phantom Read** - New rows appear between reads
4. **Lost Update** - Updates overwriting each other
5. **Race Conditions** - Unpredictable outcomes

---

## Concurrency Control Techniques

### **1. Locking (Lock-Based Protocol)**

Locks prevent simultaneous access to shared resources.

#### **Types of Locks:**

**Shared Lock (Read Lock):**
```
- Multiple transactions can hold simultaneously
- Prevents write operations
- Symbol: S-lock or R-lock
- Read operations require shared lock

Example:
T1: LOCK SHARED (Account 101)  -- Can read
T2: LOCK SHARED (Account 101)  -- Can also read
T3: LOCK EXCLUSIVE (Account 101) -- Must wait
```

**Exclusive Lock (Write Lock):**
```
- Only one transaction can hold
- Prevents all other operations
- Symbol: X-lock or W-lock
- Write operations require exclusive lock

Example:
T1: LOCK EXCLUSIVE (Account 101) -- Only T1 can access
T2: Any operation on Account 101 -- BLOCKED, waits for T1
T3: Any operation on Account 101 -- BLOCKED, waits
```

#### **Lock Compatibility Matrix:**

```
        S-Lock    X-Lock
S-Lock   YES       NO
X-Lock   NO        NO
```

---

### **2. Two-Phase Locking (2PL)**

Ensures serializability through two phases: Growing Phase and Shrinking Phase.

**Phases:**

```
Growing Phase: Transaction can acquire locks, cannot release
               ↓
Peak Point: Maximum locks held
               ↓
Shrinking Phase: Transaction can release locks, cannot acquire
```

**Example: Bank Transfer**

```
Transaction T1: Transfer $100 from Account A to Account B

Growing Phase:
  Step 1: LOCK EXCLUSIVE (Account A)
  Step 2: LOCK EXCLUSIVE (Account B)
  (Both locks acquired)

Active Phase:
  Step 3: READ Account A balance = $1000
  Step 4: UPDATE Account A SET balance = 900
  Step 5: READ Account B balance = $500
  Step 6: UPDATE Account B SET balance = 600

Shrinking Phase:
  Step 7: UNLOCK Account A
  Step 8: UNLOCK Account B
  (Can't reacquire locks after releasing)
```

**Before Transaction:**
| AccountID | Balance |
|-----------|---------|
| A | $1000 |
| B | $500 |

**After Transaction:**
| AccountID | Balance |
|-----------|---------|
| A | $900 |
| B | $600 |

### **3. Timestamp Ordering Protocol**

Each transaction gets a unique timestamp. Conflicts resolved based on timestamp order.

**How it works:**
```
T1 gets timestamp = 100
T2 gets timestamp = 200
T3 gets timestamp = 150

Execution order: T1 (100) → T3 (150) → T2 (200)
```

**Read/Write Timestamp:**
```
Each data item has:
- Read Timestamp (RTS): Latest read timestamp
- Write Timestamp (WTS): Latest write timestamp
```

**Rules:**

```
1. If T wants to READ data item X:
   If T_timestamp < WTS(X):
     REJECT (reading from future)
   Else:
     ALLOW and update RTS(X) = max(RTS(X), T_timestamp)

2. If T wants to WRITE data item X:
   If T_timestamp < RTS(X) or T_timestamp < WTS(X):
     REJECT (writing to past)
   Else:
     ALLOW and update WTS(X) = T_timestamp
```

**Example:**

**Initial State:**
| Item | RTS | WTS |
|------|-----|-----|
| X | - | - |

**Transaction T100: WRITE X**
```
T100_timestamp = 100
100 < RTS(X)? NO
100 < WTS(X)? NO
ALLOW
WTS(X) = 100
```

**Result:**
| Item | RTS | WTS |
|------|-----|-----|
| X | - | 100 |

**Transaction T50: WRITE X**
```
T50_timestamp = 50
50 < RTS(X)? NO
50 < WTS(X)? YES (100 > 50)
REJECT - Cascading abort
```

### **4. Optimistic Concurrency Control**

Assumes conflicts are rare. Transactions proceed without locking, validated before commit.

**Phases:**

```
1. READ Phase: Read data, no locks
2. WRITE Phase: Perform computations in local workspace
3. VALIDATION Phase: Check for conflicts
4. COMMIT Phase: If valid, write to database
```

**Example: Airline Seat Booking**

```
Transaction T1: Book Seat 12A for Flight AA100

READ Phase:
  Seat 12A status = Available
  LocalCopy: Seat 12A = Available

WRITE Phase:
  LocalCopy: Seat 12A = Booked
  LocalCopy: Booking = {Cust123, Seat12A}
  (Changes only in local workspace)

VALIDATION Phase:
  Check: Did anyone modify Seat 12A?
  Check: Did anyone modify Booking table?
  Result: NO conflicts

COMMIT Phase:
  Update Database: Seat 12A = Booked
  Update Database: Insert Booking record
  Transaction succeeds ✓
```

**Conflict Detection:**

```
ReadSet(T): All items read by T
WriteSet(T): All items written by T

If WriteSet(T1) ∩ ReadSet(T2) ≠ ∅
   OR WriteSet(T1) ∩ WriteSet(T2) ≠ ∅
   → CONFLICT detected
   → T1 or T2 must ROLLBACK
```

## Common Concurrency Problems and Solutions

### **Problem 1: Dirty Read**

**Scenario:**
```
T1: UPDATE Salary SET amount = 5000 WHERE EmpID = 1
T2: SELECT * FROM Salary WHERE EmpID = 1  -- Reads 5000 (uncommitted)
T1: ROLLBACK  -- Changes reversed
T2: Just read dirty data! ✗
```

**Solution: Isolation Level = READ COMMITTED**
```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
T1: UPDATE Salary SET amount = 5000 WHERE EmpID = 1
T2: SELECT * FROM Salary WHERE EmpID = 1  -- BLOCKS, waits for T1
T1: ROLLBACK
T2: Proceeds, reads original value ✓
```

---

### **Problem 2: Lost Update**

**Scenario:**
```
Initial: Account Balance = $1000

T1: READ Balance = 1000          [T1_timestamp: 100]
                                 T2: READ Balance = 1000 [T2_timestamp: 101]
T1: Balance = 1000 - 100 = 900
T1: WRITE Balance = 900
                                 T2: Balance = 1000 + 50 = 1050
                                 T2: WRITE Balance = 1050 (overwrites T1)

Final: Balance = 1050 (T1's update lost!) ✗
```

**Solution: Use Locking**
```sql
T1: LOCK EXCLUSIVE (Account)
T1: READ Balance = 1000
T1: Balance = 900
T1: WRITE Balance = 900
    T2: LOCK EXCLUSIVE (Account) -- BLOCKED, waits for T1
T1: COMMIT, UNLOCK
    T2: Gets lock
    T2: READ Balance = 900
    T2: Balance = 950
    T2: WRITE Balance = 950
    T2: COMMIT, UNLOCK

Final: Balance = 950 ✓
```

---

### **Problem 3: Non-Repeatable Read**

**Scenario:**
```
T1: SELECT Age FROM Employee WHERE EmpID = 5  -- Reads 25
    T2: UPDATE Employee SET Age = 26 WHERE EmpID = 5
    T2: COMMIT
T1: SELECT Age FROM Employee WHERE EmpID = 5  -- Reads 26 (different!)
```

**Solution: REPEATABLE READ Isolation**
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

T1: SELECT Age FROM Employee WHERE EmpID = 5  -- Reads 25 (locks row)
    T2: UPDATE Employee SET Age = 26 WHERE EmpID = 5  -- BLOCKED
T1: SELECT Age FROM Employee WHERE EmpID = 5  -- Reads 25 (same value) ✓
T1: COMMIT
    T2: Now updates, Age = 26
```

---

### **Problem 4: Phantom Read**

**Scenario:**
```
T1: SELECT COUNT(*) FROM Orders WHERE Status = 'Pending'  -- Result: 5
    T2: INSERT INTO Orders VALUES (..., 'Pending')
    T2: COMMIT
T1: SELECT COUNT(*) FROM Orders WHERE Status = 'Pending'  -- Result: 6 (phantom row!)
```

**Solution: SERIALIZABLE Isolation**
```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

T1: SELECT COUNT(*) FROM Orders WHERE Status = 'Pending'  -- Locks range
    T2: INSERT INTO Orders VALUES (..., 'Pending')  -- BLOCKED
T1: SELECT COUNT(*) FROM Orders WHERE Status = 'Pending'  -- Result: 5 (same) ✓
T1: COMMIT
    T2: Now inserts
```

## Deadlock

**Definition:** Two or more transactions waiting for each other indefinitely.

**Example:**
```
T1: LOCK EXCLUSIVE (Account A)
    T2: LOCK EXCLUSIVE (Account B)
T1: LOCK EXCLUSIVE (Account B) -- WAIT for T2
    T2: LOCK EXCLUSIVE (Account A) -- WAIT for T1

DEADLOCK! Both transactions waiting forever.
```

**Graphical Representation:**
```
T1 ----→ A (holds)
         ↓
         waits for B
         ↑
       T2 (holds)
←----
```

**Deadlock Prevention Strategies:**

```
1. Ordered Locking:
   Always acquire locks in same order
   T1: LOCK A, then LOCK B
   T2: LOCK A, then LOCK B  (not B then A)

2. Lock Timeout:
   If transaction waits > X seconds, ROLLBACK

3. Deadlock Detection:
   Build wait-for graph
   Detect cycles
   Kill one transaction (victim)

4. Conservative Locking:
   Acquire all locks before execution
```

**Example: Preventing Deadlock with Ordered Locking**

```
Bank Accounts: A, B, C, D...
Order: A < B < C < D (always)

T1: Transfer from A to B
    LOCK A (lower ID first)
    LOCK B

T2: Transfer from B to C
    LOCK B (lower ID first)
    LOCK C
    -- No deadlock possible ✓
```

## Interview Questions & Answers

### **Q1: What is the difference between Shared Lock and Exclusive Lock?**

**Answer:**
```
Shared Lock (S-lock):
- Multiple transactions can hold simultaneously
- Used for READ operations
- Allows multiple readers, no writers
- Example: 5 people reading a book (shared lock)

Exclusive Lock (X-lock):
- Only one transaction can hold
- Used for WRITE operations
- Prevents all other locks
- Example: 1 person writing in a book (exclusive lock)

Compatibility:
S + S = Compatible ✓
S + X = Incompatible ✗
X + X = Incompatible ✗
```

---

### **Q2: Explain Two-Phase Locking (2PL)**

**Answer:**
```
2PL has two phases:

1. Growing Phase:
   - Transaction acquires locks as needed
   - Cannot release locks
   - Continues until all locks obtained

2. Shrinking Phase:
   - Transaction releases locks
   - Cannot acquire new locks
   - Continues until all locks released

Benefits:
- Ensures serializability
- Prevents conflicts
- Guarantees ACID properties

Downside:
- Can cause deadlocks
- Performance overhead
```

---

### **Q3: What is Timestamp Ordering?**

**Answer:**
```
Each transaction gets unique timestamp (T_ts)
Each data item has:
- Read Timestamp (RTS): Last transaction to read it
- Write Timestamp (WTS): Last transaction to write it

Rules:
1. READ: If T_ts < WTS, reject (reading from future)
          Else allow, update RTS
2. WRITE: If T_ts < RTS or T_ts < WTS, reject
          Else allow, update WTS

Advantage:
- No blocking, no deadlocks
- Better concurrency than 2PL

Disadvantage:
- Cascading aborts possible
- Performance overhead of aborting transactions
```

---

### **Q4: Explain MVCC (Multi-Version Concurrency Control)**

**Answer:**
```
MVCC maintains multiple versions of data:

Concept:
- Each write creates new version
- Readers see consistent snapshot
- Writers don't block readers

Example:
Version 1: Balance = 1000
Version 2: Balance = 900  (written by T1)
Version 3: Balance = 850  (written by T2)

T3 can read Version 1 (snapshot before T1, T2)
T4 can read Version 3 (latest committed)
No blocking occurs!

Used in:
- PostgreSQL, Oracle, MySQL 8.0
- Very efficient for read-heavy workloads
```

---

### **Q5: What causes deadlock and how to prevent it?**

**Answer:**
```
Deadlock Occurs When:
1. Mutual Exclusion: Resources cannot be shared
2. Hold and Wait: Process holds resources and waits
3. No Preemption: Resources not forcibly taken
4. Circular Wait: Cycle of processes waiting

Deadlock Example:
T1 holds A, waits for B
T2 holds B, waits for A

Prevention Strategies:

1. Resource Ordering:
   Acquire resources in fixed order
   Prevents circular wait

2. Timeout:
   If wait > X seconds, abort

3. Deadlock Detection:
   Use wait-for graph
   Detect cycles, abort victim

4. Conservative Locking:
   Acquire all locks at start

5. Lock Timeout + Retry:
   Exponential backoff retry
```

---

### **Q6: Compare Pessimistic vs Optimistic Locking**

**Answer:**
```
Pessimistic Locking (2PL, Locking):
- Assumes conflicts will occur
- Locks resources before access
- Blocks other transactions
- Safe but slow
- High lock overhead
- Best for: High conflict workloads

Optimistic Locking:
- Assumes conflicts rare
- No locking during execution
- Validates at commit
- Fast but may abort
- Low lock overhead
- Best for: Low conflict workloads

Performance:
- Pessimistic: Slower with high conflicts
- Optimistic: Slower with many conflicts (aborts)
            Faster with few conflicts

Decision:
High conflict → Use Pessimistic
Low conflict → Use Optimistic
```

✓ Choose appropriate isolation level for workload  
✓ Use explicit locking for critical sections  
✓ Keep transactions short to reduce lock time  
✓ Acquire locks in consistent order  
✓ Monitor deadlock occurrences  
✓ Use MVCC when reading is dominant  
✓ Avoid nested transactions  
✓ Set appropriate lock timeouts
