# Database Design in DBMS

## Overview
**Database design** is the process of structuring a database so it stores data efficiently, avoids redundancy, enforces integrity, and supports the application's query patterns. A good design balances **normalization** (data correctness) with **performance** (query speed).

> **Interview one-liner:** Good DB design = the right tables, the right relationships, the right keys, and the right level of normalization for your workload.

---

## Phases of Database Design

| Phase | Goal | Output |
|-------|------|--------|
| **Conceptual** | Model the business domain | **ER Diagram** (entities, relationships) |
| **Logical** | Map to relational model | Tables, keys, normalized schema |
| **Physical** | Optimize for the DB engine | Indexes, partitions, storage, data types |

---

## Entity-Relationship (ER) Model

### Core Building Blocks
- **Entity** – A real-world object (e.g., `Customer`, `Order`).
- **Attribute** – A property of an entity (e.g., `name`, `email`).
- **Relationship** – An association between entities (e.g., Customer *places* Order).

### Types of Attributes
- **Simple vs Composite** – `age` vs `full_name (first + last)`
- **Single-valued vs Multi-valued** – `dob` vs `phone_numbers`
- **Derived** – Computed (e.g., `age` from `dob`)
- **Key attribute** – Uniquely identifies an entity

### Cardinality (Relationship Types)
```
One-to-One   (1:1)   → Person ── Passport
One-to-Many  (1:N)   → Customer ──< Orders
Many-to-Many (M:N)   → Students >──< Courses  (needs a junction table)
```

> **Interview tip:** A **M:N** relationship is always resolved into **two 1:N relationships** using a **junction/bridge table**.

## Keys (Critical Interview Topic)

| Key | Description |
|-----|-------------|
| **Super Key** | Any set of columns that uniquely identifies a row |
| **Candidate Key** | Minimal super key (no redundant attribute) |
| **Primary Key** | Chosen candidate key; unique + NOT NULL |
| **Alternate Key** | Candidate keys not chosen as primary |
| **Foreign Key** | References a primary key in another table (enforces referential integrity) |
| **Composite Key** | Primary key made of multiple columns |
| **Surrogate Key** | System-generated key (auto-increment / UUID) with no business meaning |

> **Natural vs Surrogate key** is a common debate: natural keys carry meaning but can change; surrogate keys are stable and simple.

---

## Integrity Constraints

1. **Entity Integrity** – Primary key cannot be NULL.
2. **Referential Integrity** – Foreign key must match an existing PK or be NULL.
3. **Domain Integrity** – Values must fit the column's type/range (via `CHECK`, `NOT NULL`, `DEFAULT`).
4. **Key/Unique Integrity** – No duplicate values in unique columns.

### Referential Actions (on FK)
```sql
ON DELETE CASCADE     -- delete child rows too
ON DELETE SET NULL    -- null out the FK
ON DELETE RESTRICT    -- block the delete
```

## Normalization vs Denormalization

**Normalization** removes redundancy and update anomalies (see [3.Normalisation.md](3.Normalisation.md)).

| Normal Form | Removes |
|-------------|---------|
| 1NF | Repeating groups / multi-valued attributes |
| 2NF | Partial dependency on part of a composite key |
| 3NF | Transitive dependency |
| BCNF | Remaining anomalies where a non-key determines a key |

**Denormalization** intentionally adds redundancy to **speed up reads** (fewer joins) — common in reporting/analytics and read-heavy systems.

> **Interview trade-off:** Normalize for **write consistency (OLTP)**, denormalize for **read performance (OLAP)**.

---

## OLTP vs OLAP

| Aspect | OLTP | OLAP |
|--------|------|------|
| Purpose | Day-to-day transactions | Analytics / reporting |
| Design | Highly normalized | Denormalized (star/snowflake schema) |
| Queries | Short reads/writes | Large aggregations |
| Example | Banking, e-commerce checkout | Dashboards, BI |

---

## Schema Design Patterns (Data Warehousing)
- **Star Schema** – Central **fact table** linked to **dimension tables**; simple and fast.
- **Snowflake Schema** – Dimensions further normalized; less redundancy, more joins.

---

## Best Practices
- Choose **appropriate data types** (smallest that fits) for storage and speed.
- Always define **primary keys** and **foreign keys** for integrity.
- **Index** columns used in `WHERE`, `JOIN`, `ORDER BY` (see [4.Indexing.md](4.Indexing.md)).
- Avoid **over-normalization** if it forces too many joins for hot queries.
- Design around **access patterns**, not just the data model.
- Use **naming conventions** consistently (singular vs plural, snake_case).

## Interview Quick-Fire Q&A

**Q: Difference between primary key and unique key?**
Primary key is unique + NOT NULL and only one per table; unique key allows one NULL and there can be many.

**Q: What is a foreign key used for?**
To enforce **referential integrity** — the relationship between two tables.

**Q: How do you model a many-to-many relationship?**
With a **junction table** holding foreign keys to both entities.

**Q: When would you denormalize?**
For read-heavy or analytical workloads where join cost outweighs redundancy concerns.

**Q: Natural vs surrogate key — which do you prefer?**
Surrogate (e.g., auto-increment ID) for stability and simplicity; natural keys when a reliable, immutable business identifier exists.

---

## Key Takeaways
- Design flows **Conceptual → Logical → Physical**.
- **Keys and constraints** enforce integrity.
- **Normalize** for correctness; **denormalize** for read speed.
- Design for the **query/access patterns** of your application.
