# Partitioning and Sharding in DBMS

## Overview
As data grows, a single table or single server becomes a bottleneck. **Partitioning** and **Sharding** are techniques to split large datasets into smaller, more manageable pieces to improve **performance, scalability, and manageability**.

- **Partitioning** – Splitting a table **within the same database/server**.
- **Sharding** – Splitting data **across multiple servers/databases** (a form of horizontal partitioning at the infrastructure level).

> **Interview one-liner:** Partitioning divides data *inside one machine*; sharding spreads data *across many machines*.

---

## Partitioning

Dividing a large table into smaller physical pieces (**partitions**) while it still logically appears as one table.

### Horizontal Partitioning (by rows)
Each partition holds a **subset of rows** with the same schema.
```
Orders table split by year:
Partition 2023 → rows where year = 2023
Partition 2024 → rows where year = 2024
Partition 2025 → rows where year = 2025
```

### Vertical Partitioning (by columns)
Each partition holds a **subset of columns**; frequently used columns are separated from rarely used/large ones.
```
Users table split:
Partition A → id, name, email        (hot, frequently queried)
Partition B → id, bio, profile_image (cold, rarely queried)
```

---

## Partitioning Strategies

| Strategy | How it splits | Best for |
|----------|---------------|----------|
| **Range** | Values in a range (dates, IDs) | Time-series, sequential data |
| **List** | Discrete list of values (region, status) | Categorical data |
| **Hash** | Hash of a key → even distribution | Uniform load, avoid hotspots |
| **Composite** | Combination (e.g., range + hash) | Complex large datasets |

```sql
-- Example: Range partitioning (PostgreSQL)
CREATE TABLE orders (id INT, order_date DATE)
PARTITION BY RANGE (order_date);

CREATE TABLE orders_2024 PARTITION OF orders
FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
```

### Benefits of Partitioning
- **Query performance** – **Partition pruning** scans only relevant partitions.
- **Easier maintenance** – Archive/drop old partitions quickly.
- **Parallelism** – Operations run across partitions.

---

## Sharding

**Sharding** distributes data horizontally across **multiple independent database servers** (called **shards**). Each shard holds a portion of the data and can be queried independently.

```
                 ┌─────────┐
   Requests ───▶ │  Router │
                 └────┬────┘
        ┌────────────┼────────────┐
        ▼            ▼            ▼
    Shard 1      Shard 2      Shard 3
  (users A–H)  (users I–P)  (users Q–Z)
```

### Shard Key
The column used to decide **which shard** a row goes to (e.g., `user_id`, `region`). Choosing a good shard key is the **most important sharding decision**.

**A good shard key:**
- Distributes data **evenly** (avoids hotspots).
- Matches common **query patterns** (so most queries hit one shard).
- Has **high cardinality**.

---

## Sharding Strategies

| Strategy | How it works | Pros | Cons |
|----------|--------------|------|------|
| **Range-based** | Ranges of the shard key | Simple, good for range queries | Uneven load / hotspots |
| **Hash-based** | Hash(key) → shard | Even distribution | Range queries hit all shards |
| **Directory/Lookup** | Lookup table maps key → shard | Flexible, easy rebalancing | Lookup is a single point of failure |
| **Geo/Entity-based** | By region or tenant | Data locality, compliance | Skew if one region is large |

---

## Partitioning vs Sharding

| Aspect | Partitioning | Sharding |
|--------|--------------|----------|
| Location | Same server/database | Multiple servers |
| Goal | Manageability + performance | Horizontal **scalability** |
| Scaling | Vertical (bigger machine) | Horizontal (more machines) |
| Complexity | Lower (DB handles it) | Higher (app/router logic) |
| Failure impact | One DB down = all down | One shard down = partial outage |

> **Key point:** All sharding is horizontal partitioning, but not all partitioning is sharding.

---

## Challenges of Sharding

1. **Cross-shard queries / joins** – Expensive; require gathering from multiple shards.
2. **Cross-shard transactions** – Hard to keep ACID; may need **2-phase commit** or eventual consistency.
3. **Rebalancing** – Adding/removing shards means moving data. **Consistent hashing** minimizes data movement.
4. **Hotspots** – A bad shard key overloads one shard (e.g., sharding by `country` when 80% users are in one country).
5. **Operational complexity** – Backups, monitoring, and schema changes across many shards.

### Consistent Hashing
A hashing technique that maps both keys and servers onto a **ring**, so adding/removing a shard only reshuffles a **small fraction** of keys instead of all of them. Widely used in distributed systems (e.g., DynamoDB, Cassandra).

---

## Related Scaling Concepts

- **Replication** – Copying the same data to multiple servers for **availability & read scaling** (see [11.Replication.md](11.Replication.md)). Sharding splits data; replication copies it — they are often **combined**.
- **Vertical scaling (scale up)** – Bigger server (more CPU/RAM).
- **Horizontal scaling (scale out)** – More servers → sharding enables this.

> **Interview trade-off:** **Sharding = write/storage scaling**, **Replication = read scaling + high availability**. Real systems use both together.

## Interview Quick-Fire Q&A

**Q: Difference between partitioning and sharding?**
Partitioning splits data within one database; sharding splits it across multiple database servers.

**Q: Horizontal vs vertical partitioning?**
Horizontal splits **rows**; vertical splits **columns**.

**Q: What is a shard key and why is it important?**
The key that decides data placement; a poor choice causes hotspots and uneven load.

**Q: How do you handle adding a new shard without moving all data?**
Use **consistent hashing** so only a small portion of keys are remapped.

**Q: Why are cross-shard joins expensive?**
Data lives on different servers, so results must be fetched and merged across the network.

**Q: Sharding vs Replication?**
Sharding splits data for write/storage scaling; replication duplicates data for read scaling and availability.

**Q: What is partition pruning?**
The optimizer skips partitions that can't contain matching rows, scanning only the relevant ones.

---

## Key Takeaways
- **Partitioning** = split within one DB (**Range / List / Hash / Composite**).
- **Sharding** = split across servers for **horizontal scalability**.
- The **shard key** choice determines balance and performance.
- **Consistent hashing** eases rebalancing; **cross-shard joins/transactions** are the main pain points.
- Combine **sharding (writes)** with **replication (reads + availability)** for scale.
