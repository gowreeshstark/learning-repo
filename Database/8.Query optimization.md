# Query Optimization in DBMS

## Overview
**Query optimization** is the process by which a DBMS finds the **most efficient execution plan** for a SQL query. Since SQL is **declarative** (you say *what* you want, not *how*), the optimizer decides the *how* — which indexes to use, join order, join algorithms, and access paths — to minimize cost (time, I/O, CPU).

> **Interview one-liner:** Query optimization picks the cheapest execution plan among many possible ways to run the same query.

---

## Why Query Optimization Matters
- The **same query** can be executed in many ways with hugely different performance.
- Reduces **response time**, **I/O**, **CPU**, and **memory** usage.
- Critical for **scalability** — a bad plan on a large table can be 1000x slower.

---

## Query Processing Pipeline

```
SQL Query
   │
   ▼
1. Parsing & Validation   → check syntax, tables, columns
   │
   ▼
2. Translation            → convert to relational algebra
   │
   ▼
3. Optimization           → generate & cost plans, pick cheapest
   │
   ▼
4. Execution              → run the chosen plan, return results
```

## Types of Optimization

### 1. Heuristic / Rule-Based Optimization (RBO)
Applies fixed **rules** regardless of data statistics.
**Key heuristics:**
- **Push selections (WHERE) down** — filter rows as early as possible.
- **Push projections (SELECT columns) down** — carry only needed columns.
- Perform **most restrictive** operations first (reduce intermediate rows).
- Replace **Cartesian product + selection** with a **join**.

### 2. Cost-Based Optimization (CBO)
Uses **statistics** (row counts, data distribution, index selectivity) to **estimate the cost** of multiple plans and choose the cheapest. Used by modern databases (PostgreSQL, Oracle, MySQL).

**Cost factors:** disk I/O, CPU cycles, memory, network (distributed).

> **Interview point:** RBO uses fixed rules; CBO uses table statistics to estimate and compare plan costs. Modern DBMS mainly use **CBO**.

---

## Statistics & the Optimizer
The optimizer relies on **statistics** stored about tables:
- **Cardinality** – number of rows.
- **Selectivity** – fraction of rows a condition returns (low selectivity value = more selective = fewer rows).
- **Histograms** – data distribution of column values.
- **Index information** – which columns are indexed, uniqueness.

> **Stale statistics** cause bad plans. Run `ANALYZE` / `UPDATE STATISTICS` to refresh them.

---

## Execution Plans (EXPLAIN) — Very Important

`EXPLAIN` (or `EXPLAIN ANALYZE`) shows **how** the DB will run a query.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 101;
```

**What to look for:**
- **Seq Scan (Full Table Scan)** → often bad on large tables; consider an index.
- **Index Scan / Index Seek** → good, uses an index.
- **Join type** (Nested Loop / Hash / Merge).
- **Estimated vs actual rows** → big mismatch = stale statistics.
- **Cost** and **execution time**.

---

## Join Algorithms (Common Interview Topic)

| Algorithm | How it works | Best when |
|-----------|--------------|-----------|
| **Nested Loop Join** | For each row in A, scan B | Small tables / indexed inner table |
| **Hash Join** | Build hash table on smaller table, probe with larger | Large, unsorted tables, equality joins |
| **Sort-Merge Join** | Sort both, then merge | Both inputs already sorted / range joins |

### Join Order
The **order** in which tables are joined dramatically affects cost. The optimizer tries to join to produce the **smallest intermediate results** first.

---

## Access Paths
- **Full Table Scan** – Read every row (fine for small tables or when returning most rows).
- **Index Scan** – Use an index to find rows (great for selective queries).
- **Index-Only Scan (Covering Index)** – All needed columns are in the index → no table access.

## Query Optimization Techniques (Practical / Interview Answers)

### 1. Use Indexes Wisely
Index columns in `WHERE`, `JOIN`, `ORDER BY`, `GROUP BY` (see [4.Indexing.md](4.Indexing.md)). Avoid over-indexing (slows writes).

### 2. Avoid `SELECT *`
Fetch only needed columns → less I/O, enables covering indexes.
```sql
-- Bad
SELECT * FROM users;
-- Good
SELECT id, name FROM users;
```

### 3. Make WHERE Conditions "Sargable"
Avoid wrapping indexed columns in functions — it prevents index use.
```sql
-- Bad (index on created_at not used)
WHERE YEAR(created_at) = 2024;
-- Good (index used)
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
```

### 4. Prefer JOINs over Correlated Subqueries
Correlated subqueries run once per outer row (slow); joins are usually optimized better.

### 5. Use EXISTS instead of IN (for large subqueries)
`EXISTS` can short-circuit; `IN` may materialize a large list.

### 6. Limit Rows Early
Use `LIMIT`/pagination; apply `WHERE` before `GROUP BY`, use `HAVING` only for aggregate filters.

### 7. Avoid Functions/Wildcards that Kill Indexes
```sql
LIKE '%abc'   -- leading wildcard → no index
LIKE 'abc%'   -- prefix → can use index
```

### 8. Reduce Data Early
Push filters and projections down; avoid `DISTINCT` and `ORDER BY` when unnecessary.

### 9. Batch Operations
Bulk inserts/updates instead of row-by-row to reduce round trips.

### 10. Keep Statistics Fresh
Run `ANALYZE` so the optimizer makes good decisions.

## WHERE vs HAVING (Interview Favorite)
- **WHERE** filters **rows before** grouping (can use indexes).
- **HAVING** filters **groups after** aggregation.
```sql
SELECT dept, COUNT(*) FROM emp
WHERE active = 1          -- filter rows first (efficient)
GROUP BY dept
HAVING COUNT(*) > 10;     -- filter groups after
```

## Materialized Views & Caching
- **Materialized View** – Precomputed query result stored on disk; speeds up expensive aggregations (must be refreshed).
- **Query result caching** – Cache frequent results (e.g., in Redis, see [14.REDIS.md](14.REDIS.md)).

## Interview Quick-Fire Q&A

**Q: What is query optimization?**
The process of choosing the most efficient execution plan for a SQL query.

**Q: Rule-based vs cost-based optimization?**
RBO uses fixed heuristics; CBO uses table statistics to estimate and compare plan costs.

**Q: How do you find why a query is slow?**
Use `EXPLAIN ANALYZE` to inspect the execution plan (scans, joins, estimated vs actual rows).

**Q: What is a sargable query?**
One whose WHERE clause can use an index (no function wrapping the indexed column).

**Q: Why can an index not be used?**
Leading wildcard `LIKE '%x'`, functions on the column, implicit type conversion, or low selectivity.

**Q: Name the join algorithms.**
Nested Loop, Hash Join, Sort-Merge Join.

**Q: Difference between WHERE and HAVING?**
WHERE filters rows before grouping; HAVING filters aggregated groups after.

**Q: What are database statistics used for?**
To estimate cardinality/selectivity so the optimizer picks the best plan.

**Q: Why avoid SELECT *?**
It fetches unnecessary columns, increases I/O, and prevents covering-index use.

**Q: EXISTS vs IN?**
EXISTS often performs better for large/correlated subqueries because it can short-circuit.

---

## Key Takeaways
- Optimizer converts **declarative SQL** into the **cheapest execution plan**.
- Two approaches: **Rule-based (heuristics)** and **Cost-based (statistics)** — modern DBs use CBO.
- Use **EXPLAIN/EXPLAIN ANALYZE** to diagnose plans.
- Key levers: **indexes, sargable predicates, join order/algorithm, avoid `SELECT *`, fresh statistics**.
- Know **join algorithms**, **WHERE vs HAVING**, and why **indexes get skipped**.
