# CAP Theorem in DBMS

## Overview
The **CAP Theorem** (Brewer's Theorem) states that a **distributed data store** can guarantee only **two of three** properties simultaneously: **Consistency**, **Availability**, and **Partition Tolerance**.

> **Interview one-liner:** In a distributed system, when a network partition happens, you must choose between **Consistency** and **Availability** — you can't have both.

---

## The Three Properties

### C — Consistency
Every read receives the **most recent write** or an error. All nodes see the **same data** at the same time.
> (Note: CAP consistency = **linearizability**, different from ACID's Consistency.)

### A — Availability
Every request receives a **(non-error) response**, without guaranteeing it contains the latest data. The system is **always up**.

### P — Partition Tolerance
The system continues to operate despite **network partitions** (messages lost/delayed between nodes).

```
         C
        / \
       /   \
      /     \
     A ───── P
  Pick any TWO
```

---

## Why You Must Choose

In a distributed system, **network partitions are unavoidable**, so **P is mandatory**. The real trade-off during a partition is between **C and A**:

- **CP** – Stay consistent, sacrifice availability (reject requests until resolved).
- **AP** – Stay available, sacrifice consistency (serve possibly stale data).
- **CA** – Only possible in a **single-node / non-distributed** system (no partitions).

---

## The Three Combinations

| Type | Guarantees | Behavior During Partition | Examples |
|------|-----------|---------------------------|----------|
| **CP** | Consistency + Partition tolerance | Rejects requests to stay consistent | MongoDB, HBase, Redis, Zookeeper |
| **AP** | Availability + Partition tolerance | Serves stale data, resolves later | Cassandra, DynamoDB, CouchDB |
| **CA** | Consistency + Availability | Only without partitions (single node) | Traditional single-node RDBMS |

> **Interview tip:** "CA" systems don't really exist in a distributed world — partitions will happen, so it's always **CP vs AP**.

---

## BASE vs ACID

NoSQL AP systems often follow **BASE** instead of **ACID**:

| ACID (SQL) | BASE (NoSQL) |
|------------|--------------|
| **A**tomicity | **B**asically **A**vailable |
| **C**onsistency | **S**oft state |
| **I**solation | **E**ventual consistency |
| **D**urability | |

- **Eventual Consistency** – Given no new updates, all replicas eventually converge to the same value.

---

## PACELC Theorem (Extension)
Extends CAP: **If Partition (P) → choose A or C; Else (E) → choose Latency (L) or Consistency (C).**
It highlights that even **without** partitions, there's a trade-off between **latency and consistency**.

```
if (Partition) → A vs C
else           → L vs C
```

## Interview Quick-Fire Q&A

**Q: State the CAP theorem.**
A distributed system can guarantee only two of Consistency, Availability, and Partition tolerance at once.

**Q: Why can't you have all three?**
Because partitions are inevitable; during one you must choose between rejecting requests (C) or serving stale data (A).

**Q: Is CAP consistency the same as ACID consistency?**
No. CAP consistency means all nodes see the latest write (linearizability); ACID consistency means valid state per constraints.

**Q: Give an example of a CP and an AP database.**
CP: MongoDB/HBase; AP: Cassandra/DynamoDB.

**Q: What does PACELC add?**
Even without partitions, there's a trade-off between latency and consistency.

---

## Key Takeaways
- Pick **two of three**: C, A, P — but **P is mandatory** in distributed systems.
- Real choice is **CP (consistency) vs AP (availability)** during a partition.
- **BASE + eventual consistency** power most AP NoSQL stores (see [13.NO Sql.md](13.NO%20Sql.md)).
- **PACELC** reminds us latency vs consistency matters even without partitions.
