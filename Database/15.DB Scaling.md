# Database Scaling in DBMS

## Overview
**Database scaling** is the process of increasing a database's capacity to handle growing **data volume, traffic, and concurrent users** while maintaining performance and availability. It ties together many previous topics: indexing, replication, partitioning, sharding, and caching.

> **Interview one-liner:** Scaling means growing your database's capacity — either by making the server bigger (**vertical**) or adding more servers (**horizontal**).

---

## Vertical vs Horizontal Scaling

### Vertical Scaling (Scale Up)
Add more resources (CPU, RAM, SSD) to a **single server**.

**Pros:** Simple, no app changes, keeps ACID/joins easy.
**Cons:** Hardware limit (ceiling), expensive, single point of failure.

### Horizontal Scaling (Scale Out)
Add **more servers** and distribute load across them.

**Pros:** Near-limitless scale, fault tolerant, cost-effective commodity hardware.
**Cons:** Complex (sharding, distributed transactions, consistency).

```
Vertical:   [ small ] → [ BIGGER server ]
Horizontal: [ server ] → [ server ][ server ][ server ]
```

| Aspect | Vertical (Up) | Horizontal (Out) |
|--------|---------------|------------------|
| Method | Bigger machine | More machines |
| Limit | Hardware ceiling | Virtually unlimited |
| Complexity | Low | High |
| Fault tolerance | Single point of failure | High |
| Cost | Expensive at high end | Commodity hardware |

## Techniques for Scaling Databases

### 1. Indexing
Speeds up reads by avoiding full table scans (see [4.Indexing.md](4.Indexing.md)). First and cheapest optimization.

### 2. Replication (Read Scaling)
Copy data to **replicas**; route **reads** to replicas, **writes** to primary (see [11.Replication.md](11.Replication.md)). Great for **read-heavy** workloads.

### 3. Partitioning & Sharding (Write/Storage Scaling)
Split large tables/datasets across partitions or servers (see [10.Partitioning and Sharding.md](10.Partitioning%20and%20Sharding.md)). Enables **horizontal write scaling**.

### 4. Caching
Store hot data in memory (e.g., **Redis**, see [14.REDIS.md](14.REDIS.md)) to offload the DB and cut latency.

### 5. Load Balancing
Distribute queries across multiple DB nodes/replicas to avoid hotspots.

### 6. Connection Pooling
Reuse DB connections instead of opening new ones per request — reduces overhead at scale.

### 7. Denormalization
Trade redundancy for fewer joins to speed up reads (see [9.DB Design.md](9.DB%20Design.md)).

### 8. CQRS / Read-Write Separation
Separate read and write paths/models so each can scale independently.

---

## A Typical Scaling Journey (Interview Story)

```
1. Single DB
2. Add Indexes + query tuning
3. Add Caching (Redis)
4. Add Read Replicas (replication)
5. Vertical scaling (bigger box)
6. Partitioning within DB
7. Sharding across servers (horizontal)
8. Use NoSQL / specialized stores where needed
```

> **Interview tip:** Always scale in **cheap-to-expensive** order — indexing and caching before sharding. Don't shard prematurely; it adds huge complexity.

## Read-Heavy vs Write-Heavy

| Workload | Best Techniques |
|----------|-----------------|
| **Read-heavy** | Caching + Read replicas + Indexing |
| **Write-heavy** | Sharding + Write-optimized stores + Batching |

## Challenges at Scale
- **Consistency vs availability** trade-offs (see [12.CAP Theorem.md](12.CAP%20Theorem.md)).
- **Distributed transactions** across shards (2-phase commit / sagas).
- **Data rebalancing** when adding nodes (consistent hashing).
- **Hotspots** from poor shard/partition keys.
- **Operational complexity** — monitoring, backups, failover.

## Interview Quick-Fire Q&A

**Q: Vertical vs horizontal scaling?**
Vertical adds power to one machine; horizontal adds more machines and distributes load.

**Q: How do you scale reads vs writes?**
Reads: replicas + caching. Writes: sharding / partitioning.

**Q: What's the first thing you'd do before sharding?**
Optimize with indexing, query tuning, caching, and read replicas — shard only when necessary.

**Q: Why is horizontal scaling harder?**
It introduces distributed data, consistency issues, and cross-node transactions.

**Q: How does caching help scaling?**
It serves hot data from memory, reducing DB load and latency.

**Q: What limits vertical scaling?**
Hardware ceilings, cost, and a single point of failure.

---

## Key Takeaways
- **Vertical** = bigger server (simple, limited); **Horizontal** = more servers (scalable, complex).
- Scale in order: **Indexing → Caching → Replication → Partitioning → Sharding**.
- **Reads** scale with replicas + caching; **writes** scale with sharding.
- At scale, manage **consistency, rebalancing, and distributed transactions**.
- This topic ties together indexing, replication, sharding, caching, CAP, and NoSQL.
