# Database Replication in DBMS

## Overview
**Replication** is the process of copying and maintaining the same data across multiple database servers (**replicas**). It improves **availability**, **read scalability**, **fault tolerance**, and **disaster recovery**.

> **Interview one-liner:** Replication keeps multiple copies of the same data in sync so the system stays available and reads can scale.

---

## Why Replicate?

1. **High Availability** – If one server fails, another serves requests.
2. **Read Scalability** – Distribute read queries across replicas.
3. **Fault Tolerance / Disaster Recovery** – Backup copies survive failures.
4. **Geo-distribution** – Place data near users to reduce latency.

> **Sharding vs Replication:** Sharding **splits** data across servers (write scaling); replication **copies** data (read scaling + availability). Real systems use both.

---

## Replication Architectures

### 1. Master-Slave (Primary-Replica)
- **One primary** handles all **writes**; **replicas** handle **reads**.
- Simple, common; replicas can lag behind (replication lag).

```
        Writes            Reads
Client ───────▶ PRIMARY ───────▶ Replica 1
                  │      └──────▶ Replica 2
                  └── replicates ──▶ (async/sync)
```

**Pros:** Simple, great for read-heavy workloads.
**Cons:** Single write bottleneck; failover needed if primary dies.

### 2. Master-Master (Multi-Primary)
- **Multiple primaries** accept **writes**; changes replicate to each other.

**Pros:** No single write bottleneck; high availability for writes.
**Cons:** **Write conflicts** must be resolved; more complex.

### 3. Peer-to-Peer
- All nodes are equal, each can read/write; common in distributed NoSQL (Cassandra).

---

## Synchronous vs Asynchronous Replication

| Aspect | Synchronous | Asynchronous |
|--------|-------------|--------------|
| Commit waits for | Replica to confirm | Primary only |
| Consistency | Strong (no data loss) | Eventual (possible lag) |
| Latency | Higher | Lower |
| Risk | Slower writes | Data loss if primary fails before sync |

- **Semi-synchronous** – Waits for **at least one** replica to acknowledge (a middle ground).

---

## Replication Lag
The delay between a write on the primary and its appearance on a replica.

**Problems it causes:**
- **Read-your-own-writes** violation (user updates data but reads a stale replica).
- **Monotonic reads** violation (data appears to go backwards).

**Mitigations:** Read from primary after a write, sticky sessions, or wait for replica catch-up.

---

## How Replication Works (Methods)
- **Statement-based** – Replays SQL statements (compact, but risky for non-deterministic functions like `NOW()`).
- **Row-based / WAL / Binlog** – Ships the actual row changes / write-ahead log (reliable, most common).
- **Snapshot + streaming** – Initial full copy, then stream ongoing changes.

---

## Failover
When the primary fails, a replica is promoted to primary.
- **Automatic failover** – Orchestrator detects failure and promotes a replica.
- **Challenges:** Split-brain (two primaries), choosing the most up-to-date replica, redirecting clients.

---

## Interview Quick-Fire Q&A

**Q: Difference between replication and sharding?**
Replication copies the same data for availability/read scaling; sharding splits data for write/storage scaling.

**Q: Master-slave vs master-master?**
Master-slave has one write node; master-master allows writes on multiple nodes but must resolve conflicts.

**Q: What is replication lag and why does it matter?**
Delay for replicas to catch up; causes stale reads and consistency issues.

**Q: Synchronous vs asynchronous replication trade-off?**
Sync = strong consistency but slower; async = fast but risks data loss on failure.

**Q: What is split-brain?**
Two nodes both believe they are primary after a network partition, causing conflicting writes.

---

## Key Takeaways
- Replication = **copies of data** for availability + read scaling.
- **Master-Slave** for read-heavy; **Master-Master** for write availability (with conflict handling).
- **Sync** = strong consistency, **Async** = performance with lag.
- Watch out for **replication lag**, **failover**, and **split-brain**.
