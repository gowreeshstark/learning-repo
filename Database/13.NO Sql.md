# NoSQL Databases in DBMS

## Overview
**NoSQL** ("Not Only SQL") databases are **non-relational** data stores designed for **scalability, flexibility, and high performance** with large volumes of unstructured or semi-structured data. They trade strict relational schemas and ACID for **horizontal scaling** and **flexible data models**.

> **Interview one-liner:** NoSQL = schema-flexible, horizontally scalable databases built for big data and high throughput, usually favoring availability over strict consistency.

---

## Why NoSQL? (SQL Limitations)
- RDBMS scales **vertically** (expensive) and is hard to shard.
- Rigid **schemas** slow down rapidly changing applications.
- Joins and ACID add overhead at massive scale.
- Poor fit for **unstructured / semi-structured** data (JSON, logs, IoT).

---

## Types of NoSQL Databases

### 1. Key-Value Store
- Data as **key → value** pairs; simplest and fastest.
- **Use cases:** caching, sessions, real-time lookups.
- **Examples:** Redis, DynamoDB, Riak.

```
"user:101" → { "name": "Alice", "age": 30 }
```

### 2. Document Store
- Stores **documents** (JSON/BSON); flexible nested schema.
- **Use cases:** content management, catalogs, user profiles.
- **Examples:** MongoDB, CouchDB.

```json
{ "_id": 101, "name": "Alice", "orders": [{ "id": 1, "total": 250 }] }
```

### 3. Column-Family (Wide-Column) Store
- Data stored in **columns** grouped into families; great for huge writes.
- **Use cases:** time-series, analytics, logging.
- **Examples:** Cassandra, HBase, Bigtable.

### 4. Graph Database
- Data as **nodes and edges** (relationships are first-class).
- **Use cases:** social networks, recommendations, fraud detection.
- **Examples:** Neo4j, Amazon Neptune.

---

## SQL vs NoSQL

| Aspect | SQL (Relational) | NoSQL |
|--------|------------------|-------|
| Schema | Fixed, predefined | Dynamic / flexible |
| Scaling | Vertical (scale up) | Horizontal (scale out) |
| Data model | Tables (rows/cols) | KV / Document / Column / Graph |
| Transactions | Strong ACID | Often BASE / eventual consistency |
| Joins | Supported | Limited / avoided |
| Best for | Structured data, complex queries | Big data, high throughput, flexible data |
| Examples | MySQL, PostgreSQL, Oracle | MongoDB, Cassandra, Redis, Neo4j |

---

## ACID vs BASE

| ACID (SQL) | BASE (NoSQL) |
|------------|--------------|
| Atomicity, Consistency, Isolation, Durability | **B**asically **A**vailable, **S**oft state, **E**ventual consistency |
| Strong guarantees | High availability & scalability |

> **Eventual consistency:** replicas converge over time; a read may briefly return stale data. Tied to the **CAP theorem** (see [12.CAP Theorem.md](12.CAP%20Theorem.md)).

---

## When to Use What

**Choose SQL when:**
- Data is structured and relationships matter.
- You need strong ACID transactions (banking, finance).
- Complex queries/joins and reporting.

**Choose NoSQL when:**
- Massive scale and high write throughput.
- Flexible / evolving schema (JSON, semi-structured).
- Availability > strict consistency (social feeds, IoT, caching).

## Interview Quick-Fire Q&A

**Q: What are the four types of NoSQL databases?**
Key-Value, Document, Column-Family, and Graph.

**Q: SQL vs NoSQL scaling?**
SQL scales vertically; NoSQL scales horizontally across commodity servers.

**Q: What is eventual consistency?**
Replicas may be temporarily inconsistent but converge to the same value over time.

**Q: When would you NOT use NoSQL?**
When you need strong ACID transactions and complex joins on structured data.

**Q: Give a use case for a graph database.**
Social networks or recommendation engines where relationships are central.

**Q: Is MongoDB CP or AP?**
CP by default (favors consistency during partitions).

---

## Key Takeaways
- NoSQL = **flexible schema + horizontal scaling** for big/unstructured data.
- Four families: **Key-Value, Document, Column-Family, Graph**.
- Follows **BASE / eventual consistency** rather than strict ACID.
- Choose based on **data model + consistency vs availability** needs.
