# Redis in DBMS

## Overview
**Redis** (REmote DIctionary Server) is an **in-memory, key-value** data store used as a **database, cache, and message broker**. Because it keeps data in RAM, it delivers **sub-millisecond** latency and extremely high throughput.

> **Interview one-liner:** Redis is a blazing-fast in-memory key-value store, most commonly used as a cache and for real-time features.

---

## Why Redis Is Fast
- **In-memory** storage (RAM, not disk).
- **Single-threaded** event loop → no lock contention, atomic operations.
- Efficient **data structures** implemented in C.
- Optional persistence so speed isn't lost to durability by default.

---

## Redis Data Structures (Important!)

| Type | Description | Use Case |
|------|-------------|----------|
| **String** | Text/number/binary (max 512MB) | Cache, counters |
| **List** | Ordered list (linked list) | Queues, activity feeds |
| **Set** | Unordered unique values | Tags, unique visitors |
| **Sorted Set (ZSet)** | Set ordered by score | Leaderboards, rankings |
| **Hash** | Field-value pairs (like an object) | User profiles/objects |
| **Bitmap / HyperLogLog** | Bit ops / approx counting | Analytics, cardinality |
| **Streams** | Append-only log | Event sourcing, messaging |
| **Geospatial** | Lat/long indexing | Location-based features |

```
SET user:101 "Alice"          # String
LPUSH queue "job1"            # List
ZADD leaderboard 100 "Alice"  # Sorted Set
HSET user:101 name "Alice"    # Hash
```

---

## Common Use Cases
1. **Caching** – Store frequent query results to offload the DB.
2. **Session store** – Fast, shared session storage for web apps.
3. **Rate limiting** – Count requests per user/time window.
4. **Leaderboards** – Sorted sets for real-time ranking.
5. **Pub/Sub messaging** – Real-time notifications/chat.
6. **Queues** – Lists or Streams as job queues.
7. **Distributed locks** – Coordinate across services (Redlock).

---

## Caching Strategies (Interview Favorite)

| Strategy | How it works |
|----------|--------------|
| **Cache-Aside (Lazy)** | App checks cache; on miss, load from DB and populate cache |
| **Write-Through** | Write to cache and DB together (consistent, slower writes) |
| **Write-Behind (Back)** | Write to cache first, async to DB (fast, risk of loss) |
| **Read-Through** | Cache library loads from DB on miss automatically |

### Eviction Policies (when memory is full)
- **LRU** (Least Recently Used), **LFU** (Least Frequently Used)
- **TTL-based** (expire keys), **Random**, **noeviction** (reject writes)

```
EXPIRE user:101 3600   # key expires in 1 hour (TTL)
```

---

## Persistence Options
- **RDB (Snapshotting)** – Point-in-time dumps at intervals. Compact, faster restart; may lose recent data.
- **AOF (Append-Only File)** – Logs every write; more durable, larger, slower.
- **Hybrid** – RDB + AOF combined (recommended).

---

## High Availability & Scaling
- **Replication** – Master-replica copies for read scaling & failover.
- **Redis Sentinel** – Monitors and performs **automatic failover**.
- **Redis Cluster** – **Sharding** data across nodes using **hash slots** (16384 slots) for horizontal scale.

---

## Cache Problems (Must-Know)
- **Cache Penetration** – Queries for non-existent keys hit the DB; fix with null-caching or Bloom filters.
- **Cache Avalanche** – Many keys expire at once, overloading the DB; fix with randomized TTLs.
- **Cache Stampede** – Many requests rebuild the same expired key; fix with locks/early recompute.

## Interview Quick-Fire Q&A

**Q: Why is Redis so fast?**
It stores data in memory and uses a single-threaded event loop with efficient C data structures.

**Q: Is Redis single-threaded?**
Core command execution is single-threaded (atomic, no locks); newer versions use threads for I/O.

**Q: RDB vs AOF persistence?**
RDB takes periodic snapshots (compact, may lose recent writes); AOF logs every write (more durable, larger).

**Q: How does Redis scale horizontally?**
Redis Cluster shards keys across nodes using 16384 hash slots.

**Q: What data structure for a leaderboard?**
Sorted Set (ZSet) — ordered by score.

**Q: What is cache-aside?**
App reads cache first; on miss, loads from DB and populates the cache.

**Q: Difference between Redis and Memcached?**
Redis has rich data structures, persistence, replication, and pub/sub; Memcached is a simpler pure cache.

## Key Takeaways
- Redis = **in-memory key-value store** → sub-millisecond speed.
- Rich **data structures** (String, List, Set, ZSet, Hash, Streams).
- Primary uses: **caching, sessions, leaderboards, rate limiting, pub/sub**.
- Persistence via **RDB/AOF**; HA via **Sentinel**; scale via **Cluster (sharding)**.
- Know the **caching strategies** and **cache penetration/avalanche/stampede**.
