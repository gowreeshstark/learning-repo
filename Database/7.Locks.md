# Locks in DBMS

## Overview
A **lock** is a mechanism used to control concurrent access to a data item. When a transaction needs to read or modify data, it acquires a lock to prevent other transactions from causing inconsistencies. Locks are the most common technique used by DBMS to implement **concurrency control** and preserve the **Isolation** property of ACID.

> **Interview one-liner:** A lock is a "reservation" a transaction places on data so that concurrent transactions don't corrupt each other's work.

---

## Why Locks Are Needed

Without locks, concurrent transactions cause anomalies:

1. **Lost Update** – Two transactions overwrite each other's changes.
2. **Dirty Read** – Reading data written by an uncommitted transaction.
3. **Non-Repeatable Read** – Same row read twice returns different values.
4. **Phantom Read** – New rows appear in a repeated range query.

Locks serialize conflicting operations so the final result is equivalent to some serial execution (**serializability**).

---

## Types of Locks

### 1. Shared Lock (S-Lock / Read Lock)
- Acquired for **reading** data.
- Multiple transactions can hold a shared lock on the same item **simultaneously**.
- Blocks any exclusive (write) lock.

### 2. Exclusive Lock (X-Lock / Write Lock)
- Acquired for **writing/updating/deleting** data.
- Only **one** transaction can hold it; blocks all other S and X locks.

### Lock Compatibility Matrix
```
              Requested
            S-Lock   X-Lock
Held  S-Lock  YES      NO
      X-Lock  NO       NO
```
**Rule:** Reads are compatible with reads; anything involving a write is incompatible.

### 3. Update Lock (U-Lock)
- Intermediate lock used to **prevent deadlocks** in a common read-then-write pattern.
- Compatible with S-lock but not with another U or X lock. Upgraded to X-lock when the write actually happens.

---

## Lock Granularity

The **level** at which a lock is applied. There is a trade-off between concurrency and overhead.

| Granularity | Concurrency | Overhead |
|-------------|-------------|----------|
| Database    | Lowest      | Lowest   |
| Table       | Low         | Low      |
| Page        | Medium      | Medium   |
| Row         | Highest     | Highest  |

- **Coarse-grained** (DB/table): fewer locks to manage, but low concurrency.
- **Fine-grained** (row): high concurrency, but more locks and higher management cost.

### Intention Locks (Multiple Granularity Locking)
Placed on a **higher level** (table) to signal intent to lock something at a **lower level** (row). They let the DBMS detect conflicts without scanning every row.
- **IS** – Intention Shared
- **IX** – Intention Exclusive
- **SIX** – Shared + Intention Exclusive

> **Interview tip:** Intention locks make hierarchical locking efficient — a transaction wanting a table lock can quickly see if any row is locked.

---

## Two-Phase Locking (2PL)

The most important locking **protocol** for guaranteeing serializability.

Each transaction runs in two phases:
1. **Growing Phase** – Locks are acquired; **no lock is released**.
2. **Shrinking Phase** – Locks are released; **no new lock is acquired**.

```
Locks
held  |        ___________
      |       /           \
      |      /             \
      |_____/               \_____
        growing    peak    shrinking
```

### Variants
| Variant | Description | Guarantees |
|---------|-------------|------------|
| **Basic 2PL** | Standard growing/shrinking | Serializability |
| **Strict 2PL** | Holds **all X-locks** until commit/abort | Serializable + recoverable, avoids cascading rollback |
| **Rigorous 2PL** | Holds **all locks (S & X)** until commit | Easiest to implement; most common in real DBMS |
| **Conservative 2PL** | Acquires **all locks upfront** | **Deadlock-free**, but hard to predict lock set |

> **Interview favorite:** Basic 2PL guarantees serializability but **can still deadlock** and can cause cascading rollbacks. Strict/Rigorous 2PL fix recoverability; Conservative 2PL prevents deadlocks.

---

## Deadlocks

A **deadlock** occurs when two or more transactions wait indefinitely for locks held by each other.

```
T1 holds X-lock on A, wants B
T2 holds X-lock on B, wants A
→ Both wait forever (circular wait)
```

### Four Coffman Conditions (all must hold)
1. Mutual Exclusion
2. Hold and Wait
3. No Preemption
4. Circular Wait

### Deadlock Handling Strategies

**1. Deadlock Prevention** – Design so a deadlock can't occur. Timestamp-based schemes:
- **Wait-Die** (non-preemptive): older waits, younger dies (aborts).
- **Wound-Wait** (preemptive): older wounds (aborts) younger, younger waits.

**2. Deadlock Avoidance** – Use ordering of resources or Conservative 2PL.

**3. Deadlock Detection & Recovery** – Maintain a **Wait-For Graph (WFG)**; a **cycle = deadlock**. Resolve by choosing a **victim** transaction to roll back.

**4. Timeout** – Abort a transaction that waits too long (simple but may abort unnecessarily).

---

## Lock-Related Problems

- **Deadlock** – Circular waiting (discussed above).
- **Starvation / Livelock** – A transaction repeatedly waits while others acquire the lock first. Solved with **fair queuing / aging**.
- **Lock Escalation** – DBMS converts many fine-grained locks (rows) into one coarse lock (table) to save memory; reduces concurrency.
- **Lock Contention** – Many transactions competing for the same lock, hurting throughput (hotspot rows).

---

## Locking vs Isolation Levels

Isolation levels are implemented largely via locking behavior:

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom | Typical Locking |
|-----------------|-----------|---------------------|---------|-----------------|
| Read Uncommitted | Possible | Possible | Possible | No read locks |
| Read Committed | No | Possible | Possible | Short-term read locks |
| Repeatable Read | No | No | Possible | Long-term S & X locks |
| Serializable | No | No | No | Range/predicate locks |

---

## Pessimistic vs Optimistic Concurrency Control

| Aspect | Pessimistic (Locking) | Optimistic (MVCC / Validation) |
|--------|-----------------------|--------------------------------|
| Assumption | Conflicts are likely | Conflicts are rare |
| Mechanism | Lock before access | Validate at commit |
| Best for | High-contention workloads | Read-heavy workloads |
| Downside | Blocking, deadlocks | Rollbacks on conflict |

> Many modern databases (PostgreSQL, Oracle) use **MVCC** so that **readers don't block writers and writers don't block readers**, using locks mainly for writes.

---

## Quick SQL Reference

```sql
-- Explicit shared/exclusive lock in a transaction
BEGIN;
SELECT * FROM Accounts WHERE id = 101 FOR SHARE;    -- shared lock
SELECT * FROM Accounts WHERE id = 101 FOR UPDATE;   -- exclusive lock
COMMIT;

-- Lock an entire table (MySQL)
LOCK TABLES Accounts WRITE;
UNLOCK TABLES;
```

## Interview Quick-Fire Q&A

**Q: Difference between shared and exclusive lock?**
Shared allows concurrent reads; exclusive allows a single writer and blocks everyone else.

**Q: Does 2PL guarantee no deadlocks?**
No. Basic/Strict 2PL guarantee **serializability**, not deadlock freedom. Only **Conservative 2PL** is deadlock-free.

**Q: What is the difference between Strict and Rigorous 2PL?**
Strict holds all **exclusive** locks till commit; Rigorous holds **all** (shared + exclusive) locks till commit.

**Q: How are deadlocks detected?**
Using a **Wait-For Graph** — a cycle indicates a deadlock; the DBMS aborts a victim.

**Q: What is lock escalation?**
Automatic conversion of many row-level locks into a single table-level lock to reduce overhead.

**Q: How do MVCC databases reduce locking?**
Readers see a consistent snapshot (old versions), so reads don't need locks and don't block writes.

**Q: What causes starvation and how to fix it?**
Unfair lock scheduling; fixed via **aging / fair FIFO queues**.

---

## Key Takeaways
- Two lock modes: **Shared (read)** and **Exclusive (write)**; compatibility drives concurrency.
- **2PL** ensures serializability; **Strict/Rigorous** variants add recoverability.
- **Deadlocks** are handled via **prevention (wait-die/wound-wait)**, **avoidance**, or **detection (Wait-For Graph)**.
- **Granularity** trades off concurrency vs overhead; **intention locks** make hierarchical locking efficient.
- Modern DBMS lean on **MVCC** to minimize read locking.
