# Database Indexing

## Overview
Database indexing is a data structure technique used to quickly locate and access data in a database. Indexes create a separate structure that stores sorted values from one or more columns, allowing the database engine to find rows faster without scanning the entire table.

---

## What is an Index?

An index is a database object that improves the speed of data retrieval operations. It works similar to a book's index, where you can quickly find topics instead of reading every page.

**Key Characteristics:**
- Reduces query execution time
- Slows down write operations (INSERT, UPDATE, DELETE)
- Consumes additional disk space
- Needs periodic maintenance

---

## Types of Indexes

### **1. Primary Key Index**
Automatically created on the primary key column. Ensures uniqueness and fast retrieval.

```sql
CREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    StudentName VARCHAR(100)
);
```

---

### **2. Unique Index**
Ensures all values in the indexed column are different.

```sql
CREATE UNIQUE INDEX idx_email ON Users(Email);
```

---

### **3. Composite Index (Multi-Column Index)**
Index created on multiple columns to speed up queries filtering on those columns.

```sql
CREATE INDEX idx_student_course ON Enrollment(StudentID, CourseID);
```

**Example Query:**
```sql
SELECT * FROM Enrollment 
WHERE StudentID = 1 AND CourseID = 101;
```

---

### **4. Full-Text Index**
Used for text searching in large text columns.

```sql
CREATE FULLTEXT INDEX idx_content ON Articles(Content);
```

**Example Query:**
```sql
SELECT * FROM Articles 
WHERE MATCH(Content) AGAINST('database' IN BOOLEAN MODE);
```

---

### **5. Spatial Index**
Used for geographic data and spatial queries.

```sql
CREATE SPATIAL INDEX idx_location ON Locations(GeometryColumn);
```

---

### **6. Bitmap Index**
Used for low-cardinality columns (columns with few distinct values).

```sql
-- Typically used for columns like Gender, Status
-- Example in Oracle:
CREATE BITMAP INDEX idx_status ON Orders(Status);
```

---

### **7. Hash Index**
Uses hash function to locate data. Fast for equality searches but not range queries.

```sql
CREATE INDEX idx_username USING HASH ON Users(Username);
```

---

## How Indexes Work

### **Index Structure - B-Tree (Most Common)**

```
                    [50]
                   /    \
              [25]        [75]
             /    \      /    \
           [10]  [30] [60]   [85]
           /  \   / \  | \     | \
          5   15 20 35 55 65  80  95
```

**Characteristics:**
- Self-balancing tree structure
- All leaf nodes at same level
- Efficient for range queries
- Logarithmic time complexity O(log n)

---

## Index Usage Examples

### **Before Index:**
```sql
-- Without index: Full table scan (slow)
SELECT * FROM Employees WHERE Email = 'john@example.com';
-- Scans all 1 million rows: O(n)
```

### **After Index:**
```sql
-- Create index on Email column
CREATE INDEX idx_email ON Employees(Email);

-- With index: Direct lookup (fast)
SELECT * FROM Employees WHERE Email = 'john@example.com';
-- Direct access: O(log n)
```

## Architectural Handling of Indexes

### **1. Storage Architecture**

```
Database File System
├── Data Files
│   ├── Table Data (Heap/Clustered)
│   └── Row Data
└── Index Files
    ├── Primary Key Index
    ├── Secondary Index 1
    ├── Secondary Index 2
    └── Full-Text Index
```

---

### **2. Index Creation Process**

```
1. User creates index: CREATE INDEX idx_name ON table(column)
                          ↓
2. Query Optimizer receives request
                          ↓
3. Database Engine allocates space
                          ↓
4. Scans all rows in table
                          ↓
5. Sorts data by indexed column
                          ↓
6. Creates B-Tree structure
                          ↓
7. Stores index in index file
                          ↓
8. Registers index in system catalog
```

---

### **3. Query Execution with Index**

```
User Query: SELECT * FROM Employees WHERE Salary > 50000
                          ↓
Query Parser (validates syntax)
                          ↓
Query Optimizer (checks available indexes)
                          ↓
Decision: Use index on Salary column OR full scan?
                          ↓
If Index Exists:
  - Traverse B-Tree to find first value > 50000
  - Follow leaf nodes to collect all matching rows
  - Return results (fast: O(log n + k))
                          ↓
If No Index:
  - Scan entire table row by row
  - Compare each row with condition
  - Return results (slow: O(n))
```

---

### **4. Index Maintenance**

**During INSERT:**
```
INSERT INTO Employees VALUES (5, 'Jane', 60000)
                          ↓
1. Insert row into table data file
2. Update all affected indexes
3. Rebalance B-Trees if necessary
4. Update index statistics
```

**During UPDATE:**
```
UPDATE Employees SET Salary = 70000 WHERE EmployeeID = 5
                          ↓
1. Find row using clustered index
2. Update row in table
3. Remove old index entry
4. Insert new index entry
5. Rebalance affected indexes
```

**During DELETE:**
```
DELETE FROM Employees WHERE EmployeeID = 5
                          ↓
1. Find row using index
2. Mark row as deleted
3. Remove entries from all indexes
4. Rebalance B-Trees
```

---

### **5. Index Organization - Clustered vs Non-Clustered**

**Clustered Index:**
```
Table: Employees
┌─────────────────────────────────┐
│ Clustered Index (Primary Key)   │
│ EmployeeID (sorted)             │
├─────────────────────────────────┤
│ 1  │ John  │ 50000              │
│ 2  │ Jane  │ 60000              │
│ 3  │ Bob   │ 55000              │
└─────────────────────────────────┘
```

**Non-Clustered Index:**
```
Clustered Index (EmployeeID):  1, 2, 3, 4, 5...

Non-Clustered Index (Salary):
┌──────────────────┐
│ Salary │ RowID   │
├──────────────────┤
│ 50000  │ Ptr→1   │
│ 55000  │ Ptr→3   │
│ 60000  │ Ptr→2   │
│ 65000  │ Ptr→4   │
└──────────────────┘
```

## Index Performance Considerations

### **When to Create Indexes:**
✓ Columns frequently used in WHERE clause  
✓ Columns used in JOIN conditions  
✓ Columns used in ORDER BY or GROUP BY  
✓ Large tables with frequent reads  
✓ Low-cardinality columns (few unique values)

### **When NOT to Create Indexes:**
✗ Small tables (< 1000 rows)  
✗ Columns with many NULL values  
✗ Columns with low selectivity  
✗ Tables with frequent INSERT/UPDATE/DELETE  
✗ Columns that are rarely queried

---

## Index Best Practices

```sql
-- 1. Create index on frequent search columns
CREATE INDEX idx_department ON Employees(DepartmentID);

-- 2. Use composite indexes for multi-column queries
CREATE INDEX idx_dept_salary ON Employees(DepartmentID, Salary);

-- 3. Avoid over-indexing
-- Too many indexes slow down writes

-- 4. Monitor index performance
-- SQL Server example:
SELECT * FROM sys.dm_db_index_usage_stats;

-- 5. Rebuild fragmented indexes
ALTER INDEX idx_email ON Employees REBUILD;

-- 6. Reorganize moderately fragmented indexes
ALTER INDEX idx_email ON Employees REORGANIZE;

-- 7. Drop unused indexes
DROP INDEX idx_unused ON Employees;
```

---

## Index Statistics

Database maintains statistics about indexes:

```sql
-- View index statistics (SQL Server)
DBCC SHOW_STATISTICS (Employees, idx_email);

-- Update statistics
UPDATE STATISTICS Employees idx_email;
```

**Statistics Help:**
- Query optimizer makes better decisions
- Improves query execution plans
- Should be updated regularly

## Example Scenario

**Scenario:** E-commerce database with 10 million orders

**Without Indexes:**
```sql
SELECT OrderID, Amount FROM Orders 
WHERE CustomerID = 12345 AND OrderDate > '2024-01-01';
-- Time: ~8 seconds (full scan of 10M rows)
```

**With Indexes:**
```sql
CREATE INDEX idx_customer_date ON Orders(CustomerID, OrderDate);

SELECT OrderID, Amount FROM Orders 
WHERE CustomerID = 12345 AND OrderDate > '2024-01-01';
-- Time: ~0.05 seconds (index seek)
```

**Performance Improvement: 160x faster**

## Summary

| Aspect | Details |
|--------|---------|
| **Purpose** | Speed up data retrieval |
| **Cost** | Extra disk space, slower writes |
| **Best Type** | B-Tree for most scenarios |
| **Maintenance** | Rebuild/reorganize periodically |
| **Monitoring** | Track usage and fragmentation |
| **Strategy** | Index selective columns, avoid over-indexing |
